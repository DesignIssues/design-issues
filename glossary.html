Glossary

the words this book could not avoid

Every definition here is written for somebody meeting the term for the first time, and avoids leaning on the others. Where a chapter treats the idea properly, it is named.

URIUniform Resource Identifier
A name for something, written so that it works anywhere in the world. Web addresses are the familiar kind. The point of a URI is that it means the same thing to everybody it is given to. Chapter 2
URLUniform Resource Locator
An older word for the same thing as a URI, still in common use. This book follows its source in mostly saying URI, and treats the distinction between a name and an address as a mistake: see Chapter 3. Chapter 3
HTTPHypertext Transfer Protocol
The rules a browser and a server follow when one asks the other for a page. It says how to ask, how to answer, and what the answer means. Chapter 20
server
A computer, or a program running on one, that holds pages or data and hands them out when asked. The program doing the asking, usually a browser, is called the client.
header
A labelled line at the top of a message, saying something about what follows: what kind of file it is, when it was made, how long it may be kept. Every request and reply on the Web carries several.
status code
The three-digit number at the start of a server’s reply. 200 means “here it is”, 404 “not found”, 303 “look over there instead”. Chapter 7
redirect
A reply from a server that, instead of the thing asked for, gives another address to try. The browser follows it, usually without the reader noticing. Chapter 8
httpRange-14
The name of a long argument, settled by the TAG in 2005, over whether a plain web address can name a person or an idea as well as a page. The answer was a convention: the server replies with the status code 303 and points to a page about the thing. Chapter 7
GET
The kind of request that only asks for something. Following a link sends one. It must never change anything, so it is always safe to repeat. Chapter 2
POST
The kind of request that asks a server to act: place an order, send a message, add a comment. Unlike fetching, it may commit the person who sends it to something. Chapter 84
PUT
The kind of request that stores a document at a chosen address, replacing whatever was there. Chapter 50
cache
A store of copies kept near the reader, so that a page fetched once need not be fetched again. Its hard part is knowing when a copy has gone out of date.
HTMLHypertext Markup Language
The format web pages are written in. Text, with tags around parts of it saying this is a heading, this is a link, this is a picture.
XML
A general way of putting tags around things, from which many formats were built. Related to HTML, and more strict: a document is either well formed or it is rejected. Chapter 17
markup
Tags written into a text to say what its parts are: this is a heading, this is a link. HTML and XML are both markup languages.
XHTML
HTML rewritten to obey the strict rules of XML, so that a page with a mistake in it is rejected rather than guessed at. Chapter 23
parser
The part of a program that reads text written in some format and works out its structure, so that the rest of the program can use it.
JSONJavaScript Object Notation
A plain, compact text format for data: lists and labelled values, nested inside each other. Most programs on the Web now exchange data in it.
media typealso called a MIME type
A short label saying what kind of thing a file is: a web page, a photograph, a sound recording. It travels with the file and tells the receiving program how to read it. Chapter 11
fragment identifierthe part after a #
The piece of a web address after the hash. It names a part of, or a view of, whatever the rest of the address names. It is never sent to the server: the browser that already has the page works it out. Chapter 11
schemethe part before the colon
The first word of a web address, such as https. It says which set of rules applies to the rest of the address. Chapter 4
DNSthe Domain Name System
The system that turns a name like example.org into the machine that answers for it. It is also how the Web decides who is responsible for what: owning the name means answering for what is served under it. Chapter 6
domain name
A name such as example.org, rented from a registry, under which a person or organisation publishes. Whoever holds the name decides what its addresses mean, for as long as they keep paying for it. Chapter 13
top-level domain
The last part of a domain name, such as .org or .uk. Each is run by one organisation, which rents out the names beneath it. Chapter 79
ICANNInternet Corporation for Assigned Names and Numbers
The non-profit body that oversees domain names at the top, deciding which top-level domains exist and who runs each. Chapter 79
IPInternet Protocol
The lowest common layer of the Internet. It gives every connected machine a number, its IP address, and carries small packets of data from one number to another, without promising they arrive. Chapter 6
TCPTransmission Control Protocol
The layer on top of IP that makes delivery reliable: it numbers the packets, resends any that are lost and puts them back in order, so two programs can talk as if along a wire. Chapter 6
ISPinternet service provider
The company that connects a home or office to the Internet and carries its traffic. Chapter 78
net neutrality
The principle that an ISP must treat all traffic alike: not block sites, not slow some down, and not charge to speed others up. Chapter 78
dereference
To look something up. Given a name, go and fetch what it names. Chapter 49
opaque
Something that may be used but not looked inside. A path in a web address is opaque to a browser, which passes it on without trying to work out what it means. Chapter 2
namespace
A set of terms owned by one group, so that two groups can each use the word “title” for different things without colliding. Chapter 17
vocabularyalso called an ontology
An agreed set of terms for talking about some subject, published so that anyone can use them and mean the same thing. Chapter 51
Dublin Core
One of the oldest vocabularies for describing documents: title, creator, date, subject and a few more. Libraries and archives use it widely.
FOAFFriend of a Friend
A vocabulary for describing people and who they know: a name, a photograph, a home page, a list of friends.
schema
A description of what a document or a set of data is allowed to contain. Used to check that something is well formed before relying on it. Chapter 17
metadata
Data about data: who wrote a document, when, in what language, under what licence. Written so that a program, not only a person, can use it. Chapter 27
RDFthe Resource Description Framework
A way of writing data as a pile of simple statements, each of the form “this thing has that property with this value”. Because every statement stands alone, data from different places can simply be put together. Chapter 32
triple
One statement in that form: a subject, a property and a value. “This page · was written by · Ora”. Chapter 32
graph
What a pile of such statements makes when drawn: things as dots, relationships as arrows between them. Chapter 32
Linked Data
Data published so that the things it mentions have addresses that can be looked up, and so that it points at other people’s data. Four rules, set out in Chapter 49. Chapter 49
Semantic Web
The name for the whole project of putting data, rather than only documents, on the Web. Not artificial intelligence: see Chapter 31. Chapter 30
ontology
A vocabulary, usually one with some structure saying how its terms relate to each other. Chapter 88
inference
Working out something that follows from what is already known. If every cat is an animal and this is a cat, then this is an animal. Chapter 40
Turtleand N3, its larger relative
A way of writing those statements down that a person can read. N3 adds rules and logic to it. Chapter 42
N3Notation3
Turtle with rules and logic added. Curly brackets let a group of statements be treated as one thing, so that a rule can say “if these are true, then so are those”. Chapter 42
SPARQL
A language for asking questions of data written as statements, the way a database query language asks questions of tables. Chapter 30
relational database
The ordinary kind of database, which keeps data in tables of rows and columns, with tables linked by shared values. Chapter 33
SQL
The standard language for asking questions of a relational database and changing what it holds. Chapter 33
OWLthe Web Ontology Language
A language for saying how the terms in a vocabulary relate: this kind of thing is a kind of that, no two things share this value, and so on. Chapter 34
reification
Describing a statement as a thing, so that something can be said about it. “Jane said that”, where “that” is itself a statement. Chapter 44
monotonic
A system is monotonic when adding new information never withdraws an old conclusion. It matters because on the Web anyone may add information at any time, without asking. Chapter 42
same-origin policy
The rule that code on a page from one site may not read data from another. It is what stops a malicious page raiding somebody’s bank, and what makes combining data from several places difficult. Chapter 68
CORSCross-Origin Resource Sharing
The permission a server gives so that pages from other sites may read its data, relaxing the rule above. Chapter 70
encryption
Scrambling a message so that only someone holding the right key can read it. A key here is a long secret number. Chapter 67
public keyand private key
A pair of keys made together. The private one is kept secret; the public one is given to anybody. What one of the pair locks, only the other can open, which makes both encryption and digital signatures possible. Chapter 37
digital signature
A seal made with a private key and attached to a document. Anyone with the matching public key can check that the document came from the key’s holder and has not been altered since. Chapter 37
hash
Two things in this book. The # sign in a web address, after which comes a fragment identifier. And a short fingerprint worked out from a piece of data, which changes completely if a single character of the data changes: used to check that a copy is exact.
TLSand the https prefix
The encryption that protects a connection, so that nobody in between can read or alter what passes. Chapter 67
access control
The rules saying who may read or change what, and the machinery that enforces them.
OAuth
A widely used scheme by which a person lets one site reach some of their data held by another, without handing over a password.
PKIpublic key infrastructure
The arrangement by which a handful of companies vouch for who owns a web address, which is how a browser decides a site is what it claims. Chapter 66
certificate
A small signed document saying that a public key belongs to a particular site or person. Browsers check one before showing a padlock. Chapter 69
certificate authority
A company that issues certificates and is trusted, by browsers, to have checked who it issued them to. Chapter 66
poda personal online data store
A place on the Web that holds one person’s data under that person’s control, which any application may read or write with permission. Chapter 54
Solid
The project to build that: a person’s data in one place they own, with applications kept separate from it. Chapter 54
WebID
A web address that stands for a person. Looking it up gives a profile the person controls, so that one name can be used to sign in anywhere. Chapter 54
content negotiation
The exchange in which a browser says what forms it can handle and the server picks one. It is how a single address can serve a page in the reader’s language, or a picture in a format the device supports. Chapter 10
idempotent
An operation that can be repeated without further effect. Asking for a page is idempotent; buying a book is not. Chapter 2
APIApplication Programming Interface
The set of commands one program offers to others: what can be asked for, how to ask, and what comes back. Chapter 65
SMTPSimple Mail Transfer Protocol
The rules by which email is passed from one mail server to another.
RSS
A standard format for a site’s list of latest posts. A feed reader checks the list regularly and shows what is new. Chapter 64
DRMdigital rights management
Software that lets a film or a book be played on a person’s own machine while stopping them from copying it. Chapter 80
blockchain
A shared ledger, copied to every participant, to which entries can be added but not changed. No single party keeps it, so none can quietly rewrite it. Chapter 81
specificationoften shortened to spec
The document that defines a format or a protocol precisely enough that two people can build things that work together without meeting. Chapter 21
W3Cthe World Wide Web Consortium
The body that publishes many of the Web’s specifications. Founded in 1994 and directed for most of its history by the author of these notes.
Recommendation
The Consortium’s word for a finished specification, approved by its members after a period of testing. A W3C standard, in all but name. Chapter 21
RFCRequest for Comments
The numbered documents in which the Internet’s protocols are published. The name is a relic of when they really were requests for comment.
IETFthe Internet Engineering Task Force
The open body of engineers that develops the Internet’s protocols and publishes them as RFCs.
IANAthe Internet Assigned Numbers Authority
The office that keeps the Internet’s official lists: which media types and schemes exist, and which top-level domains, and who runs each.
TAGthe Technical Architecture Group
A small group at the Consortium that rules on questions about how the Web fits together. Several chapters here record arguments it settled.
