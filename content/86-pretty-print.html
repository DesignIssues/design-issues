The short version

Write data so people can read it. Same data, same text. Small change, small diff.

The question

Written in October 2023. “Pretty printing” is formatting code “so that it is easy to read by humans, and aesthetically pleasing”. The note asks how a program should lay out data in a Solid pod (the personal data store of Chapter 54), and argues that legibility is a system property rather than a courtesy.

86.1 The view-source effect

The first reason given connects this note to the whole history:

The "view source effect" which allowed the web to spread though people copying and adapting each others web pages is important linked data in Solid pods too. Pretty Printing, 2023

Chapter 56 traced how the Web spread: copy, change, look, show someone. Copying needs a source that a stranger can read; a format legible only through a tool loses that step, and the others with it.

He then reports the experience of the field, and answers the obvious objection:

It has been the long communal experience in the internet protocol design community that simple text formats (like FTP, SNTP, HTTP, HTML, XML) have been key to adoption and understanding of new systems. Pretty Printing, 2023
So while you can ship a binary format and give everyone tools for translating it into something legible, actually is is better to ship legible formats directly across the net. Pretty Printing, 2023

86.2 Small change, small difference

The part of a program that writes data out as text is its serialiser. The note asks two things of it. First, it is useful “for the same data to consistently give the same text”. Second, “small changes in the data produce small changes in the text”. The second matters because of version control: tools such as Mercurial, git, SVN and CVS keep every past version of a file and show, as a diff, the lines that changed between two of them.

Tests benefit too. A test compares actual output with expected output; the note advises comparing pretty-printed versions rather than raw triples, so a person can see why they differ.

86.3 Writing, not only reading

Most discussions of formatting consider only the reader. The note does not:

Legibility and aesthetic properties affect not only reading code but also people writing it. If are expressing by hand instance data, from random facts through configuration files to ontologies and rules, being able to write it in a clear, English like way also is more pleasant, and easier to check for mistakes. Pretty Printing, 2023

This is the case for the notation of Chapter 42, made on grounds of comfort rather than logic: a syntax close to a sentence is easier to get right by hand.

When a group is collaborating the same same data document, such as on a whiteboard or in a chat, then legibility and writability are both important. Pretty Printing, 2023

Data gets pasted into conversations, and a format that can be read in a chat window without tooling is one a team can discuss.

86.4 The argument in general

The note lists six benefits of different kinds; the case does not rest on the first.

The note ends with a caution. Indentation, line length and the “spaces or tabs” question are matters of taste, and a developer whose output users will see must guess their preferences rather than impose his own.

86.5 What makes Turtle legible

Pod data is usually Turtle, JSON-LD, or N3 (a superset of Turtle). Turtle lets spaces and line breaks be used freely, and has shorthands a serialiser should use:

FeatureLong formShort form
Prefix<http://xmlns.com/foaf/0.1/name>foaf:name
SemicolonSubject repeatedp:joe foaf:name "Joe"; foaf:age 42.
CommaSubject and property repeatedp:joe foaf:knows p:ann, p:bob.
Square bracketsBlank node labelled _:b1[ foaf:name "Ann" ]
ParenthesesA list built node by node( 1 2 3 )
Raw number"42"^^xsd:integer42

N3 adds raw dates, an is … of form for links pointing in, @keywords to drop leading colons, and curly brackets for nested graphs. Of shared sketching in a chat, the note remarks: “(This is what N3 was originally made for.)”

What happened since

  • A canonical form, but not a pretty one. RDF Dataset Canonicalization (W3C Recommendation, May 2024) writes any dataset as a deterministic list of N-Quads lines for comparison and signing. That meets the first requirement of section 86.2, but the output is not meant for reading and does not promise small diffs.
