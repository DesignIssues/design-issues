The short version

Write data so people can read it, because the Web spread by people copying what they could read. Always write the same data the same way. Then a one-field edit shows up as a one-line change in version control.

The question

Change one number in a person’s record, an age from 41 to 42, and save it. One program writes back a file in which one line differs. Another rewrites the whole record in a new order, burying the change. The data is identical; only the program that wrote it out differs. This October 2023 note asks how such a program should write data so that people can read it.

“Pretty printing” is formatting code “so that it is easy to read by humans, and aesthetically pleasing”. The note applies it to data in a Solid pod (the personal data store of Chapter 54).

86.1 Why the Web could be learnt by copying

The first reason is about developers trying out existing programs, who “need to be able see how they work. Then, when they are making their own applications, to be able to understand what is happening and what has gone wrong.”

The "view source effect" which allowed the web to spread though people copying and adapting each others web pages is important linked data in Solid pods too. Pretty Printing, 2023

(That is, the effect matters for linked data in pods too.) Chapter 56 traced that loop: copy a page, change it, see it at once, send the URL. Copying needs a source a stranger can read. The field’s experience agrees:

It has been the long communal experience in the internet protocol design community that simple text formats (like FTP, SNTP, HTTP, HTML, XML) have been key to adoption and understanding of new systems. So while you can ship a binary format and give everyone tools for translating it into something legible, actually is is better to ship legible formats directly across the net. Pretty Printing, 2023

On our reading, every pod should teach its format, as early web pages taught HTML.

86.2 One fact changed, one line changed

The part of a program that writes data out as text is its serialiser. The note asks it, first, “for the same data to consistently give the same text”; second, that “small changes in the data produce small changes in the text”. The second matters for version control: tools such as git keep every past version of a file and show, as a diff, the lines that changed between two.

Pod data is a graph of triples, each one statement: subject, property, value. Figure 86.1 shows them in Turtle, a text form common in pods: read p:joe as ‘Joe’, foaf:name as ‘name’, and a as ‘is a’ (section 86.5 explains the short names). In a diff, lines marked − were removed and lines marked + were added.

For tests, the note advises comparing pretty-printed output rather than raw triples, so a person can see why they differ.

86.3 Writing, not only reading

Legibility helps the writer too:

Legibility and aesthetic properties affect not only reading code but also people writing it. If are expressing by hand instance data, from random facts through configuration files to ontologies and rules, being able to write it in a clear, English like way also is more pleasant, and easier to check for mistakes. Pretty Printing, 2023

It matters most when several people shape the same data together, on a whiteboard or in a chat: “Being able to share and co-design a bit of data is key to the remote collaborative design process.” N3 (Chapter 42), a syntax close to a sentence, was first made for exactly this.

86.4 Smaller files, the benefit the note doubts

The note’s sixth benefit, after the five above, is size. With Turtle’s shorthands, triples “can take significantly less space”, as the two panels of Figure 86.3 show. Yet the note hedges at once: “This may or may not be important. The text may get compressed at another stage.” The argument rests on people, not bytes.

86.5 Shorthands that make data read like sentences

Pod data is usually Turtle, JSON-LD, or N3 (a superset of Turtle). Turtle allows free use of spaces and line breaks, and a serialiser should use its shorthands: the four in Figure 86.3, plus square brackets for a blank node (a thing with no name of its own) and parentheses for a list.

N3 adds a few more, such as dates written plainly and a way to write a link backwards, so that everything about one thing can be written in one place.

The last word is on taste. Indentation, line length and the “spaces or tabs” question, which “is infamous for bike-shedding”, are matters of taste; a developer whose output users see must guess their preferences, not just insert his own. The note keeps out of it: “I won’t give you my favorite settings here, to keep the topic on the principles.”

What happened since

  • A canonical form, but not a pretty one. RDF Dataset Canonicalization (W3C Recommendation, May 2024) writes any dataset as a deterministic list of lines for comparison and signing. That meets the first requirement of section 86.2, but is not meant for reading and does not promise small diffs.
  • Turtle revised. From 2022 the W3C RDF-star Working Group revised Turtle for RDF 1.2, adding syntax for statements about statements.
