The short version

Calendar invitations pass between programs in a standard text format called iCalendar. This note reads its specification closely, asking how it would look as simple linked data.

Most of it translates neatly, because the structure is already there. The faults found are common ones: no single list of what each field may hold, behaviour shown only in examples, relationships dressed up as objects, and a rule letting each field set its own grammar, so no general reader can exist. Above all, the format says what a meeting is but not what sending one means. The same checks apply to any data format.

The question

In October 2001 Berners-Lee spent a few hours reading fifty pages of iCalendar, the specification for exchanging calendar entries, published as RFC 2445 (an RFC is one of the numbered documents that define internet standards), with a view to evaluating proposals for putting it into XML. The note is what he found: a worked example of the method Chapter 26 describes.

My conclusion early on was that the spec should be written in terms of RDF properties, particularly as it has a clear property/value and parameter/value structure. Building an RDF model: A quick look at iCalendar, 2001

RDF is a way of writing data as subject–property–value statements. He reached that view early, even though RFC 2445 never mentions RDF: the structure was already there.

What an iCalendar line looks like

iCalendar is plain text, one property per line. Two examples quoted in the note attach a file to an event: 

ATTACH;FMTTYPE=image/basic;ENCODING=BASE64;VALUE=BINARY:MIICajCC…
ATTACH:http://xyz.com/public/quarterly-report.doc

The name before the first semicolon is the property. The NAME=value pairs after it are its parameters. What follows the colon is the value: the file encoded as text, or its address.

A harder example from the note: the attendee line below names c@y.com, but adds that the invitation came (was delegated) from b@y.com and has been passed on to a@y.com.

A recurrence rule is a string holding its own attribute–value pairs: the whole model escaped into a field.

A summary of domains and ranges, he says, would make the specification much clearer. Prose specifications rarely have one, because they describe fields where they are used.

The third finding is a serious kind of defect:

The parameter value type of "URI" implicitly causes dereferencing. This is not clear from the spec but is assumed by the examples. Building an RDF model: A quick look at iCalendar, 2001

To dereference an address is to fetch what it names. Here a network request is triggered by something only an example shows.

The last two findings are one mistake. Reification means turning a statement into a thing that can itself be described. The note calls RELTYPE=SIBLING a classic wanton reification: just say SIBLING. Similarly, an encoding relates the attached file to the string that carries it.

63.3 The line that stops general parsing

One sentence of the specification draws the sharpest reaction. ABNF is the grammar notation internet standards (RFCs) use:

"Each property defines the specific ABNF for the parameters allowed on the property" This makes general parsing impossible, direct conversion into XML difficult. Building an RDF model: A quick look at iCalendar, 2001

If every field defines its own grammar, a program cannot even tell where one parameter ends without knowing the property it is reading. There is no generic reader, only readers that implement the whole specification, and each new field is a change to every one of them.

The only hope is that in fact that it not true and there is more consistency than this line leads you to believe! This sounds like a remake of the RFC822 problem which HTTP has in spades: One parser per page of the spec. Building an RDF model: A quick look at iCalendar, 2001

RFC 822, the 1982 email-header standard, gives each header its own syntax; Chapter 32 treats that as a symptom of a missing model. Here the defect reappears in a format designed sixteen years later.

What happened since

  • The mapping was built. An RDF calendar workspace, which the note’s own preface mentions, began in late 2002 with running code, example data and schemas.
  • The protocol was next door. It was in a companion RFC (iTIP, RFC 2446, 1998), revised as RFC 5546 in 2009; CalDAV (RFC 4791, 2007) added server access.
  • The format was revised, not restructured. RFC 5545 (2009) replaced RFC 2445 and kept per-property parameters.
  • XML and JSON forms arrived. xCal (RFC 6321, 2011) and jCal (RFC 7265, 2014), the kind of translation he was evaluating.
  • The note joined the series in 2014, its preface says, because of later work on RDF, iCalendar and vCard.
