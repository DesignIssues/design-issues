The short version

Web pages spread because anyone could copy one, change it and see the result at once. Linked data had no such tool. Tabulator tried to be one: familiar outlines and tables, web addresses hidden, and queries and forms without code.

The question

Written in 2010 and extended into a history in 2019, this note is about building software rather than specifying it:

There was, in 2010, an unfulfilled need for a powerful, friendly program to interact with data on the web. Goals for a Human-Data Interface, 2010

56.1 What the document Web had that the data Web lacked

The document web spread by the simple method of people copying the source of each other's web pages, and getting the instant gratification of being able to see one's work in a web browser, and indeed to pass on the URL to friends and family. Goals for a Human-Data Interface, 2010

Against that he sets the early data projects:

However, most of the initial Semantic Web projects (around 2000) used back-end machines with no generic user interface. Researchers, to explain data to each other, tended to use circles-and-arrows diagrams of the graphs. These, though are hopeless -- very inefficient uses of space -- when it comes to displaying data to a normal user. Goals for a Human-Data Interface, 2010

Ordinary users expect an address book, a spreadsheet, a music library: lists, tables, forms, and faceted views, where a list is narrowed by picking values, as with a shop’s filters. The note concedes:

The different apps are islands, with no links between them, but they do give a user experience which users seem to use. Goals for a Human-Data Interface, 2010

The task was to keep that experience and add the links.

56.2 Two modes: outline and table

Late in 2007 Berners-Lee wrote a data browser that showed a thing’s properties as an outline. Where a property led to another thing, a triangle, as in a Mac file window, opened it. The graph looked like a tree, and users are used to trees.

His colleague Philippe le Hégaret complained that he wanted a table. So Berners-Lee added query by example: select lines in one interesting case, press a button, and get a table of every other place in the data with the same shape, the same pattern of links. Because it made tables from the graph, he called the program Tabulator.

A graph can loop back on itself: Joe knows Ann and Ann knows Joe. A tree cannot. Tabulator simply shows Joe again, closed (Figure 56.3).

56.3 The design principles

The note lists six design principles. In them, ‘ontology’ means the vocabulary: the published terms, with labels, that the data uses.

PrincipleIn plain terms
Never show URIsShow names, never web addresses.
Use the ontologiesTake on-screen words from the vocabulary’s labels, in the user’s language.
Use existing user interface languageBehave like the file browsers and tables people know.
Represent the graph as a treeAn expandable outline (Figure 56.3).
Read-writeAllow editing only where the user has the right.
A little semanticsWork out obvious facts, so a record with a transaction date is treated as a transaction without being labelled one.

The first is a prohibition:

While RDF buffs may revel in the URIs of nodes, users do not. User experience should not include naked URIs. Goals for a Human-Data Interface, 2010

Identifiers stay the foundation, but out of sight: the person sees a name taken from the vocabulary’s labels, and the software uses the identifier.

A little semantics: smushing

Inference here means the program working out facts that nobody wrote down. The note’s best case is “smushing”: deciding that two entries describe the same thing, as when many address books list the same people. In the Friend of a Friend (FOAF) project a profile could list a friend by email address alone. If the viewer already had that address in their own contacts, Tabulator treated the two entries as one person and showed the name the viewer knew. The note calls this low level of inference a sweet spot.

56.4 The audience, and the ambition

The target user explains the whole design:

A spreadsheet user is an interesting example: they spend a lot of effort in some cases getting the computer to do what they want, and work at quite a high level of abstraction. In fact they tend to pour their energy into a spreadsheet creating tables and relations about which the computer itself does not understand the semantics. Goals for a Human-Data Interface, 2010

The goal follows:

A major goal is that the software should allow users to be as powerful as possible without having to write their own code. Goals for a Human-Data Interface, 2010

56.5 Forms and panes: power without code

For common things, such as contacts, developers wrote special views called panes, offered as icons suited to the type of thing on screen.

Between panes and outline sat forms, which users made without code. A form was stored as data, the form editor was itself a form, and a shared registry offered each form to anyone viewing that type of thing. Forms are relatives of the shapes of Chapter 57. The note’s conclusion:

The spectrum, from hand-coded interfaces, through user-created forms to generic adaptive default interfaces was an important optimization. Goals for a Human-Data Interface, 2010

What happened since

  • The program became infrastructure. By 2019, the note records, Tabulator had been repurposed as the data browser for Solid, built on its store, rdflib.js.
  • The no-code ambition arrived elsewhere. No-code database tools such as Airtable (founded 2012) took up the ambition without linked data underneath.
