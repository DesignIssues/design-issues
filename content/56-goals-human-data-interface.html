The short version

Web pages spread because anyone could copy one, change it and see the result at once. Linked data had no such tool. Tabulator tried to be one: familiar outlines and tables, web addresses hidden, and queries and forms without code.

The question

Around 2000 most Semantic Web projects had data but no interface an ordinary person could use. Researchers drew circles and arrows for each other, diagrams the note calls “hopeless” for normal users. This 2010 note, extended into a history in 2019, tells of one attempt to fix that: Tabulator.

There was, in 2010, an unfulfilled need for a powerful, friendly program to interact with data on the web. Goals for a Human-Data Interface, 2010

56.1 What the document Web had that the data Web lacked

The document web spread by the simple method of people copying the source of each other's web pages, and getting the instant gratification of being able to see one's work in a web browser, and indeed to pass on the URL to friends and family. Goals for a Human-Data Interface, 2010

Ordinary users expect an address book, a spreadsheet, a music library: lists, tables, forms, and faceted views like a shop’s filters. The note concedes:

The different apps are islands, with no links between them, but they do give a user experience which users seem to use. Goals for a Human-Data Interface, 2010

The task was to keep that experience and add the links.

56.2 Two modes: outline and table

Late in 2007, by the note’s account, Berners-Lee wrote a data browser that showed a thing’s properties as an outline. Where a property led to another thing, a triangle, as in a Mac file window, opened it. The graph looked like a tree, which users know.

His colleague Philippe le Hégaret complained that he wanted a table. So Berners-Lee added query by example: select lines in one interesting case, press a button, and get a table of every other place in the data with the same shape. Because it made tables from the graph, he called the program Tabulator.

A table with dates could be shown as a timeline, and one with coordinates on a map (Yahoo Maps, in those days). Clicking a point took the user back into the outline, so query and graph traversal worked alternately.

A graph can loop back on itself: Joe knows Ann and Ann knows Joe. A tree cannot. Tabulator simply shows Joe again, closed (Figure 56.3).

56.3 Six rules, the first a prohibition

While RDF buffs may revel in the URIs of nodes, users do not. User experience should not include naked URIs. Goals for a Human-Data Interface, 2010

It heads six principles, in which ‘ontology’ means the vocabulary, the published, labelled terms the data uses.

A little semantics: smushing

Inference means working out facts nobody wrote down. The note’s best case is “smushing”: deciding that two entries describe the same thing. In the Friend of a Friend (FOAF) project a profile could list a friend by email address alone. If the viewer already had that address in their own contacts, Tabulator treated the two entries as one person and showed the name the viewer knew. As the store lasted all session, “one could go back to an earlier object and find it now augmented with all kinds of new data”, because anyone could publish facts about anything, and smushing joined them to what was already on screen. The note calls this low level of inference a sweet spot.

56.4 Built for spreadsheet users

The target was capable people untrained in RDF, such as the spreadsheet user, who works “at quite a high level of abstraction” yet builds tables whose meaning the computer does not understand: talent, the note argues, that a richer interface could use. Hence:

A major goal is that the software should allow users to be as powerful as possible without having to write their own code. Goals for a Human-Data Interface, 2010

Query by example fell short of it in one respect: there was “no way of saving the views and queries the user had discovered”.

56.5 Forms and panes: power without code

For common things such as contacts, developers wrote special views, panes, offered as icons suited to the type of thing on screen.

Between panes and outline sat forms, which users made without code. A form was stored as data, the form editor was itself a form, “the form form”, and a registry on the now defunct tabulator.org offered each form to anyone viewing that type of thing. Still, “The odd useful form written with the system survives, as does the form form.” Forms are relatives of the shapes of Chapter 57. The note’s conclusion:

The spectrum, from hand-coded interfaces, through user-created forms to generic adaptive default interfaces was an important optimization. Goals for a Human-Data Interface, 2010

What happened since

  • The browser fought back. As a web page Tabulator was “a browser within a browser”. The Same Origin Policy, mixed-content rules and later CORS made that mode “a constant battle”, so the Firefox extension was the stronger version.
  • The program became infrastructure. By 2019 Tabulator had become Solid’s data browser. Open a data object in an ordinary browser and the server first sends a small page that loads the data browser, which fetches the same address again as data.

The note ends on a spectrum it “did not explore”: private, shared and public data; its servers lacked user-accessible access control. Solid has it now, and such systems “become more exciting when the user can control who has access” (Chapters 54 and 55).
