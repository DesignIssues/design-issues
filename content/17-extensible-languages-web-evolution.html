The short version

Real documents mix vocabularies: an invoice uses business terms for the price and a supplier’s terms for the part. Each vocabulary must be well defined, declared in the block that uses it, and marked on every name by a visible prefix. A reader must be able to tell what it may safely skip without looking anything up.

The question

Chapter 16 ended with a demand: free extension, but with an extension mechanism that is itself well defined. This note, written with Dan Connolly in February 1998 and also issued as a W3C Note, sets that demand out as a list of requirements. The authors are careful about their standing:

Whilst technically the personal opinion of the authors, it their best attempt as technical coordinators at outlining common architectural principles for W3C development. Extensible languages, 1998

17.1 What partial understanding looks like in life

The old rule

The note starts from the rule that had governed Web extension since 1989, inherited from Internet email:

If you find a language element you don't understand, ignore it. Extensible languages, 1998

The Web grew very fast under it, but until a feature was agreed nobody knew what it meant or what ignoring it would do. Distributed object systems had the opposite profile.

The invoice

The note’s example is an invoice for an aeroplane part.

We are constantly handling information with partial understanding. Imagine if an old version of a word processor could read a file written by a new version with partial understanding, rather than panicing that it had met a being from the future. Extensible languages, 1998

The note defines its own terms:

TermThe note’s meaningIn the invoice
ElementA stretch of a document identified by a local nameThe cost entry
VocabularyA set of such names whose meaning is defined somewhere else, by a resource on the Webitem, cost, quantity, signature, due date
SchemaA specific document that defines a vocabularyThe published definition of the business terms

A namespace is a vocabulary named by a URI; tying a prefix to that URI is a binding.

17.2 A message is an expression, not a procedure call

A procedure call is one program asking another to run a single named operation with fixed inputs, like a form with fixed fields. It is tempting to treat a message as such a call. The authors reject the analogy:

don't think of an HTTP message or an HTML document as an RPC call, but rather as the transmission of a expression in some language. Extensible languages, 1998

Nesting whole documents is not enough: names from two vocabularies must sit together in one expression. That is the first requirement.

17.3 The first four requirements

The note sets out seven requirements; the three on schemas come in section 17.5. A vocabulary is in scope where its names may be used; an identifier is a name.

RequirementWhat breaks without itIn the invoice
More than one vocabulary may be in scope at one point in a documentExtensions can only be nested, never mixed; no bold inside a formulaA Swiss-franc amount sits inside a price written in business terms
A vocabulary may be introduced with a purely local changeGenerated fragments cannot declare their own termsThe supplier’s program declares its part terms inside the item block
The syntax must tie an identifier to its schema without inspecting any schemaOne vocabulary’s change silently redefines another’s namesf:chf is read as currency from the f binding alone
A namespace may be defined by present or future languages for writing schemasThe definition mechanism is frozen at the level of the dayThe currency terms could be defined in a schema language invented later

The third is argued most sharply. In some programming languages, finding which module (separately written unit) a name comes from means reading the modules and applying priority rules. The note grants this may suit a language such as Java, and contrasts Modula-3, which settles names unambiguously. For documents it is a serious flaw:

when one module changes (without the knowledge of the designers of the other module), it can unwittingly redefine a local identifier used by the second module, completely changing the meaning of a previously written document. Extensible languages, 1998

This is why XML namespace prefixes bind directly and visibly, rather than being resolved by lookup.

17.4 Why local scope

Markup wraps each piece of content in named tags, <name>…</name>. A prefix such as f: says which vocabulary the name comes from. The note’s example binds f to a currency schema for one block, using NS:using as a made-up stand-in for a real syntax: 

<a:details>
  <NS:using href="http://blah/currency" as="f">
    <a:price>
      <f:chf>4.00</f:chf>
    </a:price>
  </NS:using>
</a:details>

XML Namespaces later put the binding in an attribute, holding for that element and everything inside it: 

<a:price xmlns:f="http://blah/currency">
  <f:chf>4.00</f:chf>
</a:price>

Why not declare every binding once, at the top? The note gives four reasons.

Generated documents

Many pages are assembled by programs that write one part without seeing the rest. Moving bindings to the top afterwards means buffering the whole document, which rules out pipelined processing, where each part is passed on as soon as it is produced.

Long documents

Imagine a list of suppliers, each with its own catalogue schema. With local bindings the working set, the memory held while processing, stays finite; with global bindings it grows with every page.

Joining documents

The authors suggest it would be a worthy design goal that joining any two XML documents gives an XML document. Without local scope, one must be rewritten end to end to rename clashing prefixes.

Fewer mistakes

When a name is bound close to where it is used, people editing by hand make far fewer mistakes.

17.5 What may be extended, and what may not

The invoice supplies the remaining three requirements. Its designer wants the item description open to any supplier’s part vocabulary, but the list of people allowed to sign closed: only Tom or Joe may sign.

So a schema language needs a way to say that a content model (the rule for what may appear inside an element) may be extended, and a way for a new schema to declare that it is such an extension. The seventh requirement makes partial understanding cheap:

It should be possible to create an original document schema such that one can determine, without access to the extension schema, which uses of extensions to that document can be ignored. Extensible languages, 1998

An invoice must be processable as an invoice without fetching anybody’s part catalogue.

What happened since

  • Namespaces shipped with local scope. XML Namespaces became a W3C Recommendation in January 1999 with prefixes bound directly and scoped to the element that declares them: requirements two and three.
  • Schemas gained ways to mark content as skippable. XML Schema 1.0 (W3C Recommendation, May 2001) lets a schema mark where foreign content may appear and, with processContents="skip" or "lax", be passed over without its schema. SOAP 1.1 (2000) added the converse, a mustUnderstand flag, which is Chapter 18’s concern.
  • The concatenation goal was not met. Joining two XML documents still yields a document with two roots, which is not well formed (XML’s basic syntax rules require a single root element).
