The short version

Before anyone builds something that other people will build on in turn, the same handful of choices arrive. Simple, or capable? Strict about what is accepted, or forgiving? Control kept in one place, or given away?

In 1998 Tim Berners-Lee wrote down his answers: six rules, two from software engineering, two from the Internet, and two he had often found useful for the Web. They are simplicity and modularity; tolerance and decentralisation; and the test of independent invention and the principle of least power. The rest of this book keeps applying them.

The question

When Berners-Lee designed HTML he deliberately did not make it a programming language. He wanted other people’s programs to present it differently, extract tables of contents from it, index it. That refusal is one reason a search engine can read a web page. In 1998 he wrote down the rule behind it, along with five others he kept appealing to in arguments, scattered across many of his writings with no single place to point to. The note’s first lines admit as much:

Again and again we fall back on the folklore of the principles of good design. Sometimes I need a URI for them so this is started as collection of them. Principles of Design, 1998

That is a working note, not a manifesto, and the author says so: he calls the content “largely motherhood and apple pie” while insisting it still needs a home.

1.1 Three pairs, three traditions

The six principles are not a flat list. Berners-Lee groups them by where they come from. Simplicity and modularity, he says, are “the stuff of software engineering”. Decentralisation and tolerance are “the life and breath of Internet”, and he credits Brian Carpenter’s RFC 1958, Architectural Principles of the Internet, of June 1996. The remaining pair, the test of independent invention and the principle of least power, are ideas he has found “commonly useful for the Web”.

The software-engineering pair is about the system one is building. The Internet pair is about the network one is building on. The Web pair is about the systems other people will build later, which do not exist yet and cannot be consulted. The pairs can pull against each other: tolerating malformed input (an Internet virtue) means writing rules for it, which costs simplicity (a software one).

PrincipleTraditionWhat goes wrong without it
SimplicitySoftware engineeringEvery later specification must handle an extra case
ModularitySoftware engineeringA change in one part forces changes in all
ToleranceInternetSystems break on slightly wrong input
DecentralisationInternetOne point caps growth, and its failure stops everything
Test of independent inventionWebTwo rival systems cannot work together
Least powerWebData only its own program can read

1.2 Simplicity, and what it is not

The section opens with the slogan “Keep it simple, stupid!” and an admission: simplicity “is easily to quote but often ignored in strange ways”, perhaps because it is in “the eye of the beholder”. The definition that follows is meant to take it out of the beholder’s eye: “A language which uses fewer basic elements to achieve the same power is simpler.” Berners-Lee then separates this from familiarity. A two-line solution that uses recursion (a function that calls itself) is simpler than a ten-line one that avoids it with an explicit loop, even where some readers find the longer version easier to follow.

The worked example is XML. An XML document is built from two kinds of thing: elements, the named and nested pieces such as <p>, and attributes, the name-and-value settings attached to them, such as the class="x" in <p class="x">. Processing instructions are a third kind, the constructs that begin with <?, such as <?xml-stylesheet …?>.

His objection is not that processing instructions are large but that they are contagious. They complicate what was a clean design of elements and attributes, and so every specification that refers to XML processing must afterwards say what it does about them as well. Simplicity here is measured in other people’s specifications, not in one’s own.

1.3 Modularity, and being a module

Group features so that the bindings within a group (the ways one feature depends on another) are tight, and the bindings between groups are loose. The groups become units of independent change: one person can alter and test one part while others alter other parts. This depends on a simple, abstract interface; a design in which each module must know the insides of the others is not modular but merely partitioned. Then comes the harder demand:

It is also necessary to realize that your own system, no matter how big and wonderful it seems now, should always be designed to be a part of another larger system. This is often much more difficult than modularity. Principles of Design, 1998

1.4 Tolerance, and its cost

The rule is stated in quotation marks in the note: “Be liberal in what you require but conservative in what you do”. It is usually credited to Jon Postel, who edited many of the early Internet protocol specifications and put a version of it into the specification of TCP in 1981. The note does not name him; it says only that the rule applies “pretty well in life” as well as across the Internet.

The note gives its own concrete case: “Write HTML 4.0-strict. Accept HTML-4.0-Transitional (a superset of strict).” HTML 4.0 came in two main versions. Strict left out the older presentational features; Transitional kept them, so every Strict document is also a Transitional one. A careful program sends the narrower kind and accepts the wider.

Berners-Lee records the objection as well as the rule. When browsers are lax about what they expect, the system works better, but the laxness teaches page authors to be lax too. The Web later answered this objection in a way the note did not foresee (see What happened since).

He then draws the limit. Tolerance in a program is never a licence for vagueness in a specification. The specification must still draw a precise line between conformance (meeting every requirement it sets) and non-conformance, whatever programs then choose to accept across that line. Nor is tolerance an excuse for a product that breaks a standard.

1.5 Decentralisation, including of concepts

If every operation passes through one common point, that point caps how far the system can grow, and when it fails, everything fails. That is the network argument. Berners-Lee applies it to vocabulary as well as to infrastructure.

His example is a knowledge representation system, a system that records facts in a form a program can reason with. Suppose it requires anyone who uses the concept of an automobile to use the one term http://www.kr.org/stds/industry/automobile. It then works only for those whose idea of an automobile matches that one formulation. The Semantic Web, he writes, must avoid such conceptual bottlenecks just as the Internet avoids network bottlenecks.

This is the seed of the argument that runs through Volumes IV to VI: that the Semantic Web must let anyone mint a term, and must solve agreement by mapping between vocabularies rather than by mandating one.

1.6 If someone else had invented it first

The test is a single question: “If someone else had already invented your system, would theirs work with yours?” Put another way, does this system have to be the only one of its kind? The note says the test is described in more detail in another of the Design Issues notes, Evolution, and adds three points of its own.

First, the test is “modularity inside-out”: designing a system not to be modular in itself, but to be one part of a larger system that has not yet been specified (the third panel of Figure 1.2). Second, such a system should try to do one thing well, and leave other things to other modules. Third, it must avoid conceptual and other centralization, because “no two modules can claim the need to be the unique center of a larger system”. The note’s shorthand for the whole test is “the TOII”.

The Web itself was designed to pass. A rival, larger address space could take in every URI as one of its parts, and both would keep working; Chapter 2 shows this with the international telephone system, and Chapter 16 tells Berners-Lee’s own story of the Web meeting an imagined rival, the Multi Media Mesh.

1.7 Least power: why HTML is not a program

The note’s comparison is weather data. Published as a table of values with a declarative description, it can be averaged, plotted, combined with other sources, and queried in ways its publisher never considered. Published through a Java applet, a small program that the browser downloads and runs inside the page, it may look better and can be analysed by nobody.

The search engine finding the page will have no idea of what the data is or what it is about. Principles of Design, 1998

The only way to discover what an applet means is to run it in front of a person. The difference is between two kinds of language. A declarative language states what is the case and leaves the reader to decide what to do with it; HTML says “this is a heading”. A procedural language is a list of steps for a computer to carry out, as in Java or C.

Between the two Berners-Lee sets out a scale (Figure 1.5), from plain descriptions such as HTML to programming languages such as Java. On the rungs between, languages grow towards being Turing complete, able in principle to express any computation: “Postscript is, but PDF isn’t, I am told”.

The powerful end of the scale is attractive: an open-ended hook into which anything can be placed. The profession spent the 1960s to the 1980s trying to move up it. His claim is that for data on the Web the incentive runs the other way:

The reason for this is that the less powerful the language, the more you can do with the data stored in that language. If you write it in a simple declarative from, anyone can write a program to analyze it in many ways. Principles of Design, 1998

He then gives the design decision this principle was extracted from:

I chose HTML not to be a programming language because I wanted different programs to do different things with it: present it differently, extract tables of contents, index it, and so on. Principles of Design, 1998

A later follow-up credits Meredith Patterson’s talk The Science of Insecurity with the point that the principle of least power is also important for the security of interfaces that may be exposed to attack.

Where these principles are used

Decentralisation and independent invention are applied to URI space in Chapter 2. Modularity in the inside-out sense becomes the independence axioms of Chapter 4. Simplicity and the cost of extra constructs return in Volume III, in particular in Chapter 16 on evolvability and Chapter 19 on modularity. Least power is the argument beneath the whole of Volumes IV and V, and is stated again at the opening of Chapter 5.

What happened since

  • Least power was promoted. It left this personal note and became a W3C Technical Architecture Group finding, The Rule of Least Power, edited by Berners-Lee and Noah Mendelsohn, published in February 2006.
  • The applet stopped running. Chrome 45 (September 2015) and Firefox 52 (March 2017) dropped the plug-in interface applets ran on, and JDK 9 (2017) deprecated the applet API. A weather applet of 1998 can no longer be run even in front of a person; an HTML table of the same year still displays.
  • The security reading became a field. Patterson and Len Sassaman’s language-theoretic security (LangSec) work, presented from 2011, argued that parser expressiveness is itself the attack surface. It holds that inputs an interface accepts should be in a language simple enough to be decidable: simple enough that a program can always tell whether a given input is valid.
  • Tolerance was reconsidered. The Internet Architecture Board published RFC 9413, Maintaining Robust Protocols, in June 2023, arguing that liberal acceptance degrades interoperability over time because divergent implementations are never corrected. The 1998 objection recorded in this note is the same objection, sustained.
  • The tolerance argument was settled differently on the Web. HTML5, whose first W3C Recommendation came in October 2014, specified error handling exactly, so that lax input produces one defined result rather than many. That is neither strictness nor tolerance but a third answer the 1998 note does not anticipate.

Questions

1.2 Tolerance and simplicity can conflict: accepting malformed input requires rules for handling it, and those rules are additional basic elements. Give an example from HTML where this conflict was resolved in favour of tolerance, and say what it cost.

1.3 Apply the test of independent invention to a photo-sharing site that only lets you link to other users of the same site. Would a rival site’s links work with it?

1.4 The principle of least power claims that weaker languages make data more reusable. State the strongest counter-argument. Which of the other five principles would someone who wants a powerful language point to?
