The short version

Most of the world’s structured data sits in tables. Read a table the right way and it is already a graph: each row is a thing, each column is a property, each cell is a value.

Two things do not carry over. A table quietly claims to be complete, and nothing in either model writes that claim down. And the keys that name rows can change, which is harmless inside one database and breaks links on the Web.

The question

Employee records, car registrations: a vast amount of the data that already exists sits in the tables of relational databases. A Semantic Web that could not reach it would leave much of what is recorded out. Berners-Lee says reaching it was the point all along:

Indeed, one of the main driving forces for the Semantic web, has always been the expression, on the Web, of the vast amount of relational database information in a way that can be processsed by machines. Relational Databases on the Semantic Web, 1998

He wrote it in September 1998, as a parenthesis to Chapters 5 and 30.

33.1 The mapping

A relational database stores data in tables. Each row is one record, say one employee, and each column holds one kind of fact, such as a shoe size. The primary key is the column whose value picks out exactly one row, such as an employee number. RDF, the Web’s data model (Chapter 32), stores facts as triples (a thing, a property, a value) that together form a graph. The correspondence takes three lines (Figure 33.1), and the note says why it is so direct:

The record is nothing but the content of its fields, just as an RDF node is nothing but the connections: the property values. Relational Databases on the Semantic Web, 1998

33.2 What changes: anyone can add a relationship

Entity-relationship modelling is the standard way of designing a database on paper: list the kinds of thing, and the relationships each kind can have. Is RDF such a model? Yes and no, says Berners-Lee: a good basis for one, but more general. Apart from one “simple but significant change”, many of its concepts carry straight across:

The RDF model is the same, except that relationships are first class objects: they are identified by a URI, and so anyone can make one. Furthurmore, the set of slots of an object is not defined when the class of an object is defined. Relational Databases on the Semantic Web, 1998

Object-oriented systems, the usual way of building such models in software, assume the opposite: an object’s data lives inside the object, in slots its class set aside. RDF lets a relationship be stored apart from everything else about the two things it joins, because, in the note’s words, “The Web works though anyone being (technically) allowed to say anything about anything.”

33.3 What a database does that a graph does not

A row says that a red car has Massachusetts plate 123XYZ. The table may also carry, in the note’s words, “the unwritten semantics that if any car has a Massachusetts plate then it must be in the table.” Neither model has a simple way of writing that rule down.

Typing

E. F. Codd, who invented the relational model, included datatypes with inheritance (types that can be refined into sub-types), and meant them to be implemented more fully than they were. In practice a count of rooms and a shoe size are both just integers, so nothing stops a query listing, for every employee, the houses with as many rooms as that employee’s shoe size. Practical systems trust the application to ask only sensible questions. On the Web that trust no longer holds:

Once a database is expreted onto the Web, it becomes possible to do all kinds of strange combinations, so a stronger typing becomes very useful: it becomes a set of inference rules. Relational Databases on the Semantic Web, 1998

If shoe size and room count are declared different kinds of number, a program can conclude that a query joining them is nonsense, and refuse it.

Keys that change

The naming problem of Chapter 3 returns: a primary key can change without the row changing identity: a person may change their name. Other tables refer to the row by its key, and SQL can cascade the change, rewriting every such reference so none points at nothing (referential integrity). That works inside one database; it cannot reach links made from elsewhere on the Web.

He offers three answers: give each row a hidden row ID (many systems keep one, though SQL does not expose it in a standard way); forbid the key to change; or put up with broken links.

33.4 A million copies, a million schemas

A schema is the declared shape of some data: its tables and columns, or the elements a document may contain. He expects relatively few document schemas, and expects many sites to export documents defined by the same one. Database schemas are created independently per database:

Even if a million companies clone the same form of employee database, there will be a million schemas, one for each database. Relational Databases on the Semantic Web, 1998

So the new technology may have a modest role: expressing the equivalence of terms between those million schemas, the conversion layer of Chapter 30.

33.5 An address for every cell

The rest of the note is a strawman, a first draft put up to be criticised: a layout giving a URI to each part of a database, down to a single cell and an arbitrary query. A 2002 version, based on code Dan Connolly implemented, looks like Figure 33.5.

A table’s address can also serve as a namespace, so a column such as email gets a Web-wide name, and a row joined from two tables carries names from both.

Berners-Lee is unsure whether a query on a primary key, or a single cell, is really an identifier. His ruling applies the rule of Chapter 2 that fetching a URI with GET must not change anything. A query that only reads may sit in a URI after a question mark. A query that changes the table, such as UPDATE or DELETE, should be sent with HTTP POST, never named by a URI. Search engines and browsers follow GET links freely, assuming that changes nothing; a link that deleted a row would be triggered by the first robot that found it, as happened in 2005 with the prefetching tool described in Chapter 2.

What happened since

  • The mapping was standardised twice. Direct Mapping of Relational Data to RDF and R2RML, a customisable mapping language, both became W3C Recommendations in September 2012. The three-line correspondence of section 33.1 is the direct mapping almost verbatim.
  • The primary key problem was settled by convention. Practice moved to surrogate keys, meaningless identifiers that never change, which is closest to the first of the three options offered here.
  • The million schemas are still there. Mapping between independently designed schemas remains largely manual, and is a large part of the cost of data integration projects.
