The short version

When a browser asks a web server for an address, the server replies with a number before it sends anything else. A reply of 200 means “here it is”. The rule agreed in 2005 says that a 200 shows the address names a document, and that any other reply does not show that.

The question

Three years after the argument of Chapter 7, the Technical Architecture Group (the TAG) decided the matter. The TAG called it “httpRange-14”: its name for the issue, number 14 on its list of open questions. This note is Berners-Lee’s account of the decision, written in June 2005. It is short because the answer turned out to be a rule about response codes rather than a rule about meaning.

8.1 What was decided

Every reply from a web server begins with a three-digit response code that says how the request went. Three of them matter for this chapter:

CodePlain meaning
200 OK“Here is the page.”
303 See Other“Look over there instead”, with a second address to try.
404 Not Found“Nothing here.”

The note states the resolution twice, in nearly identical words:

The W3C Technical Architecture group eventually decided to resolve the architectural problem that if an HTTP response code of 200 (a successful retrieval) was given, that indicated that the URI indeed was for an information resource, but with no such response, or with a different code, no such assumption could be made. This compromise resolved the issue, leaving a consistent architecture. What HTTP URIs Identify, 2005

An “information resource” is the formal term for what most people call a web page or a document: something whose whole content can be sent down the wire. The rule is easy to read as stronger than it is; Figure 8.1 shows its one-way shape. The detail about 303 is not in this note, which never mentions that code, but in the TAG’s own resolution: after a 303 the URI “could be any resource”.

8.2 What it cost and what it bought

Berners-Lee describes the effect as an extension of range rather than a change of principle:

The TAG resolution effectively extends the range of things one can use HTTP URIs. However, it does not allow one to simply serve a web page at a URI which is used for something else. What HTTP URIs Identify, 2005

The second sentence is the constraint that makes the first safe. A publisher who wants a URI to name a person may not also serve that person’s home page from it with a 200, because a 200 would mean the URI names the page.

The note adds that it is still “useful to serve information to those that look up a URI”, even when the URI is not meant for a document. It does not say how. The TAG’s resolution does: reply with a 303 pointing to a separate address that serves a document about the thing (Figure 8.2).

Chapter 7 argued that this question should be fixed in the specification; the Group fixed it in the protocol exchange. Berners-Lee accepts the result without pretending it is what he asked for, and his 2002 page acquired a header saying the compromise works quite well.

8.3 How the problem arose in practice

The note also records how the problem arose in practice. Berners-Lee names the vocabularies:

The Dublin Core project, one of the first RDF vocabularies, and later Friend of a Friend, and various others simply used HTTP URIs to identify RDF Properties. The result was that one could no longer be sure that an HTTP URI was intended to identify the web page one got when one used the URI in a browser. What HTTP URIs Identify, 2005

Dublin Core is a set of names for describing documents (title, creator, date); Friend of a Friend is a set for describing people. In each, a “property” is a word like title given a web address. Figure 8.3 shows the danger the note spells out.

The architecture did not fail. It was outrun by deployed practice. Chapter 9 gives Berners-Lee’s fuller account of that pressure, and is franker about who conceded what.

What happened since

  • The redirect pattern was codified. The TAG’s 2007 draft finding Dereferencing HTTP URIs and the W3C Interest Group note Cool URIs for the Semantic Web, of December 2008, turned the resolution into publishing guidance, setting out both the 303 pattern and the hash pattern (Chapter 11) as acceptable.
  • The rule was questioned again. The extra round trip made 303 unpopular. In 2012 the TAG issued a call for change proposals on httpRange-14, which explored serving descriptions directly, but did not overturn the 2005 resolution.
  • Neither pattern won. Vocabularies published after 2005 use both the 303 pattern and the hash pattern. A consumer of arbitrary Linked Data must still handle each.
  • The underlying ambiguity outlived the fix. Structured data embedded in pages, which became the dominant way of publishing descriptions of things after Schema.org launched in June 2011, sidesteps the question entirely by describing things inside a document rather than giving them dereferenceable URIs of their own.
