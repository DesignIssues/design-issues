The short version

Does a web address name a page, or the thing the page is about? In 2005 the answer became a rule about server replies, which begin with a number: 200 means here is the page. Under the rule, a 200 shows the address names a document; any other reply leaves the question open.

The question

The address of the Dublin Core word title also fetched a web page. A statement that it has creator Dublin Core team could then be read two ways: who made the web page, or who defined the property? Nothing in the address said which. Berners-Lee records that the issue caused “a lot of discussion in technical circles, and much heated debate” until, in June 2005, three years after the argument of Chapter 7, the W3C’s Technical Architecture Group (the TAG) settled it as “httpRange-14”, issue 14 on its list. This short note is Berners-Lee’s account. The answer was a rule not about meaning but about the number a server sends back.

8.1 The ruling: let the server’s reply decide

Every reply from a web server begins with a three-digit response code that says how the request went. Three of them matter for this chapter:

CodePlain meaning
200 OKhere is the page
303 See Otherlook at this other address instead, with the second address given
404 Not Foundnothing at this address

The resolution:

The W3C Technical Architecture group eventually decided to resolve the architectural problem that if an HTTP response code of 200 (a successful retrieval) was given, that indicated that the URI indeed was for an information resource, but with no such response, or with a different code, no such assumption could be made. This compromise resolved the issue, leaving a consistent architecture. What HTTP URIs Identify, 2005

An “information resource” is the formal term for what most people call a web page or a document: something whose whole content can be sent down the wire. If a URI has fetched a web page, such as the New York Times home page or, as Berners-Lee points out, the very note he was writing, it may be used to name that page. So a 200 tells a client something; a 404 tells it nothing. The rule runs one way (Figure 8.1).

8.2 The price of naming a person: one extra round trip

Berners-Lee describes the effect as an extension of range rather than a change of principle:

The TAG resolution effectively extends the range of things one can use HTTP URIs. However, it does not allow one to simply serve a web page at a URI which is used for something else. What HTTP URIs Identify, 2005

The second sentence makes the first safe. A URI that names a person may not also serve that person’s home page with a 200, because a 200 would mean the URI names the page.

The note adds that it is still “useful to serve information to those that look up a URI”, even when the URI is not meant for a document. It does not say how, and never mentions the 303 code. The TAG’s own resolution does: reply with a 303, after which the URI may name anything at all, pointing to a separate address that serves a document about the thing (Figure 8.2).

8.3 Where the ambiguity came from

Some early vocabularies of RDF, the Semantic Web’s format for machine-readable statements, gave their words HTTP addresses. Dublin Core (names for describing documents: title, creator, date) and Friend of a Friend (names for describing people) both did, so the word title had a web address. Berners-Lee names them:

The Dublin Core project, one of the first RDF vocabularies, and later Friend of a Friend, and various others simply used HTTP URIs to identify RDF Properties. The result was that one could no longer be sure that an HTTP URI was intended to identify the web page one got when one used the URI in a browser. What HTTP URIs Identify, 2005

Figure 8.3 shows the danger the note spells out.

Deployed practice had outrun the architecture; Chapter 9 gives Berners-Lee’s fuller account of that pressure. In Chapter 7 he wanted the rule written into the definition of HTTP itself. The TAG instead let the server’s reply code carry the answer. He accepts the result without pretending otherwise: a note added in 2006 to his 2002 page calls it a compromise “which I think works quite well”.

What happened since

  • The redirect pattern was codified. The TAG’s 2007 draft finding Dereferencing HTTP URIs and the W3C Interest Group note Cool URIs for the Semantic Web, of December 2008, turned the resolution into publishing guidance, setting out both the 303 pattern and the hash pattern (Chapter 11) as acceptable.
  • The rule was questioned again. The extra round trip made 303 unpopular. In 2012 the TAG issued a call for change proposals on httpRange-14, which explored serving descriptions directly, but did not overturn the 2005 resolution.
  • The underlying ambiguity outlived the fix. Structured data embedded in pages, which became a widespread way of publishing descriptions of things after Schema.org launched in June 2011, mostly avoids the question for the things described, by describing things inside a document rather than giving them dereferenceable URIs of their own.
