The short version

A page on the Web is written for a person to read. A machine can fetch it and display it, but it cannot answer a question about what the page says, because nothing in the page tells it which words are prices and which are dates.

This chapter is the first full plan for fixing that: a stack of layers, each one useful on its own before the layer above it exists. Its central bet is a modest one. The system is never asked to work out an answer from scratch; it only checks a proof that someone hands it.

The question

It is the companion to Chapter 5, written the same month of September 1998 and spun off from it because the subject needed more room than a survey could give. It is candid about its standing:

A road map for the future, an architectural plan untested by anything except thought experiments. Semantic Web Road map, 1998

30.1 The problem being solved

The diagnosis has not aged:

One of the major obstacles to this has been the fact that most information on the Web is designed for human consumption, and even if it was derived from a database with well defined meanings (in at least some terms) for its columns, that the structure of the data is not evident to a robot browsing the web. Semantic Web Road map, 1998

Berners-Lee sets aside the artificial intelligence problem of training machines to behave like people. The Semantic Web instead develops languages for writing information in a form machines can process. Chapter 31 makes the negative case.

30.2 The layers

Berners-Lee justifies the base by minimalism. A universal web of assertions must rest on a model general enough that any application maps onto it, and generality forces simplicity. An assertion is a single statement, such as this page’s author is Alice. Quotation is a statement about a statement: Bob says that this page’s author is Alice. The base contains these two things only. Quotation is there early for two reasons: it will be needed later anyway, and most early applications are metadata, data about data, where statements about statements are basic even before logic arrives.

The base layer has no negation (saying something is not so) and no implication (if one thing holds, then another does). So, given a set of facts, it is always easy to say whether a question can be answered. Nothing can be intractable, meaning it would take impossibly long to work out.

Schema

A schema declares a new property and constrains how it is used, typically what kinds of thing it applies to. That allows simple checks: that a driver’s licence has the name of a person, and not a model of car, as its name. The schema language is kept deliberately weak.

Conversion

Two applications seldom use the same vocabulary, the set of terms their data is written in. The conversion layer states rules for translating one into another. It is allowed implication but still no negation. The note’s example is three databases built independently and put on the Web, joined through a zip, a US postcode (Figure 30.2).

Logic

The logical layer adds “not” and “and”, then “for all x”. With these a document can carry general rules. Where a Library of Congress schema says “author” and a British Library one says “creator”, a rule can carry one over: if Dickens is the author of Bleak House in one catalogue, he is its creator in the other. A small piece of RDF, the format the note proposes for writing such statements, states it once for every case: for any person x and resource y, if x is the author of y then x is the creator of y.

Signature

For reasoning to take trust into account, a public key, the published half of a signing key, becomes a first-class object, a thing the logic can talk about, and the model records which key signed which assertion. Proof checking then verifies signatures as well as logic. Signature work can proceed in parallel with the other layers.

30.3 Why bother at the bottom

If an application’s data is simple, why express it in this model at all? The answer argues for the whole enterprise:

The answer is that we expect this data, while limited and simple within an application, to be combined, later, with data from other applications into a Web. Semantic Web Road map, 1998

The example is access control, where a decision may combine privacy preferences, group membership and data typing, each trivial alone and none sharing a format with the others. Chapter 37 works it through in detail.

30.4 Proof, and the asymmetry that makes it work

The roadmap’s most important design decision is a restriction. The system is required to validate proofs, not to find them. A proof here is a list of signed statements plus the rules that join them, which anyone can re-check step by step.

Someone granted access to a site is given a document explaining to the server why they should have it. The proof is “a chain [well, DAG] of assertions and reasoning rules” (a DAG is a chain that may branch and rejoin), with pointers to the supporting material. The note expects the same of privacy and most electronic commerce:

The HTTP "GET" will contain a proof that the client has a right to the response. the response will be a proof that the response is in deed what was asked for. Semantic Web Road map, 1998

Finding a proof for an arbitrary question is intractable; checking one that arrives with the request is not.

30.5 Engines of the future

Indexes of terms, Berners-Lee expects, will let the Web be searched “as though it were one giant database, rather than one giant book”. He then proposes joining two kinds of engine that had each failed alone (Figure 30.4).

The number of steps matters because each step out on the Web may follow every link from every result of the step before: two steps over a hundred links each is ten thousand fetches. He states the limit plainly: no machine will guarantee to answer arbitrary questions.

What happened since

  • The lower layers shipped. RDF, for assertions, became a W3C Recommendation (finished-standard status) in February 1999; RDF Schema, a vocabulary-definition language, in February 2004; OWL, a richer ontology language, in the same month, whose equivalentProperty states exactly the conversion of Figure 30.2; and SPARQL, a query language for RDF, in January 2008.
  • The proof layer did not. No interoperable proof exchange format was standardised. The asymmetry of section 30.4, which the roadmap treats as its central bet, was never put to the test.
  • The search-plus-logic engine arrived in another shape. Large knowledge graphs behind search, beginning with Google’s in May 2012, combine indexing with structured data, as the note proposed, without the proof machinery.
