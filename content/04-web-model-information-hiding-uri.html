The short version

A web address often has a hash in it, with something after the hash naming a part of the page. Nobody has to think about this, which is the point: the piece of software that fetches the page and the piece that finds the right part of it are kept deliberately ignorant of each other.

This chapter is about where those dividing lines run (the note recorded them in 1998), and why drawing them there is the reason the Web’s separate parts could go on being revised for decades without any one revision breaking the others.

The question

Why can HTTP, HTML and new document formats each be revised without breaking the others? The answer is that the module boundaries were drawn in the right places early on, and this 1998 note says where. Its subject is information hiding.

Berners-Lee numbered the note zero in his axioms sequence, though he wrote it in January 1998, more than a year after the Axioms note of Chapter 2 (December 1996). Chapter 2 describes what URIs are; this note describes the machine that consumes them.

4.1 Three modules

Information hiding means each part of a system knows only what it needs, so the others can change without it noticing. The model applies that idea to a browser, or to anything else that follows a link, by dividing it into three parts that know different things.

Access is handed the URI with the fragment removed. It returns two things: a data stream, which is simply the bytes of the document as they arrive, and a media type such as text/html, which says what kind of document those bytes are. Both are passed to a factory, meaning code that builds an object of the right kind, and the object it builds is then given the fragment identifier. Figure 4.2 follows one link through these steps.

Berners-Lee states the arrangement as two axioms:

The access machinery does not need to look at the fragment identifier.

The presentation object does not need to know the URI of the resource.

And derives from them the claim that matters for everyone who writes specifications:

The specifications for access protocols are independent of the specifications for fragment identifiers. The Web Model, 1998

4.2 Why the fragment stays on the client

The immediate payoff is a link that stays on the same page, such as <a href="#notes">. A link within a document specifies only a fragment, and the object can follow it without consulting the access code at all, because the hash syntax is universal across every scheme.

The consequence is that an author can write a document full of internal links without knowing what URI the document will eventually be served under, and can move it without editing it.

Signed documents

Berners-Lee credits Jim Gettys with the observation that makes this more than a convenience. As digitally signed documents become common, editing a document to fix its own internal links would break the signature on it. A document that can be self-consistent independently of its namespace is one that can be signed once.

Room to evolve

The second payoff is evolutionary, and he is emphatic about it. Because no access specification refers to fragment semantics, anyone defining a new media type is free to invent whatever notion of a view or a part suits it, knowing that nothing else will break. Equally, anyone designing a new way to name and fetch documents need not care what kinds of document will travel over it.

This has already (1998) proved incredibly enabling to the community, as HTTP has advanced in parallel with many other ways of accessing data, and the number of exciting media types has grown very rapidly, and will be the key to many new revolutions built on top of the basic Web idea. The Web Model, 1998

Webizing

New applications such as the Semantic Web can be built on this model: not as a new Web, but by introducing new types of document. Webizing a language, he says, means taking names that were global only within one document and making them truly global by adding the document’s URI and a hash. A name #alice, used inside http://example.org/people, becomes http://example.org/people#alice, which means the same thing anywhere. This is the mechanism of Chapter 6 and of Volume IV.

4.3 Why relative resolution is universal

Suppose Ann writes a book as a set of files on her own disk. Chapter one is at file:///home/ann/book/ch1.html, and it links to chapter two by writing only href="ch2.html". That short form is a relative reference: it gives only the part of the address that differs. The address of the document it appears in, here chapter one’s, is the base URI. To follow the link, the application combines the two, replacing the last part of the base with ch2.html.

A design decision is recorded here that could have gone the other way. The application could have passed both the relative reference and the base to the access module, letting each scheme define its own resolution algorithm. Instead, one algorithm was made common to all schemes.

The justification is the same shape as the one for fragments, and equally practical. Sets of documents that link to each other, such as the chapters of a book, are moved between file systems, HTTP space and FTP space constantly. Because the resolution rules are universal, the documents need not be modified when they move. Berners-Lee adds the honest caveat: moving half a set to one place and half to another still breaks the links.

4.4 The scheme, and why it must not be spent

The last section of the note is a warning, and it is the part that later events bore out.

The access scheme is by definition the highest point of flexibility. The Web Model, 1998

Its value is that it is the escape hatch. If the entire Web developed a problem that could not be solved within existing protocols, a new space could be created, and Berners-Lee argues that there is empirical reason to believe this would work because it already worked for Gopher and FTP:

If you have ported a concept between environments in the past, then there is a better hope that you can in the future. The Web Model, 1998

The danger is that spending the hatch destroys it. If many schemes are introduced, the space of scheme names becomes a namespace with all the properties that make namespaces hard:

  • clashes between names destroy interoperability;
  • ownership of names becomes commercially valuable;
  • fair management becomes both essential and difficult.

Worse, software would be needed to look up schemes and fetch handlers for them, which means something like DNS, which means that the top level of the Web’s namespace has silently become DNS again. At that point, he observes, there is no top-level extension switch left.

The conclusion is procedural: access schemes should not be open to trivial extension, and should be extended only by new standards with full open review. He does not rule new schemes out. He accepts data:, which puts a small document inside the URI itself, as genuinely new and orthogonal to HTTP, but suggests that many other proposed schemes would be better expressed as extensions within HTTP.

A space first, a protocol second

The note ends this section with a distinction that softens the warning. A scheme names a part of the URI space first, and a protocol only second. The protocols used to reach a space can therefore be replaced while the names in it stay the same: a new protocol for looking up DNS names, for example, could take over gradually without any http: address changing. His analogy is the telephone:

When touch-tone dialing was introduced, the telephone numbering system remained the same. The Web Model, 1998

4.5 A note on the word “resource”

The note closes with the etymology, which explains a persistent confusion. The first Web specification said Universal Document Identifier. The IETF discussion changed “document” to “resource” on two grounds: documents did not obviously cover films and sounds, and URIs exist for endpoints such as mailboxes and login ports, which are not documents at all. The word then picked up two further senses.

SenseIntroduced byCovers
“resource”The IETFAnything with a URI, including mailboxes (mailto:) and login ports (telnet:)
“resource”RDFAnything at all: the class of which every class is a subclass
“information resource”The Technical Architecture Group (a later addition to the note)Document-like things, the narrower original sense

Three meanings, one word, and the reader of any given specification must determine which is in force.

What happened since

  • The independence axiom was written into the standard. RFC 3986, of January 2005, specifies that the semantics of a fragment are defined by the media type of the retrieved representation, which is this chapter’s first axiom in normative form.
  • The client-side fragment was abused, then replaced. Single-page applications used fragments to encode application state, and Google’s AJAX crawling scheme of 2009 made a convention of it before deprecating it in October 2015. The History API’s pushState method restored a distinct URI per view, which is what the model asked for.
  • New fragment conventions kept arriving, as predicted. W3C Media Fragments URI 1.0 became a Recommendation in September 2012. Text fragments, addressing a passage by its words, shipped in Chrome in 2020. Neither required any change to HTTP, which is the flexibility this chapter claims.
  • The scheme warning was borne out by mobile. Applications claimed custom schemes in large numbers through the 2010s, and collided exactly as described: any application could register any scheme, and resolution was undefined. Both major platforms retreated to verified https links, Universal Links on iOS and App Links on Android, both introduced in 2015.
