The short version

Data on the Web can be written back as well as read. Send changes rather than whole files, and the server must refuse loudly when a change no longer applies. A “data wiki” treats every unused address as an empty document ready to fill.

The question

Shared calendars, the note observes, are “silos within the domain of calendaring”, though they have “a classic burning need for multi-person collaboration”: working out when several people are free is a classic challenge. Berners-Lee proposes letting applications write data on the Web as well as read it, and predicts that once storage is decoupled from applications, “application growth becomes dramatic”. The status line reads “Not finished at all”. The first paragraph states the goal:

The result is that storage becomes a commodity, independent of the application running on it. Read-Write Linked Data, 2009

A commodity is interchangeable, like electricity from a socket: any application could use any provider’s storage.

50.1 Editing where the information is

Berners-Lee hopes not to have to argue that the Web should be read-write; that has been done, he says, from Weaving the Web to the Read-Write Web blog. Then he adds: “I actually realize that in 20 year of writing these articles, I haven’t written a separate page on that topic!” What he offers instead is a maxim:

Also, I like the maxim that wherever you have access to information which you have the authority to correct or extend, there should be an easy way for you to do at that place. Read-Write Linked Data, 2009

The Web was built as a collaborative space; Berners-Lee’s word for the ambition is intercreative, written with a trademark sign.

50.2 Send the change, not the file

Two people edit the same calendar entry at once. The calendar is linked data: a document with a URI, holding triples, statements of the form subject, property, value. There are two ways to change it. HTTP PUT uploads a fresh copy of the whole file. A patch sends only the change: remove the triple saying the meeting is at 10:00, add one saying 11:00. The note does not spell out the danger of PUT shown in Figure 50.1, but it is why the 409 rule below matters.

The note’s patch is written in SPARQL Update, the editing half of the RDF query language, and sent by HTTP POST to the document’s own URI. Its one-line curl example, which sets Joe’s age to 66, sends: 

INSERT DATA { <http://dig.csail.xvm.mit.edu/2007/wiki/people/JoeLambda#JL>
              <http://xmlns.com/foaf/0.1/age> 66 }

A typical patch is a DELETE followed by an INSERT.

Replace the documentSend the change
What is sentThe whole new state, with PUTDelete this, then insert that, with POST (SPARQL Update)
If someone else changed it firstTheir change is overwrittenThe delete fails; the server must reply 409 Conflict
Who is toldNobodyThe writer, who backs the change out or retries

Berners-Lee then notices a second use for the same mechanism:

The atomicity of the DELETE,INSERT function can be used to provide various mutual exclusion systems, such as reserving a resource or generating unique sequential numbers, and so on. Read-Write Linked Data, 2009

Atomic means the delete and the insert happen together or not at all. Mutual exclusion means only one party can win. Figure 50.2 shows both uses.

50.3 The data wiki, and the empty document

One extra rule turns the protocol into a writable space, and it is a single change to how absence is reported:

Whenever a client requests a page which doesn't previously exist, instead of returning a "400 Not found" error, the server returns 200 OK, and a valid data document (in RDF/XML or N3) which contains zero triples. Read-Write Linked Data, 2009

The real code for not found is 404; 400 means Bad Request. RDF/XML and N3 are two notations for triples.

Every address is then a document that says nothing. A client can read, add a statement and write back, never distinguishing creation from modification: a wiki’s blank page, for data.

50.4 A Microsoft header, reused

The header that tells clients a server accepts edits begins with MS, and Berners-Lee’s only comment on the letters is: “Perhaps the MS stands for ‘modification service’.” The history is in a footnote. Every HTTP reply begins with header lines: labelled notes the client reads before the content. A server must say in one of them that it accepts writes, and a footnote explains the header used. Microsoft first built a proprietary write-back protocol, the “Microsoft Frontpage Extensions”, then introduced the MS-Author-Via header so that its clients could switch those off and use WebDAV instead, a standard extension of HTTP for editing files on a server.

Most WebDAV servers of the 2000s sent the header, so it was natural to advertise SPARQL there too.

Header lineMeaningEra, per the note
MS-Author-Via: DAVAccepts whole-file PUT, via WebDAVInherited from Microsoft

A second footnote records that the content type was application/sparql-query until 2013, and changed as the code in use changed to track the Linked Data Platform (LDP) work. A liberal server, it adds, accepts both types.

50.5 Who may write: deferred

The note does not deal with database-like storage interfaces, atomic transactions, or fine-grained access control. Its conclusion says read-write linked data comes “easily”, “with a little glue from the reuse of existing HTTP headers”, and then defers a large question:

Of course for many real-world applications, one does not want a data wiki in which anyone can write. We therefore need to extend the system to include access control. Read-Write Linked Data, 2009

The note belongs to a series: later notes take up access control (Chapter 54) and notification of changes (Chapter 58). Easy, says the conclusion; not finished at all, says the status line.

What happened since

  • SPARQL 1.1. SPARQL 1.1 Update and the SPARQL 1.1 Graph Store HTTP Protocol became W3C Recommendations on 21 March 2013. The note’s Followup cites a 2010 draft of the latter.
  • Linked Data Platform. LDP 1.0 became a W3C Recommendation on 26 February 2015, specifying reading and writing linked data over HTTP.
  • Solid. The Solid Protocol, built on LDP, is a specification of the W3C Solid Community Group (version 0.9, 2021), not a W3C Recommendation. It standardised HTTP PATCH with an N3 Patch format, the kind of patch language the note’s footnote anticipated.
