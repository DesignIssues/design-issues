The question

Written on the same December day in 1996 as the axioms of the previous chapter, and numbered by its author as the second in that sequence, this note exists to end an argument. The argument was whether the Web needed two kinds of identifier: names, which stay with a thing for life, and addresses, which change when it moves. Berners-Lee records that the word “identifier” had been chosen precisely to avoid the question, and that the evasion failed:

historically, that did not prevent a quagmire of circular discussion which in some circles paralyzed any forward progress. The Myth of Names and Addresses, 1996

The note's method is worth noticing. It does not propose a scheme. It attacks a distinction, and replaces it with a trade-off that has no technical solution.

3.1 The belief being attacked

The belief is learned young and from good examples. A variable name in a program is not a memory address. A fully qualified domain name is not an IP address. From these one generalises to two kinds of object: names, which follow a thing wherever it resides, and addresses, which change when it moves.

Berners-Lee's counter is that the second half of the generalisation is an illusion produced by not looking far enough down. Between anything one would call a name or an address and an actual location in three-dimensional space there is a long chain of indirection. A memory address is usually virtual, translated by hardware, possibly to a page on disk. A filename is resolved through mount tables and directories to an inode and thence to tracks and sectors. An IP address is not bound to a machine either, though it can only be reallocated within the routing structure.

From which he draws the generalisation that replaces the distinction:

we see that the constraint on how you can re-use an address is a function of what information is in the address. The Myth of Names and Addresses, 1996

3.2 Two anecdotes

The note's argument turns on two stories from the author's own records, and they are the reason it persuades where an abstract argument would not.

The Australian server. While Berners-Lee still maintained a registry of every Web server he knew of, a group in Australia sent details of a new server carrying botanical information, and supplied an IP address. He replied asking for a domain name, preferring it on principle. They answered that the domain name would depend on which university department ended up responsible for the server, which a reorganisation had left unsettled, but that the IP address could be guaranteed stable for a long time. The supposed name was the volatile part and the supposed address was the stable one.

info.cern.ch. The first Web server carried, among much else, the master list of Web servers. As coordination of the Web's protocols moved from CERN to MIT and the new Consortium, the information was maintained in America while the machine name still said CERN. CERN then asked that the name no longer be used for it, since the content was no longer under CERN's control and CERN could not assume responsibility for it; there was in any case a policy that names in the cern.ch domain should not refer to addresses off the CERN site. Every hypertext pointer into info.cern.ch space had to be changed to point into w3.org.

In neither case did the thing move. In both cases the name had to change, because the name contained a claim about authority and the authority changed.

3.3 Reading a URI for its future breakages

The note then performs an exercise that is still the best short teaching device in the collection. It takes an invented but entirely typical URI: 

http://pegasus.cs.foo.edu/disk1/students/romeo/cool/latest/readthis.html

and walks the segments, asking of each what would have to change in the world for that segment to become wrong. The scheme is among the least likely to change. The machine name encodes a function that will be reassigned. The department binds the document to a faculty the author may leave. The institution will outlast the relationship. The disk is an arbitrary grouping that will be broken at the next reorganisation. The status of being a student ends. The author may hand over maintenance, or the document may be adopted by a publisher or accepted as a thesis, and the responsible party changes. What is “cool” and what is “latest” both change by definition. The extension forecloses serving the same content in another format later.

The surprise is the verdict on the one segment that says nothing at all:

Perhaps the unlikely to change piece of information in the URL “readthis” as it contains no information at all, just like the proverbial “click here”. Effectively, it is a random name assigned to the document and as such, is perhaps the safest part of the path. The Myth of Names and Addresses, 1996

Meaninglessness is durability. This is the observation that the rest of the note formalises.

3.4 The naming problem

Stated as a dilemma, in the author's italics:

The naming problem. If you put information in a name, it decreases its longevity. If you do not, you cannot dereference it to a resource.

Information must be present because dereferencing requires it: to find out anything about a name one must look it up, and lookup is delegated hierarchically to whoever the name says is responsible. To find pegasus.cs.foo.edu one must ask a server controlled by Foo University. The information in the name is what routes the question.

The alternative is available and Berners-Lee describes it honestly. Message identifiers in mail carry no dereferenceable information; they support equality and lookup within a finite set, and nothing else. He suggests these deserve the word “identifier” rather than “name”.

3.5 Persistence is a contract

The conclusion is the one that makes this chapter belong in Volume I rather than in a chapter on URI syntax. Since the information in a name binds it to an authority, keeping the name dereferenceable over time means keeping that authority in operation over time, and that is an agreement between organisations rather than a property of a protocol.

Berners-Lee tests the alternative and rejects it: a worldwide hash table of randomly generated names would work technically, but would impose one funding model and one quality of service on everybody, with no way to pay more for a name that lasts longer. He sketches instead an alumni association selling perpetual care on a URI in return for an endowment.

Two proposals close the note. The first is that a new URI scheme's specification should describe the name-like and address-like properties of its identifiers, so that users know what to expect, which quietly disposes of the binary distinction by turning it into a spectrum to be documented. The second:

Metadata should be used to express the quality of service for the binding between a URI and a resource. The Myth of Names and Addresses, 1996

He also floats a mechanism the Web never adopted in that form: a syntax for putting a date into a domain name, so that an agent failing to resolve info.cern.ch could look for info.cern.ch.1994 and find the archive server holding that space as it then stood.

What happened since

  • The name and address split was decided by disuse. The Uniform Resource Name effort produced RFC 2141 in 1997 and a revision, RFC 8141, in April 2017, but URN schemes never became the general answer. HTTP URIs carried both roles, which is the outcome this note argues for.
  • Paid persistence arrived, as a contract. The Handle System and the Digital Object Identifier, with the International DOI Foundation founded in 1998, supply exactly what is described here: an organisation funded to keep resolution working, with the fee attached. The technology is secondary to the undertaking.
  • Time-based access was built, differently. RFC 7089, published in December 2013, specifies Memento, which asks for a resource as it was at a given datetime using a header rather than a dated hostname. The requirement Berners-Lee described was met; his syntax was not.
  • The second anecdote acquired an ending. CERN restored the first website and served it again at its original name in 2013, during the Web's twentieth-anniversary project. The URI outlived the reorganisation that retired it, because an organisation chose to make it so.

Questions

3.1 The note claims that a segment carrying no information is the most durable part of a path. Explain why this does not imply that opaque identifiers should be used throughout, using the naming problem as stated.

3.2 Both anecdotes involve a change of responsible party without any movement of data. Describe a third case from your own experience, and identify which segment of the identifier carried the authority claim.

3.3 A Digital Object Identifier contains a registrant prefix, which is information about authority. By the argument of this chapter, what threatens its longevity, and what mitigates the threat?

3.4 Berners-Lee rejects a global hash table of random names on the grounds that it imposes one funding model. Is that objection technical, economic, or political? Does it apply to content-addressed systems that hash the data itself?
