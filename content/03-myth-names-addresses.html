The short version

Everybody has clicked a link and got an error page. The usual diagnosis is that web addresses are merely addresses, and that what we need instead are proper names, which would stay with a thing wherever it went.

This chapter argues that the distinction is imaginary, and proves it with two true stories in which the supposedly permanent name had to change although nothing had moved. What replaces it is a genuine dilemma with no technical escape.

The question

Written on the same December day in 1996 as the axioms of the previous chapter, and numbered by its author as the second in that sequence, this note exists to end an argument. The argument was whether the Web needed two kinds of identifier: names, which stay with a thing for life, and addresses, which change when it moves. Berners-Lee records that the word “identifier” had been chosen precisely to avoid the question, and that the evasion failed:

historically, that did not prevent a quagmire of circular discussion which in some circles paralyzed any forward progress. The Myth of Names and Addresses, 1996

The note’s method is worth noticing. It does not propose a scheme. It attacks a distinction, and replaces it with a trade-off that has no technical solution.

3.1 The belief being attacked

The belief is learned young and from good examples. Computing students are taught that a name is something a person chooses and reads, while an address is something a machine uses to find a location. From such examples one generalises to two kinds of object: names, which follow a thing wherever it resides, and addresses, which change when it moves.

The Internet supplies the most familiar case. A domain name such as pegasus.cs.foo.edu is meant for people. To use it, a computer asks a directory server run by Foo University, which answers with a number called an IP address (for “Internet Protocol”), written as four numbers such as 192.0.2.17. The network’s routers, the machines that pass messages along, then use that number to find a particular computer. So the domain name looks like the name and the IP address looks like the address.

Berners-Lee’s counter is that the distinction is an illusion produced by not looking far enough down. The only true location is a point in physical space, and between it and anything one would call a name or an address there is a long chain of look-ups. The domain name is one step in that chain; the IP address is simply the next. Even an IP address is not bound to a machine, and memory addresses and filenames are translated in the same way, through further steps, before anything physical is reached.

From which he draws the generalisation that replaces the distinction:

we see that the constraint on how you can re-use an address is a function of what information is in the address. The Myth of Names and Addresses, 1996

3.2 Two anecdotes

The note’s argument turns on two stories from the author’s own records, and they are the reason it persuades where an abstract argument would not.

The Australian server. In the early days Berners-Lee kept a list of every Web server he knew of. A group in Australia sent details of a new server of botanical information, giving its IP address. He asked for its domain name instead. They replied that the domain name would depend on which university department ended up responsible for the server, which a reorganisation had left unsettled, but that the IP address would stay the same for a long time.

info.cern.ch. The first Web server, at CERN, held among much else the master list of Web servers. When coordination of the Web moved from CERN to MIT and the new World Wide Web Consortium (W3C), the information came to be maintained in America while its name still said CERN. CERN then asked that the name no longer be used, since it could not take responsibility for content it did not control. Every link into info.cern.ch had to be changed to point into w3.org.

In neither case did the thing move. In both cases the name had to change, because the name contained a claim about authority and the authority changed.

3.3 Reading a URI for its future breakages

The note then performs an exercise that is still the best short teaching device in the collection. It takes an invented but entirely typical URI: 

http://pegasus.cs.foo.edu/disk1/students/romeo/cool/latest/readthis.html

He walks the segments, asking of each what change in the world would make it wrong. Figure 3.3 gives his answers. One needs a word of explanation: the final .html names a format, which makes it awkward to offer the content in another format later, such as audio for blind readers.

The surprise is the verdict on the one segment that says nothing at all:

Perhaps the unlikely to change piece of information in the URL “readthis” as it contains no information at all, just like the proverbial “click here”. Effectively, it is a random name assigned to the document and as such, is perhaps the safest part of the path. The Myth of Names and Addresses, 1996

Meaninglessness is durability. This is the observation that the rest of the note formalises.

3.4 The naming problem

To dereference a name is to use it to fetch the thing named, by asking whoever is responsible for it. That is what a browser does with a link, and it is the hinge of the whole note. Berners-Lee states the dilemma in one sentence:

The naming problem: if you put information in a name, it decreases its longevity; if you don't you can't dereference it to a resource. The Myth of Names and Addresses, 1996

Information must be present because dereferencing requires it. Many names are handed out hierarchically, each level by the authority above it, and the look-up follows the same path. Berners-Lee’s analogy is a street name: to find out where the new “North Street” is in a small town, one asks that town for the definitive answer. In the same way, to find pegasus.cs.foo.edu one must ask a server controlled by Foo University. The information in the name is what routes the question.

The alternative is available and Berners-Lee describes it honestly. Every e-mail message carries a Message-ID, a string such as <20261014.5f3a@mail.example.org> that need only be unique. It cannot be typed into a browser to fetch the message; there is nobody to ask. What it does support is equality: two copies of a message with the same Message-ID are the same message. Within a finite collection, such as one mailbox, one can also look a message up by it. On a global scale one cannot. He suggests that such strings deserve the word “identifier” rather than “name”.

3.5 Persistence is a contract

The conclusion is the one that makes this chapter belong in Volume I rather than in a chapter on URI syntax. Since the information in a name binds it to an authority, keeping the name dereferenceable over time means keeping that authority in operation over time, and that is an agreement between organisations rather than a property of a protocol.

Two ends of the scale

Berners-Lee tests the information-free alternative and rejects it. One could keep a worldwide hash table, in effect one giant shared list of randomly generated names, each pointing to its resource. That would work technically, but it would impose one funding model and one quality of service on everybody, with no way to pay more for a name that lasts longer.

At the other end of the scale sit hierarchical systems such as the domain name system. Here a name leads to an authority, and the only way to keep the name working is a contract with every organisation involved in looking it up. He sketches what such a contract might look like: the Foo University alumni association runs a service offering names such as 

http://alumni.foo.edu/1998/romeo/202-aab

to any graduate who pays their dues, and keeps each one working indefinitely in return for an endowment, a lump sum paid once and invested so that its income covers the cost for ever.

Two proposals

Two proposals close the note. The first is that a new URI scheme’s specification should describe the name-like and address-like properties of its identifiers, so that users know what to expect, which quietly disposes of the binary distinction by turning it into a spectrum to be documented. The second:

Metadata should be used to express the quality of service for the binding between a URI and a resource. The Myth of Names and Addresses, 1996

He also floats a mechanism the Web never adopted in that form: a syntax for putting a date into a domain name, so that an agent failing to resolve info.cern.ch could look for info.cern.ch.1994 and find the archive server holding that space as it then stood.

What happened since

  • The name and address split was decided by disuse. The Uniform Resource Name effort produced RFC 2141 in 1997 and a revision, RFC 8141, in April 2017, but URN schemes never became the general answer. HTTP URIs carried both roles, which is the outcome this note argues for.
  • Paid persistence arrived, as a contract. The Handle System and the Digital Object Identifier, with the International DOI Foundation founded in 1998, supply exactly what is described here: an organisation funded to keep resolution working, with the fee attached. The technology is secondary to the undertaking.
  • Time-based access was built, differently. RFC 7089, published in December 2013, specifies Memento, which asks for a resource as it was at a given datetime using a header rather than a dated hostname. The requirement Berners-Lee described was met; his syntax was not.
  • The second anecdote acquired an ending. CERN restored the first website and served it again at its original name in 2013, in a project marking twenty years since CERN released the Web software into the public domain in April 1993. The URI outlived the reorganisation that retired it, because an organisation chose to make it so.

Questions

3.1 The note claims that a segment carrying no information is the most durable part of a path. Explain why this does not imply that opaque identifiers should be used throughout, using the naming problem as stated.

3.2 Both anecdotes involve a change of responsible party without any movement of data. Describe a third case from your own experience, and identify which segment of the identifier carried the authority claim.

3.3 A Digital Object Identifier such as 10.1000/182 begins with a registrant prefix (here 10.1000), which is information about authority. By the argument of this chapter, what threatens its longevity, and what mitigates the threat?

3.4 Berners-Lee rejects a global hash table of random names on the grounds that it imposes one funding model. Who would pay to keep such a table running, and what would happen to a name whose owner stopped paying? Does the same objection apply to content-addressed systems (where a file’s name is computed from its contents)?
