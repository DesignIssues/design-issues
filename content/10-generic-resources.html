The short version

One address can stand for something that comes in several forms: a report in English and in French, say, or as a web page and as a PDF. Whoever owns the address decides how much the thing it names is allowed to vary. When a reader follows the link, the browser and the server agree which form to send; this is called content negotiation. Berners-Lee’s observation is that the ways things vary are few: time, language, format, and the kind of device they are meant for.

The question

This note is older than most of Volume II and is presupposed by all of it. Written in 1996, it carries two status lines added at different times, and the second is unusually insistent:

This is an important axiom of web design, which must be understood for new designs to use URIs and HTTP properly. Generic Resources, note added 2000

The question is what a URI identifies when the thing identified has no one fixed sequence of bits. The answer supplies the notion of “document” that Chapter 7 depends on, and was the thinking behind HTTP content negotiation in 1992.

10.1 A ladder, not a pair

A resource may correspond to exactly one bit stream, as the text of an Internet RFC always has the same checksum. Or it may be generic: well specified as a concept but not closely enough to fix the bits. The note refuses to make this binary; Figure 10.1 shows its ladder.

Ownership decides where on the ladder a given URI sits:

Each resource may have a URI. The authority which allocates the URI is the authority which determines wo what it refers: Therefore, that authority determines to what extent that resource is generic or specific. Generic Resources, 1996

This is Chapter 2’s identity axiom (whoever owns a URI decides what it means): “how much may this URI’s content vary?” is always answered by the publisher. Nor is it a design decision:

This model is more of an observation of a requirement than an implementation decision. Multilevel gnericity clarly exists in all our current life with books and electronic documents. Adoption of this model simply follows from the rule that Web design should not arbitrarily seek to constrain life in general for its own purposes. Generic Resources, 1996

How a generic URI is served

A generic URI still has to deliver particular bits. A browser’s request carries headers, labelled lines of information; Accept-Language names the reader’s languages and Accept the formats it can display. The server picks the best-fitting form and says which it chose (Figure 10.2). This is content negotiation.

10.2 Four dimensions

The note’s empirical claim is that genericity in electronic resources runs along a small number of axes, and that the smallness matters.

From the smallness he draws a design instruction:

The fact that there are such a small number of dimensions currently apparent sugests that Web software should handle them individually in its interface with the user, even though the architecure should handle them as a single concpet. Generic Resources, 1996

One mechanism underneath, four controls on top. The browser’s language setting is the interface; the Accept-Language header it sends is the architecture.

10.3 Derivation is not genericity

A specific version may derive from one source, several, or unrelated ones. Berners-Lee keeps this derived-from relation separate from genericity. Take a Russian novel whose French translation was made from the English. All three are language versions of the novel, any of which a server could send for its URI: that is genericity. The chain Russian, English, French is history: that is derivation.

Genericity answers “may this be served for that URI?” Derivation answers “where did this come from?” A system that conflates them will serve a translation as though it were authoritative.

10.4 Saying it in metadata

The rest of the note is proposals, useful mainly as a record. Two statements are wanted: which dimensions a URI is generic in, and how two resources relate along a dimension. Both matter to a cache, a program that keeps copies of pages and must know when a stored copy is still good.

The first was a vary= field in an HTTP URI: header, URI: http//foo.com/bar/baz vary=time,language, a statement about the URI’s relation to the resource, recalling Chapter 3’s quality-of-service argument (an owner should state how stable a URI is). The second was a typed link, one that names its relation. In September 2000 Berners-Lee added RDF versions (RDF is W3C’s format for machine-readable statements), using classes (categories a resource belongs to) and properties (named relations between resources):

Statement wanted1996 proposal2000 RDF form

The note now marks the 2000 vocabulary as superseded by a later ontology at w3.org/2006/gen/ont, which does not cover target medium, the one dimension HTTP never negotiated either.

What happened since

  • Language and format shipped; time came later; the fourth went elsewhere. Content negotiation for media type, language and encoding is specified in what is now RFC 9110, of June 2022. Time was never part of core HTTP negotiation; the Memento extension, RFC 7089 of December 2013, added it with an Accept-Datetime request header, used mainly by web archives. Target medium was never negotiated in HTTP. It was handled by stylesheet media types from CSS2 in 1998, refined by Media Queries (a W3C Recommendation in June 2012).
  • The vary= proposal became something narrower. The Vary response header exists, but it describes which request headers affect the response for cache purposes. It does not state the publisher’s commitment about how much a resource may vary, which is what this note asked for.
  • Negotiation lost ground to distinct URIs. Publishers largely chose to give each language and each format its own address, with rel="alternate" links between them, because separate URIs can be linked to, indexed and cached. That is the ladder of section 10.1 made explicit rather than negotiated.
  • The genericity ontology was not widely adopted. The vocabulary at w3.org/2006/gen/ont is little used. The distinctions it draws are now usually made informally, or not at all.
