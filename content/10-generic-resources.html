The short version

One address can stand for something that comes in several forms: a report in English and in French, say, or as a web page and as a PDF. Whoever owns the address decides how much the thing it names is allowed to vary. When a reader follows the link, the browser and the server agree which form to send: content negotiation. Berners-Lee’s observation is that the ways things vary are few: time, language, format, and the kind of device they are meant for.

The question

Follow some links twice and the same bytes come back: the text of an Internet RFC, the note says, never changes and will always have the same checksum. Follow others and the bytes differ: most home pages change with time, and one address may send French to one reader and English to another. All are named by URIs. So what does a URI name when no single set of bits is the answer?

Berners-Lee’s answer, from 1996, supplies the notion of “document” that Chapter 7 depends on and, the note says, was the thinking behind HTTP content negotiation in 1992. In 2000 he added an insistent status line:

This is an important axiom of web design, which must be understood for new designs to use URIs and HTTP properly. Generic Resources, note added 2000

10.1 A ladder, not a pair

A resource may correspond to exactly one bit stream (one exact sequence of bytes), as the RFC does. Or a resource may be generic: well specified as a concept but not closely enough to fix the bits. The note refuses to make this binary; Figure 10.1 shows its ladder.

Ownership decides where on the ladder a given URI sits. The authority that allocates a URI determines what it refers to, and so, the note says, how generic or specific that resource is. This is Chapter 2’s identity axiom (whoever owns a URI decides what it means): how much may this URI’s content vary? is always answered by the publisher.

Nor, the note insists, is the ladder a design decision: books and electronic documents already come in many levels of genericity, and the model follows from one rule:

Web design should not arbitrarily seek to constrain life in general for its own purposes. Generic Resources, 1996

How a generic URI is served

A browser’s request carries headers, labelled lines of information; Accept-Language names the reader’s languages and Accept the formats it can display. The server picks the best-fitting form and says which it chose (Figure 10.2). This is content negotiation.

10.2 Only four ways to vary

The note claims that genericity runs along a small number of axes, and that the smallness matters (why, below). The Wall Street Journal varies with time, while each issue is fixed; most home pages change too, “in a less periodic way”. A translated paper may be cited in general, or as exactly the French translation one read. An image may travel as PNG or JFIF. And one resource may be aimed at a printer, a laptop, a cellphone, or be “projected onto a large screen for an audience” (Figure 10.3).

Because there are so few, he argues, software should give the user a separate control for each, even though the architecture treats them as a single concept. One mechanism underneath, four controls on top. The browser’s language setting is the interface; the Accept-Language header it sends is the architecture.

10.3 Derivation is not genericity

A specific version may derive from one source or several. Berners-Lee keeps this derived-from relation separate from genericity. Take a Russian novel whose French translation was made from the English. All three are language versions of the novel, any of which a server could send for its URI: that is genericity. The chain Russian, English, French is history: that is derivation.

Genericity answers may this be served for that URI? Derivation answers where did this come from? The note says only that derivation “is not part of the genericity relationship”. The risk of mixing the two is easy to see, though: a system that records the French as a version of the English may send the French when the English is asked for.

10.4 Writing the promise down

A cache, a program that keeps copies of pages, has to know whether a stored copy is still good, and a statement from the publisher is what can tell it. The note wants two: which dimensions a URI is generic in, and how two resources relate along a dimension.

In 1996 it proposed a header and a labelled link. In September 2000 Berners-Lee added RDF versions (RDF is W3C’s format for machine-readable statements), which the note now marks as superseded by a later ontology at w3.org/2006/gen/ont; that ontology does not cover target medium, a dimension the note itself says HTTP content negotiation did not handle.

The withdrawn 2000 section, still in the page source, is history but shows the idea. A TimeInvariant URI promises that what it returns will not change over time; Fixed promises it will not change under any circumstances, so every Fixed resource is also time-, language- and type-invariant. It gives one case: “P3P policies are supposed to be in u:Fixed.” (P3P was W3C’s format for machine-readable privacy policies.)

What happened since

  • Language and format shipped; time came later; the fourth went elsewhere. Content negotiation for media type, language and encoding is specified in what is now RFC 9110, of June 2022. Time was never part of core HTTP negotiation; the Memento extension, RFC 7089 of December 2013, added it with an Accept-Datetime request header. Target medium was handled instead by stylesheet media types from CSS2 in 1998, refined by Media Queries (a W3C Recommendation in June 2012).
  • The vary= proposal became something narrower. The Vary response header exists, but it describes which request headers affect the response for cache purposes. It does not state the publisher’s commitment on how much a resource may vary, which this note asked for.
  • Negotiation lost ground to distinct URIs. Publishers largely gave each language and format its own address, with rel="alternate" links between them (Google has recommended hreflang alternates since 2010), because separate URIs can be linked to, indexed and cached. Asked what a URI names, publishers answered by giving each rung its own address: the ladder of section 10.1 made explicit rather than negotiated.

Questions

10.1 The note claims genericity is observed rather than designed. Give a kind of resource whose variation does not fit any of the four dimensions, and say whether it is a fifth axis or a case of derivation.

10.2 Publishers largely chose separate URIs over negotiation. State the strongest argument for negotiation that this outcome discards. (Hint: think about sharing a link to the French version.)

10.3 A URI is Fixed in the sense of section 10.4, as the note says P3P policies should be. What does that commit the publisher to? Could a cache keep its copy forever? Why?

10.4 A system records a French translation as a version of the English it was made from. Using an example, explain what it might wrongly serve, and why.
