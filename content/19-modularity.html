The short version

A module is a part that can be changed or reused without understanding the parts around it. By 2008 the HTML5 draft had grown into parts that all depended on one another. Berners-Lee asked for separable pieces, such as the canvas drawing commands, to be split out. The Web works because each layer (IP, TCP, HTTP) offers a simple interface to the next.

The question

Published on the W3C blog in January 2008 and copied here, then edited in 2010 after a comment from Noah Mendelsohn, this note has a subtitle that carries the argument:

Simple things make firm foundations Modularity, 2008

The question is whether a specification that describes what browsers actually do can also be one that others can build on.

19.1 The tangle, as HTML5’s editor described it

The note opens with what it calls a classic example: HTTP and HTML are specified independently. HTTP first carried HTML, then images, PDF, SVG and JSON, each announced by a media-type label such as image/png, and HTTP itself did not change for any of them.

HTML was not so cleanly divided inside. Ian Hickson, then co-editor of HTML5, explained why modularising it is harder than it looks:

Note that it really isn't that easy. For example, the HTML parsing rules are deeply integrated with the handling of <script> elements, due to document.write(), and also are deeply integrated with the definition of innerHTML. Scripting, in turn, is deeply related to the concept of scripting contexts, which depends directly on the definition of the Window object and browsing contexts, which, in turn, are deeply linked with session history and the History object (which depends on the Location object) and with arbitrary browsing context navigation (which is related to hyperlinks and image maps) and its related algorithms (namely content sniffing and encoding detection, which, to complete the circle, is part of the HTML parsing algorithm). Ian Hickson, quoted in Modularity, 2008

ParsingReading the page’s text into a structure the browser can work with

Berners-Lee does not argue with the description. His reply is to ask for the parts that can be separated to be separated. He also quotes Laurens Holst’s reply: modular pieces would be easier to grasp, for reviewers and implementers alike.

19.2 Change and re-use: one property, two sides

The note gives the basic reason first:

There are lots of reasons for modularity. The basic one is that one module can evolve or be replaced without affecting the others. If the interfaces are clean, and there are no side effects, then a developer can redesign a module without having to deeply understand the neighboring modules. Modularity, 2008

Then the half that Chapter 1 calls the harder one:

The flip side is that a cleanly designed module designed as part of one system can be re-used in other systems. Modularity, 2008

Berners-Lee applies this to the canvas element: a blank rectangle in a page that a script can draw on. Its drawing commands differ in nature from the rest of HTML, which mostly sets and reads values in the markup. So does the section on client-side database storage, a way for a page to keep data on the reader’s own computer.

The element belongs in HTML, he argues, but the drawing commands belong in a separate document. Hickson agreed they should be split out in the long term, but said other parts had higher priority for anyone willing to edit.

19.3 Technology, not documents

What matters is the independence of the technology, which need not align with the boundaries of documents. HTML5 put two technologies, a markup language and a drawing interface, into one document; HTTP/1.1, one technology, was split across six RFCs in 2014. Berners-Lee adds that it usually makes sense for the boundaries to align anyway, so that different people can review, edit and implement different parts.

19.4 Designing for a system that does not exist

IP moves small numbered parcels of data (packets) between machines; TCP turns them into one reliable stream of bytes; HTTP uses that stream to fetch whatever a URI names, with a label saying what kind of data it is.

The note closes:

The web architecture should not be seen as a finished product, not as the final application. We must design for new applications to be built on top of it. There will be more modules to come, which we cannot imagine now. Modularity, 2008

An invariant is a promise that holds whatever happens above it. For HTTP: give it a URI and it returns data labelled with how to read it.

Clean interfaces give you invariants, which developers use as foundations of the next layer. Messy interfaces introduce complexity which we may later regret. Modularity, 2008

The note ends with a request rather than a rule: let us try, as we make new technology, or plan a path for old technology, always to keep things as clean as we can.

What happened since

  • The split happened, then was undone. The W3C published HTML Canvas 2D Context separately, as a Recommendation in 2015. In 2019 the W3C and WHATWG agreed that the WHATWG HTML Living Standard is authoritative, and it defines the canvas drawing commands inside HTML; in 2021 the W3C marked its separate Recommendation superseded.
  • The circle was not broken. As of 2026 the HTML Living Standard still specifies parsing, scripting and navigation as mutually dependent, in the way Hickson described.
  • A related kind of reuse arrived. Custom elements (page authors’ own tags) shipped in Chrome in 2016, giving the Web a way to plug components into HTML and into each other.
  • The ladder kept extending. HTTP/3, standardised in 2022, moved HTTP from TCP onto QUIC; HTTP/2 had kept TCP and changed only HTTP’s framing. Both left HTTP’s promise unchanged: a URI in, labelled data out.
