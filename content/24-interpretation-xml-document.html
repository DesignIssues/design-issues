The short version

One XML file can mix tags from several vocabularies, so something must decide which specification governs which part. Berners-Lee’s answer: the outermost element decides, and each element governs only what is inside it. Some elements, such as include, transform and decrypt, are replaced by their result; an element must also be able to mark its contents as quoted.

The question

Chapter 17 established that one document may carry several vocabularies. This note (2002, revised 2005) asks the question that leaves open:

If one party sends another an XML document, how does one say what it means? The Interpretation of XML documents, 2002

24.1 The problem: specifications that fight

The XSLT specification admits the problem. XSLT marks a template page with an xsl:version attribute; if another language used an axl:version attribute the same way, then for a document carrying both “it would be unclear whether the document should be processed by an XSLT processor or an AXL processor”. Without an overall architecture, the note says, specs battle each other, and worse:

In such a world, one would never know whether one had correctly interpreted anything, as there might be somewhere something deemed to change the meaning of what we have. Clearly this way lies chaos. The Interpretation of XML documents, 2002

Paul Prescod listed the candidate authorities: the DOCTYPE, the top-level namespace, a schema reference, other namespaces declared at the root, any attribute on the root element, and anything at all in the document. He concluded that the namespace of the root element, the outermost element containing everything else, is the only thing a processor must be able to dispatch on. Berners-Lee accepts that first conclusion and rejects Prescod’s second, a pipeline of wrapper elements to fix the order of processing.

24.2 Why a pipeline cannot work

The usual assumption was a pipeline: one stage per technology, such as inclusion, then style sheets, then decryption. Berners-Lee calls this, in the general case, “basically broken”: once elements nest arbitrarily, no single order of stages handles them all.

Many ways, one meaning

The note sketches three top-down procedures:

StrategyHow it works
Repeated pipelineRun each processor in turn, cycling until no functions are left.
Recursive parserHand each foreign element to the code for its namespace as it is met.
Lazy viewerElaborate a function (run it and put its result in its place) only when the reader scrolls to it, so that “certain things never need to be evaluated at all, saving time and bandwidth.”

These are “mathematically equivalent in their effect”, which is why he speaks of the meaning of a document rather than its processing model.

24.3 Elements that turn into other elements

The XSLT specification’s own example is an expense report page containing <p>Total Amount: <xsl:value-of select="expense-report/total"/></p>. The XSLT element is replaced by a computed number, and nothing else on the page moves. Berners-Lee calls such elements XML functions.

What they share:

  • any document may use them, without its schema foreseeing them;
  • the result may contain further functions;
  • “none of its ancestors or siblings may be affected”.

The last property makes order unimportant: no function can change anything outside its branch (though, as section 24.5 shows, it may read outside it). Of nested inclusions the note says it “doesn’t make any difference” whether the inner ones are expanded first.

24.4 The need to quote

Sometimes a function must be mentioned without being run. In an XML package (files bundled under a cover note, of which only the cover note is live) the packaged items are quoted. An XSLT template that outputs an XInclude element contains a real XInclude element, which must not be expanded inside the XSLT.

A pipeline cannot say this. Such ambiguities, Berners-Lee says, “stem from the lack of quoting syntax in XML”. The same kind of failure, text meant as data being obeyed as instruction, reappears today in prompt injection.

24.5 What the note leaves open

The open issue is references to parts of the document that may not yet have been elaborated.

  • A function may read outside itself. Does it see the document before or after other functions run?
  • An XPointer could point into the raw or the elaborated document. Berners-Lee inclines to “after”, so that a pointer into SVG lands on SVG.
  • XML Signature, he was told, signs the raw source before XInclude; either choice is sometimes useful.

24.6 Reading the label before opening the document

Because the root element decides, its namespace says what the whole document is: an XHTML root yields a hypertext page, an SVG root a diagram. Knowing this, “the operating system … can use icons to tell the user, before they open an email or follow a link, what sort of a thing it contains”. The note recommends a specific MIME type, the label a server sends in the HTTP headers, for each well-known root, and adding +xml to the label (as in image/svg+xml) only when a generic XML program may read the document top-down.

One great schema for each combination of vocabularies scales badly: a group combining four specifications must settle how every pair fits, and the note asks whether it would take “n2 years”. He would rather each facility had its own schema. The note ends:

The top-down processing model for XML as an architectual principle resolves many of the questions which remain unanswerable with pipelined processing. In fact, consideration of the example shows that pipeline processing could be actually dangerious, producing errors and possibly security issues, in the case of generally nested XML technologies of the types discussed. The Interpretation of XML documents, 2002

What happened since

  • The question was overtaken. Mixed-namespace XML did not become the ordinary way to publish; the HTML that won (Chapter 23) has no author-declared namespaces.
  • A pipeline language was standardised. XProc became a W3C Recommendation in May 2010.
  • A related danger materialised. XML Signature wrapping attacks, described by McIntosh and Austel in 2005, exploit a gap between the element a signature covers and the element an application acts on, a cousin of the question in section 24.5.
  • The quoting problem recurs. “Prompt injection”, in use since 2022, is section 24.4’s failure in AI systems.
