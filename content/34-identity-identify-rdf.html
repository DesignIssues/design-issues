The short version

RDF data is written in XML markup, so a reference such as #foo can mean a piece of the document, a node in the data, or the real person. Berners-Lee gives each kind of pointer its own attribute, shows that one URI can change meaning with the file’s label, and says to identify a person by something unique, such as a mailbox, without confusing the two.

The question

Chapter 32 established that the model is a graph of statements. This note, from 1998, asks the question that immediately follows and is easy to get wrong: when a statement refers to something, what exactly is it referring to? The element in a document, the node in the graph, or the thing in the world?

Berners-Lee opens with the example that shows how invisible the problem usually is:

In most cases it seems obvious to the human reader. The jam jar label text does not (normally) read “jam jar label text” or “jam jar label” or “jam jar” but “jam”. Identity, 1998

People resolve these levels without noticing. Machines cannot.

34.1 Three things a reference might mean

The markup is XML: tagged elements, which carry attributes (name=value settings) and contain child elements. The data is RDF: a graph whose nodes stand for things, linked by properties. The XML encodes the graph; the graph describes the world.

Berners-Lee’s example describes a person, Albert, in an element with id="foo". Inside it, a description of Albert’s father, Joe, says that Joe wrote #foo and is a friend of #foo (Figure 34.1). Which does each mean?

A programming language would add a marker character, but the aim is to use only the existing language. So he distinguishes by the name of the referring attribute, not its value:

AttributeWhat it refers toIn the example
value=a literal: the string itself, not a referencethe name “Joe”
href=the piece of document (text, or XML fragment) that the URI points atJoe wrote the element
resource=the abstract thing that the RDF node for that fragment describesJoe’s friend is Albert

He notes why the middle form has to exist at all, and the reason is practical:

This is important, as for example it is bits of XML which one digitaly signs, not (in sigend XML) bits of RDF. Identity, 1998

34.2 The clash he records as a bug

A section added in February 2000 is flagged in the original as a bug in the relationship between the two layers: Chapter 24’s interpretation problem, where the same bytes read differently under different rules.

Take a URI with a fragment (the part after #) pointing into a file describing Ora Lassila. A fragment’s meaning comes from the media type, the label saying what kind of file it is (Chapter 11).

Even the XML reading is unclear. His verdict:

To have a different interpretation of a URI as a function of the notional type of the document belies the fact the point of using XML syntax for RDF was that RDF documents should be XML documents! Of course we embed RDF in regular XML documents. So this distinction is nonsense. Identity, 1998

The easy fix fails. RDF could take the URI to mean the node the element describes, but RDF must also make statements about elements themselves.

Berners-Lee wrote the snippet himself, and might say he is the author of foo.rdf#bar; but he is not the author of Ora Lassila (Figure 34.2). He lists three remedies:

  • Already in RDF: parseType="Resource" or parseType="Literal" on inline data. Fixes: says whether the reference is to the RDF thing or to the XML.
  • A new property: one linking an XML subtree to the RDF object it describes. Fixes: lets both be named and related.
  • A new attribute: object= for the RDF node, leaving resource= for the fragment. Fixes: gives the node the pointer it lacks in Figure 34.1.

34.3 Identifying things that have no address

The second half is the part that became standard practice, and it carries a warning about terminology.

RDF treats people as “resources” and in using this terminolgy which normally means tautologically “things with URIs” makes people expect Ora to be synonymous with his web page or his mailbox. This is not of course good design. Identity, 1998

The method he proposes instead is to identify a thing by a property that happens to be unambiguous, rather than by giving it an address it does not have. Ora gets an anonymous node, with no URI. If no two people share a mailbox, two descriptions with the same mailbox can be merged into one person, and conclusions drawn.

Shortcuts are sometimes needed, but they cost something. A compound property such as author-mailbox collapses two steps into one arrow.

With the shortcut there is no node for the author, and the fact that a person wrote the book and has that mailbox must be stated elsewhere. The schema, the published definition of a vocabulary’s terms, is a good place, because it makes the expansion evident to any processing machinery.

He also declines, explicitly, to settle which properties should be treated as identifying, calling it a rat hole that is not core to the discussion. That restraint is the same one as Chapter 22: the mechanism can be specified without settling the philosophy.

What happened since

  • The mechanism was standardised. Inverse functional properties, which formalise “no two things share this value”, are part of OWL, a W3C Recommendation of February 2004. The Friend of a Friend (FOAF) vocabulary identifies people by mailbox, or by a scrambled (hashed) form that hides the address.
  • RDF got its own media type. RFC 3870, published in September 2004, registered application/rdf+xml, a label under which RDF’s own fragment rules apply.
  • The question of what a URI names went to the TAG. In June 2005 the W3C Technical Architecture Group resolved its “httpRange-14” issue: an http URI may name anything, including a person, but one without a fragment that answers with a document names a document.
