The short version

  • The problem: a compact way to write one step along a link, such as from a person to their email address.
  • Forward steps are easy to write; backward steps read badly in every notation tried.
  • Sets and lists are different shapes, and a set stored as a list suffers.

The question

Berners-Lee describes this note as “simply a footnote historical record about some rather arbitrary choices, to save me going over the reasons again and again.” Volume III argued that specifications should record which decisions were arbitrary. This is what such a record looks like while the decisions are still open.

43.1 The problem: saying “one step along”

In RDF, data is a graph: things joined by labelled links. Each label is a property, such as email or boss. Moving along links is traversal. The need is constant: given an expression for a person, write one for the thing one email link away.

Berners-Lee sets the criteria first:

“Neat”? Compact, powerful, simple, naturally understandable because of metaphors with existing use of similar syntax. Alternative design choices in Notation3, 2002

Familiarity counts as a design property: borrowed syntax costs less to learn. Two directions are named. Forward traversal follows a link the way it points; backward traversal asks what points here. His instinct is that forward traversal is the more common need.

43.2 The candidates

The note weighs seven families of notation, several with variants, each borrowing a metaphor:

The note then sorts them by two questions: does the operator come before or after the term, and which way does it travel?

This is the most transferable point in the note. A notation that borrows familiarity from a natural language inherits its asymmetries: any syntax that feels natural in English will find an email’s owner harder to name than a person’s email.

The note also offers a way round. A backward step along email is a forward step along its inverse. So a compact way to write an inverse would serve, if it is clear when that is merely syntax and when the inverse is really being named.

43.3 Sets, and why containers were the wrong shape

A later section, dated 2005, argues for adding sets, and the argument is empirical:

It turns out that in many cases in applications we have seen, containers are in fact logically unordered sets, not ordered lists. Whether it is mail addresses on a mailing list, or rows in a database, or statements in an N3 formula, the order is immaterial, and something can occur in the set once or not at all. Alternative design choices in Notation3, 2005

Using a list for a set has three costs:

CostWhat it means in practice
Two lists with the same members in different orders are not evidently the sameComparison and deduplication become application logic
The fact that it is really a set is communicated out of bandOnly people who know the application know it
Implementations cannot use libraries optimised for setsThe wrong data structure is used throughout

So sets need what lists have: a form in ordinary statements, which general-purpose software can pass along, and a shorthand for people.

What was proposed

For statements, the note borrows from OWL: [ owl:oneOf (1 2 3) ] is the class whose members are exactly 1, 2 and 3, in any order. The shorthand was harder; the note tables seven syntaxes, including:

SyntaxForAgainst
(1, 2, 3)Almost no new punctuationParser must read ahead a whole expression
($ 1 2 3 $)Otherwise just like a listNone recorded
{$ 1, 2, 3 $}Curly braces are conventional for setsBraces already mean formulae
@Set{1, 2, 3}Just a new keywordNone recorded

It records that “The current choice is {$ 1, 2, 3 $}”, with dollar signs to tell a set from a formula. A harder question stays open: does {$ :a, :b, :c $} say that the three are different things? If so, members can be counted, but union and intersection need to know which are the same. If not, union is safe but counting is not.

43.4 Why an unfinished note is worth a chapter

Little here is final: the set syntax is a current choice, and a section of loose material is headed simply as fodder. Chapter 21 asks a specification to state which decisions are arbitrary and which follow from logic. In finished documents the arbitrary choices have hardened into the only way things are written. Here they are still soft, and one can see which parts of a notation were forced, as when a parser cannot tell a list from a set in time, and which were a matter of taste and personal history.

What happened since

  • Caret and slash arrived in the query language. Property paths became part of SPARQL 1.1, a W3C Recommendation of March 2013. They use ^ for an inverse step and / for a sequence: two of the candidates weighed here.
  • No set literal was standardised. RDF 1.1 and Turtle, both W3C Recommendations of February 2014, kept ordered collections and rdf:Bag but added no set syntax or semantics.
