The short version

When a program meets a label it does not know, it can stop, skip it, or skip only the label and keep the text. Which is right depends on the label, and nothing in the document says which. Berners-Lee asks that formats let the writer say so, in particular that a reader must understand a part or stop.

The question

This is one of the shortest notes in the collection, and it names the gap that Chapters 16 and 17 both circle without closing. Free extension lets anything be added. Nothing lets a publisher say that an addition must be understood.

Berners-Lee states the cost in one sentence:

Historically the lack of such a “mandatory field” has led to a complete inabaility to get any particular guaranteed behaviour be clients on the web. Mandatory extensions, 1998

The word is “complete”: nothing at all can be guaranteed. If every extension may be ignored, then no extension may be relied upon, and the set of things a publisher can count on is frozen at whatever was in the base specification (the first, agreed version of the format).

18.1 The requirement

The note states the demand twice. A language must provide not only for its own extension but for a way to say whether a given extension is optional. Berners-Lee calls this a fundamental key to smooth evolution from one version of a language to the next.

An element is one labelled piece of a document, such as <bold>…</bold>; a namespace is a whole vocabulary of such labels. A schema is the published description of a format’s labels and how they fit together. He allows the flag in either place, shown here for an imagined recipe-plus format:

Flag written in the documentFlag written in the schema
One elementthis <allergen> must be understoodrecipe-plus’s schema says <allergen> must be understood
A whole namespacethis recipe says every recipe-plus term must be understoodrecipe-plus’s schema says all its terms must be understood

The same places can equally say “may be skipped”.

The note was written when XML namespaces were arriving, and the complaint is that they solve half the problem:

XML provides in Namespaces a standard way of extending languages. It should also, in my opinion, provide a standard way to specify mandatopry or optional extensions. Mandatory extensions, 1998

18.2 Three things to do with something not understood

Meeting an element it does not recognise, a processor can do one of three simple things, and which one is correct depends entirely on what the element means.

The examples in the figure are his. A logical negation must stop a processor, because ignoring it inverts what the document says. A comment may be dropped whole. Emphasis should be unwrapped, since the text inside it still belongs to the document.

HTML inherited mail’s rule as unwrap-always: right for bold, wrong for a comment, whose private text is shown.

18.3 Sublanguages

His other proposal, listed first in the note, is smaller. Berners-Lee wants a language to be able to declare itself a sublanguage of another:

The simple assertion that language A is a sublanguage of language B means that the writer's intent is preserved if a dpcument in language A is converted into a document in language B just by relabelling every term as being from langauge B. Mandatory extensions, 1998

A receiver that knows only B can then treat the A namespace as though it were B. The constraint he attaches is the important part: the assertion must be simple enough to put in the document, so that the receiver need not dereference (fetch from the Web) a schema to act on it.

This is the same instinct as the final requirement of Chapter 17 (section 17.5). Whatever a processor needs in order to cope with the unfamiliar should travel with the document, not wait at the end of a network request.

What happened since

  • The proposal was not adopted for XML. No standard way to mark an extension mandatory or ignorable was added to XML or to namespaces.
  • It was adopted elsewhere. SOAP 1.1 (W3C Note, 2000), a messaging format built on XML, added exactly this: a mustUnderstand attribute on header entries, which a receiver must either honour or fail on. The HTTP Extension Framework (RFC 2774, 2000) let a request declare an extension mandatory with a Man: header. Internet certificates, as profiled in RFC 2459 (1999), carry a “critical” flag on X.509 extensions: a certificate with an unrecognised critical extension must be rejected.
  • HTML chose the third option permanently. The HTML5 parsing rules, first published by the W3C in January 2008, define exactly how unknown elements are parsed and displayed (unwrapped), which removes the ambiguity without supplying the mandatory flag.

Connections

The inability this note names is the disadvantage of free extension recorded in Chapter 16, and the requirement it makes is the one Chapter 17 stops short of. The tolerance principle that produced the old rule is Chapter 1, and its reconsideration is Chapter 23. An older precedent: PNG 1.0 (1996) already marked each chunk of an image file critical or ancillary by the case of its name’s first letter, so a decoder could skip an unknown chunk without consulting any schema, the instinct of section 18.3.

Questions

18.1 Take a markup or data format you use and find an element or field for which each of the three behaviours would be correct. What in the format, if anything, distinguishes them?

18.2 A publisher wants to add a feature that consumers must not ignore. Under free extension, what can the publisher do instead, and what does it cost?

18.3 A new format, “recipe-plus”, adds labels to an existing recipe format. Write one sentence it could carry saying old readers may treat it as the old format. When would that sentence be a lie?

18.4 Name a case where stopping is safer than guessing, and one where it is not.
