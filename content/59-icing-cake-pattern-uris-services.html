The short version

Put the published page’s address first. Reach every tool for that page by adding a few characters to its address, so that people and programs can always find their way between the page and its tools.

The question

A small note from December 2016 with a status line reading “good enough for government work”, about a design decision every project makes without noticing: when a thing has tools attached to it, whose address comes first?

59.1 Two patterns

A version control system keeps every past version of a project’s files; GitHub is the best-known web interface to one. When the project is a website, one file gets several addresses. In Berners-Lee’s example, a page index.html in the project myproject of the account acmedata has an editable view, a raw copy on a second domain, a hosted copy on github.io, and finally the live copy on the owner’s own domain.

On w3.org the arrangement is reversed. The page keeps its plain address, and its tools are reached by adding a comma and a short word to the end.

59.2 The complaint, stated twice

Berners-Lee names two failures of discoverability, meaning being able to find one address from the other, and they are symmetrical:

One disadvantage of this pattern is that when you are in the project github web pages, it it is not at all obvious how to construct the URL above for the live site, and the project folks he to make an explicit link to it in their documentation. Icing on the cake, 2016

And in the other direction:

Another disadvantage is that when you are on the live site, either the acmedata.github.io site or the acmedata.com site, their is no obvious way of knowing that the github site exists or of finding its URI. Icing on the cake, 2016

A software package may record its repository in package.json, a project’s description file, but a client fetching the HTML page cannot discover the link.

59.3 Why the choice is architectural

The pattern names what a system treats as primary. In the first, the repository is the real thing and publication is an export. In the second, the published thing is the real thing and everything else is an accessory:

The live data is the center. This is the cake - this is the main purpose of the site: serving the web pages. That is the cake, and everything else is icing on the cake. Icing on the cake, 2016

The server sees the comma and runs the tool on the address before it. The comma itself is incidental; suffixes need only be short, simple and memorable. What matters is a fixed rule, so that anyone holding the page’s address can work out the tool’s.

The note’s appendix, a snapshot of 10 December 2017, lists about sixteen such tools. Five of them:

SuffixWhat it returns
,textA plain text version of the page
,checklinkThe bad links in the page
,validateThe markup errors: mistakes in the page’s HTML tags
,spellThe spelling errors
,cvslogThe log of changes to the document

59.4 The same problem, generally

Chapter 57 asked where an application should save data so another can find it. This note asks the same about tools: where should a validator or change log live so that anyone holding the page can find it? In both, a protocol is not enough; what is missing is a rule that lets one party compute where another put something.

It is also Chapter 3’s argument about information in names. An address that names the tool which made it will eventually be wrong. Naming the work and deriving the tool’s address leaves the tool free to change. A page at acmedata.github.io/… breaks if the project moves off GitHub; acmedata.com/… does not.

59.5 Icing for machines

A comma typed by hand serves a person. Berners-Lee also wants icing visible to programs. The Memento protocol adds HTTP headers, labels sent with every page that the reader does not see, that let a browser find older versions of a page. Solid, his personal data system, links each resource to the page controlling who may access it.

w3.org itself falls short: follow a link into its CVS, an older version control system, and the addresses look much like GitHub’s, with no way straight back. What he would like instead:

It would certainly be interesting for someone to make a web interface for a version control system which is all icing on the original cake, where at any point you can strip off the ,stuff and get back to the original file live on the web site Icing on the cake, 2016

His conclusion asks for both: the comma for people, and a link for software.

What happened since

  • The hosted-copy pattern predates the note. GitHub Pages launched in 2008.
  • Discovery was patched, not fixed. npm’s package.json has a repository field, which the live page does not expose.
  • Memento was already published, as RFC 7089 (December 2013, an Informational RFC).
  • Well-known locations were revised. RFC 8615 (May 2019) replaced RFC 5785 (2010). Both reserve /.well-known/ for metadata about a site, solving discovery per site rather than per document.
