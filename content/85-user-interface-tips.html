The question

Written in December 2016 and, by the author’s own description, a list of his own biases in a bit of a random order. It is the least architectural note in the collection and it is included because of an observation in its opening:

In a way, more than 25 years after the WWW project started, you'd think that these things would be be generally understood. And they are covered in many blogs and books. But here are some points which still now seem to need pointing out. User Interface: Random tips, 2016

Twenty-five years, well documented, still being got wrong. That is the interesting fact, and most of the items have a common cause.

85.1 Text must be copyable

The argument for copyable error messages is about who can be helped:

People who do not understand a lot about your system may still be able to use a full detailed error message, but looking it up in a search engine, or asking a friend. User Interface: Random tips, 2016

A message nobody can copy can only be used by someone who already understands it. Making it copyable moves it from the small set of people who can act on it to the whole Web of people who might.

85.2 The self-defeating password field

The argument about pasting is a chain of consequences ending in the opposite of what was intended:

If they then can't paste them in, and are forced to type them (perhaps on a phone keyboard with the echo of the characters replaced by dots) they may give up and switch to using a short and unsafe password out of frustration. User Interface: Random tips, 2016

A field that blocks pasting was built to be more secure and makes users less secure, because the security of a password is decided by whether it can be remembered, and blocking the paste requires it to be. This is Chapter 23’s incentive analysis in miniature: the design shapes behaviour, and the behaviour is what matters.

The demand for visibility is the same argument from the other side:

If you want me to use a good password, I am not going to be able to type it in without mistakes -- unless you let me see it as I type it User Interface: Random tips, 2016

85.3 The cause underneath

Berners-Lee names the mechanism by which these things go wrong:

If you take suppress and replace the default line editing the browser does in each device, then you should have really important reason for it, not just cuteness. User Interface: Random tips, 2016

Every item on the list is the same act. The platform supplies text handling that works everywhere, in every language, with every assistive technology, and a developer replaces it to make one field prettier or stricter. The replacement handles the case it was written for and loses everything else the original did.

He names the usual culprit specifically: auto-completion libraries, and gives the test. If one does not allow pasting, it is a step backwards, and the right response is to go back to the basic widget.

85.4 Why the list still needed writing

The chapter’s value is not its advice, which is elementary, but the question in its opening. Why does something so well documented still need saying?

Because each violation is invisible to its author. A developer who replaces a field tests that it accepts the input they had in mind. Nobody tests that an error message can be selected, because the test is performed by someone who already knows what the error means. The failures are all in the gap between the author’s situation and the user’s.

That is the same gap Chapter 88 describes for language, and it has the same remedy: the work of thinking about what somebody on the other side of a boundary is doing, which Berners-Lee there calls hard work.

What happened since

  • Password fields became pasteable by consensus. Major security guidance from the mid-2010s explicitly told sites to allow pasting, and browsers began overriding attempts to block it, which is the rule of section 85.2 enforced by the platform.
  • Visibility toggles became standard. The option to reveal a password is now offered by the platform on most devices.
  • Copyable error messages did not improve. Uncopyable messages remain common, particularly in mobile applications and in dialogues rendered outside the ordinary text system.
  • The cause persists. Custom input components replacing platform ones are more common than in 2016, and each generation reintroduces the same losses.
