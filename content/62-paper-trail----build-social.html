The short version

Many processes move through stages: drafted, approved, published. Often a database holds “the current stage”. Berners-Lee proposes holding no such record. Each new document points back to the documents that justify it, and the stage is whatever the latest show, as with a W3C draft. A rules document, the schema, says what a new document needs and what may come next.

The question

Social processes look like state machines. However, they don't exist as a state variable stored in one place, but as a trail of documents. Paper Trail, 1999

Its simplest case is a loan between two people: the balance can be worked out from the repayments alone, so nobody need hold it. The main example is W3C’s own process, where a specification’s stage is shown by the documents written and endorsed so far. Written in February 1999, and offered as a possible student project, the note calls itself an example of how a social machine can be made without a centre. Chapter 61’s note of 2000 points back to it.

62.1 No state variable anywhere

A state machine is always in one of a fixed set of stages and moves between them when certain events happen; a traffic light is one. Social processes behave like this but store no single value, no state variable, saying which stage they are in. So:

You know the true state of the machine only if you have access to the latest documents. Paper Trail, 1999

That, he adds, is not a problem to solve: it is the real life being modelled. Paper Trail lets people follow a strict process by creating documents in a constrained way. Each carries a pointer to a schema (the document defining its type and rules), pointers to the documents justifying it, and a notarisation: a time stamp recording when software checked it against the schema.

62.2 What must exist, and what may come next

The schema holds prerequisites, the other documents that must exist for a document to be valid, and hints, the kinds of document that may be made from it: the state transitions.

In Figure 62.1’s example, if the prerequisites exist the software creates and notarises the new draft, which carries a button leading to a form for the next document type the hints allow. A “proposed recommendation” needs everything a draft needed plus an endorsement by the director or any two members of the management group.

62.3 State as a function of messages

The note then turns to computer protocols, agreed rules for exchanging messages. In the loan, the state is the balance, each repayment a message, and the process ends at zero. Written generally, a protocol P defines each new state from the latest message, the previous state and the time: sn = P(mn, sn−1, t). Equivalently, from all the messages to date: sn = P′(m1 … mn). The second is the paper trail: only messages and a function.

The state may be anything from a single number to a web of statements (the richer, the more interesting to him), but it must hold whatever is needed to compute future states. In TCP, the protocol under most Internet connections, that means unacknowledged packets; once the connection closes, it could be just “terminal state”, or also every byte transferred: a design choice.

Starting, ending, forgetting and nesting

StartSome messages are valid beginnings: in TCP one sends a SYN message; on the telephone one picks up the receiver.
EndNo further message changes a final state. The loan reaches one at zero; a lifetime warranty “remains in non-final state (until you die!)”.
ForgetOnce the state is known, the messages behind it can be thrown away: the protocol is, the note says, “an information destroying function”. In the US, records may be discarded after seven years, when “no one even the tax man has the right to query them”.
NestA protocol runs inside a larger one: a W3C working group’s last state, its work accepted as a Recommendation, is a message to the Consortium. A minority report reveals a group that never reached its final state.

62.4 A process with no one in charge

Such processes can run on a newsgroup or by email: “it works in a write-only medium”. Nobody edits a shared record. As in commerce, one’s view of the state depends on which messages one has seen; there is no privileged party to ask, and anyone who can fetch the documents can check them.

The product the note expects is a standard language for writing protocols. Messages would describe themselves, containing “a pointer to the language in which they are written, and that includes (or points to) the protocol to which they claim to adhere.” The self-describing Web would extend from documents to conversations.

62.5 Left for the student

The brief ends with “Challenges if you finish early”: model an “auction”, a “peer review journal”, “presidential impeachment ;-)”; allow for the fact that “States can split”, as when a draft goes to W3C, the IETF, or both. The sharpest question: “Do you need to be able to prove non-existence of documents?” Holding a valid document does not show that no later one has overridden it. The note leaves open whether such proof would be local to an author or global.

What happened since

  • The note’s own epilogue (2001) and update (2004). A Web Services workshop surfaced the need for process-flow descriptions; by 2004 the Semantic Web Application Platform (SWAP) could implement the ideas.
  • The pattern won without the vocabulary. Version control systems are paper trails: state is a function of the commits. The history proves integrity, not that commits followed the rules.
  • Append-only became an architecture. Event sourcing, deriving current state from a log of events, is section 62.3’s second formulation; Martin Fowler described it in a 2005 article.
  • Public notarisation logs, 2013. Certificate Transparency (RFC 6962) made append-only, publicly checkable logs a standard tool.
