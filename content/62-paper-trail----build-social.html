The short version

Many processes move through stages: drafted, approved, published. Usually a database holds “the current stage”. Berners-Lee proposes holding no such record. Each new document points back to the documents that justify it, and the stage is whatever they show. A rules document, the schema, says what a new document needs and what may come next.

The question

Chapter 61 asked for a way to formalise a sequence of messages. This note, from February 1999, is the proposal, and its status line describes it as an example of how a social machine can be made without a centre.

The observation it rests on is one sentence:

Social processes look like state machines. However, they don't exist as a state variable stored in one place, but as a trail of documents. Paper Trail, 1999

62.1 No state variable anywhere

A state machine is always in one of a fixed set of stages and moves between them when certain events happen; a traffic light is one. A state variable is the single stored value saying which stage it is in. Social processes have the first without the second, and the consequence follows:

You know the true state of the machine only if you have access to the latest documents. Paper Trail, 1999

This, Berners-Lee adds, is not the problem being addressed but real life being modelled. His proposal lets people follow a strict process by creating documents in a constrained way. Each carries a pointer to a schema (the document defining its type and rules), pointers to the documents justifying it, and a notarisation: a time stamp recording when software checked it against the schema.

62.2 Prerequisites and hints

The schema carries two kinds of thing, and the distinction is the design’s neatest feature. Prerequisites say what must exist for a document to be valid, expressed in terms of other documents. Hints say what kinds of document may be made from this one, which are the state transitions.

In the W3C example of Figure 62.1, if the prerequisites exist the software creates and notarises the new draft. The draft then carries a button leading to a form for the next type of document the hints allow. Promoting it to a “proposed recommendation” needs everything above plus an endorsement, which the source spells out: the director, or any two members of the management group.

Validity is enforced; transitions are merely offered.

62.3 The general form

Halfway through, the note turns to computer protocols, agreed sets of rules for an exchange of messages. A protocol P defines each new state from the latest message, the previous state and the time: sn = P(mn, sn−1, t). Equivalently, it defines the state from all the messages to date: sn = P′(m1 … mn). The second is the paper trail: only messages and a function.

The note’s simple example is a loan between two people: the state is the balance, and the process ends when it reaches zero. Berners-Lee ranks what the state might be, a piece of editorial opinion in a technical note:

The state could be a logical formula, an RDF graph, or an XML document, or just a number, in decreasing order of interest. Paper Trail, 1999

A number says where things stand; a formula says what follows. The state must hold whatever is needed to compute future states: for the loan, the balance. Once the loan is repaid, the state could hold just the fact that it was paid, or every repayment: a design choice, not a fact.

Starting, ending and forgetting

StartSome messages are valid beginnings: in TCP, the protocol under most Internet connections, one sends a SYN message; on the telephone one picks up the receiver.
EndNo further message changes a final state. The loan reaches one at zero; a lifetime warranty never does.
ForgetThe protocol is “an information destroying function”: saying what must be remembered defines what can be thrown away. In the US, records of a transaction may be discarded after seven years.
NestA real protocol runs inside a larger one: a W3C working group’s last state, its work accepted as a Recommendation, is a message to the Consortium as a whole.

That outgoing message is a step in the larger protocol. A minority report shows the nesting breaking: it passes on a view inside a group that never reached its final state.

62.4 Why it is a social machine

Social processes can run on a newsgroup or by email: “it works in a write-only medium”. In this model, nobody edits a shared record. As in commerce, one’s view of the state depends on which messages one has seen, and in this model there is no privileged party to ask. Anyone who can fetch the documents can check them.

Chapter 37 argued that the machine loop should be kept closed and joined to the social world only at the edges. Here the loop is the documents, and the edges are the moments a person presses the button.

What happened since

  • 2001. The note’s epilogue records that a Web Services workshop on transactions over the Net surfaced the need for process-flow descriptions.
  • 2004. An update says the Semantic Web Application Platform (SWAP) could now implement these ideas.
  • The pattern won without the vocabulary. Version control systems are paper trails: state is a function of the commits. Anyone with the history can check its integrity, though not whether commits followed the rules.
  • Append-only became an architecture. Event sourcing, where current state is derived from a log of events rather than stored, is section 62.3’s second formulation. It was named and popularised in the mid-2000s.
  • Notarisation became cheap. Signed commits, transparency logs and timestamping services supply the check-and-record step.
  • Rules-in-the-schema remained rare. Most workflow systems hold their rules in code, not in a document the participants can read.
