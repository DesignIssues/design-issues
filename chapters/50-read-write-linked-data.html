Chapter 50

Read-Write Linked Data

2009

Source Read-Write Linked Data, a Design Issues note by Tim Berners-Lee, 2009-10-11. read the original

The short version

Data on the Web can be written back as well as read. Send changes rather than whole files, and the server must refuse loudly when a change no longer applies. A “data wiki” treats every unused address as an empty document ready to fill.

The question

Chapter 49 said how to publish data so others can read it. This note, whose status line reads “Not finished at all”, asks how they write it back. The goal is stated at the outset and is larger than the protocol:

The result is that storage becomes a commodity, independent of the application running on it. Read-Write Linked Data, 2009

Berners-Lee notices, in passing, something surprising about his own archive:

(I actually realize that in 20 year of writing these articles, I haven't written a separate page on that topic! ) Read-Write Linked Data, 2009

The topic is why the Web should be writable. He takes that case as made elsewhere, in Weaving the Web and on the Read-Write Web blog.

50.1 The maxim

The motivation is given as a principle about where editing should happen:

Also, I like the maxim that wherever you have access to information which you have the authority to correct or extend, there should be an easy way for you to do at that place. Read-Write Linked Data, 2009

Not in an administrative interface, not by filing a request: at the place where the information is, by the person entitled to change it. The original Web was built as a collaborative space. Berners-Lee’s word for the ambition is intercreative, which he marks, in jest, with a trademark sign.

50.2 Two ways to write

Linked data lives in documents, each with an address (a URI). A document holds triples: single statements of the form subject, property, value, such as: Joe’s age is 65. The note’s example is a shared calendar, which several people edit at once.

There are two ways to change a document. HTTP PUT uploads a fresh copy of the whole file. A patch sends only the change: remove the triple saying the age is 65, add one saying 66. Figure 50.1 shows what goes wrong with PUT.

The note’s patch is written in SPARQL Update, the editing half of the RDF query language, and sent by HTTP POST to the document’s own URI. A typical patch is a DELETE followed by an INSERT.

Berners-Lee then notices a second use for the same mechanism:

The atomicity of the DELETE,INSERT function can be used to provide various mutual exclusion systems, such as reserving a resource or generating unique sequential numbers, and so on. Read-Write Linked Data, 2009

Atomic means the delete and the insert happen together or not at all. Mutual exclusion means only one party can win. Figure 50.3 shows both uses.

50.3 The data wiki, and the empty document

One extra rule turns the protocol into a writable space, and it is a single change to how absence is reported:

Whenever a client requests a page which doesn't previously exist, instead of returning a "400 Not found" error, the server returns 200 OK, and a valid data document (in RDF/XML or N3) which contains zero triples. Read-Write Linked Data, 2009

The real HTTP code for not found is 404; 400 means Bad Request. 200 OK is the ordinary success reply. RDF/XML and N3 are two ways of writing triples down, one in XML and one in a terser text notation. The note adds that an empty RDF/XML document is not a zero-length file, though an empty N3 one can be.

Every address is then a document that says nothing. A client can read, add a statement and write back, never distinguishing creation from modification: a wiki’s blank page, for data. The cost is that a mistyped address silently becomes a new document, and a crawler cannot tell a real page from an empty one.

50.4 The header with a history

A server must also advertise that it accepts writes, and a footnote explains the header used. Microsoft first built a proprietary write-back protocol, the “Microsoft Frontpage Extensions”, then introduced the MS-Author-Via header so that its clients could switch those off and use WebDAV instead, a standard extension of HTTP for editing files on a server. Most WebDAV servers of the 2000s sent the header, so it was natural to advertise SPARQL there too.

On the letters, Berners-Lee writes only: “Perhaps the MS stands for ‘modification service’.” A second footnote records that the content type was application/sparql-query until 2013, and changed because the code in the field changed first. The specification followed the implementations, which is Chapter 16’s cycle in miniature.

50.5 What is deliberately left out

The note names its own boundaries twice, and both exclusions matter. It does not deal with database-like storage interfaces, atomic transactions, or fine-grained access control. And it is explicit that a space anyone may write to is not what most applications want:

Of course for many real-world applications, one does not want a data wiki in which anyone can write. We therefore need to extend the system to include access control. Read-Write Linked Data, 2009

That extension is Chapter 54, and the order is deliberate. Establish that writing works, then establish who may. A design that starts from permissions tends to produce a system where writing is a privilege; this one produces a system where it is the default and permission is the constraint.

What happened since

  • SPARQL 1.1. SPARQL 1.1 Update and the SPARQL 1.1 Graph Store HTTP Protocol became W3C Recommendations on 21 March 2013. The note’s Followup cites a 2010 draft of the latter.
  • Linked Data Platform. LDP 1.0 became a W3C Recommendation on 26 February 2015, specifying reading and writing linked data over HTTP.
  • Solid. The Solid Protocol, built on LDP, is a specification of the W3C Solid Community Group (version 0.9, 2021), not a W3C Recommendation. It standardised HTTP PATCH with an N3 Patch format; Solid servers commonly accept SPARQL Update as well. The note’s footnote anticipated such a patch language.

Connections

The readable half is Chapter 49, and the access control this note defers is Chapter 54. The patch format and its weak and strong forms are Chapter 45, and the live notification of changes is Chapter 58. The axiom that a URI must not name the result of a changing operation is Chapter 2.

Questions 4

50.1 A whole-document write loses a concurrent change silently. Describe the sequence of events, and say what the loser observes.

50.2 A conditional delete gives you mutual exclusion. Write a reservation using only delete and insert, and say what happens when two clients race.

50.3 The data wiki returns an empty document rather than a not-found error. What does a client gain by never seeing not-found, and what might it lose?

50.4 The maxim says editing should be possible where the information is. Find a place in a system you use where it is not, and say what stands in the way.
