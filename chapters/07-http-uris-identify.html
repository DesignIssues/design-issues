Chapter 7

What do HTTP URIs identify?

2002

Source What do HTTP URIs identify?, a Design Issues note by Tim Berners-Lee, 2002-09-01. read the original

The short version

A web address (an HTTP URI) names a document, not the thing the document is about. The page about a car is not the car. Berners-Lee held this view in 2002 while in a minority on the W3C’s architecture group. He took the rival views one at a time and found a snag in each, from content filters to recommending a war.

His answer for naming things that are not documents is the hash (#): page#car names something described in page. In 2005 the group settled on a compromise that kept his distinction but added a redirect as an alternative to the hash.

The question

Berners-Lee sees a web page showing a photograph of a car. He copies the address from his browser and emails it to a friend: look, the car is a Toyota. The friend clicks the link. The same address comes up, but the page is a table of the car’s weight, length, colour and registration number. Same address, same car, and yet, he argues, the Web did not work. Explaining why left him in a minority on the W3C’s architecture group, as the note’s status line says:

This was a result of my being in a minority with this opinion on the Technical Architecture Group, and yet finding it the only one I could accept. What do HTTP URIs Identify?, 2002

The Technical Architecture Group is the small W3C committee charged with deciding questions about the Web’s overall design. The question put to it was what an HTTP URI denotes, meaning what thing in the world it is a name for. For a decade nobody had needed to ask. Berners-Lee notes that the ambiguity of natural language had concealed the problem so well that the original author of HTTP and its later co-author, who wrote his doctoral thesis analysing the Web, held conflicting ideas of what the terms meant without either noticing. English copes with such vagueness: people say “Moby Dick weighs over three thousand tons”, “Moby Dick was finished over a century ago” and “I left Moby Dick on the beach”, and nobody is misled. The note refuses to take human language as its guide.

What forced the question was RDF, a language for machine-readable statements of the form subject, property, value, in which every name is a URI. A language with well-defined logical properties cannot leave denotation vague. Once people began using HTTP URIs to name ideas such as “colour” or “is a kind of car” rather than pages, two parties could use the same identifier for different things and never discover it.

7.1 An address names a document, in a very wide sense

Berners-Lee’s answer is that an HTTP URI without a fragment (the part after a # sign) identifies a document, in a sense of “document” that is deliberately wide. His own list of what counts includes a poem, an order for ball bearings, a painting, a film, a review of a film, a sound clip, a record of the temperature of a furnace, and an array of a million integers all zero. He is explicit that the word is a placeholder:

I'm going to refer to this as a document, because it needs a term and that is the best I have to date, but the reader should be sure to realize that this does not mean a conventional office document What do HTTP URIs Identify?, 2002

Each such document is one abstract work that can be delivered as many different files, varying by date, format and language (Chapter 10 develops this). What holds the files together is that they have a great deal in common, and that the publisher is the authority on how much variation is permitted.

7.2 The page about a car is not the car

The argument against collapsing the document into the thing it describes is made twice, once on logical grounds and once on social ones. The logical version is short: protocols can now talk about cars as well as about pages, so a reader must either distinguish the car from the page about the car or be hopelessly fuzzy.

The social version goes further:

The process of publishing and reading is a real social process between social entities, not mechanical agents. To be socially responsible, to be able to handle trust, and so on, we must be aware of these operations. The difference between a car and what some web page says about it is crucial - not only when you are buying a car. What do HTTP URIs Identify?, 2002

The test of a shared link

The note turns this into the test that opened this chapter. Every link carries the expectation that the person who follows it gets basically the same information as the person who made it. A JPEG instead of a GIF, a black-and-white copy or, for a reader who cannot see the picture, a well-written description would not have mattered; a table of measurements does. The test fixes what the address names:

The sameness we are after is the sameness of information content. What do HTTP URIs Identify?, 2002

7.3 Eight ways out, and the snag in each

Most of the note sets out the rival views fairly. Take one, which lets the property decide which thing a name means. In the note’s example, saying that http://example.com/albert “is a color photo” is about the representation, that it “used to work down the mill” is about the man, and that it “was taken on a rainy day” is about the original photograph. Now let the page be a review of another web page. “It was written in 2001” could be about the review or the page reviewed, and no property can tell them apart. As the note puts it, anyone can write anything about anything “except those things which might get confused with the document they are writing.”

AlternativeThe snag
The URI identifies the abstract thing, not a documentMany systems already use URIs to name documents, and a URI can name only one thing; this leaves no way to refer to the page itself. Filters list a page friends made with a photograph of the person as containing nudity: the page, not the person. The public already treats two pages on one subject as different works
The owner may define it to mean whatever they likeNothing can be used before asking the owner; defaulting to a page needs closed-world reasoning; a test by GET would mean changing every deployed server
Let logic disambiguatePossible in theory, he says, but a mess; a name would mean different things in different places
Let different properties imply different levelsStumbles when a page is about another page, as with Albert above
Carry extra information alongside the URIA reference then needs more than a URI, so a bare link no longer works on its own
Disambiguate by contextFails once the two communities talk to each other; breaks the rule that a URI names one thing
Change the meaning for the Semantic WebA change that large would need a new URI scheme
Abandon abstract identification entirelyConsistent, he concedes, but RDF could no longer name documents directly

One term in the table needs explaining: closed-world reasoning assumes that anything not stated is false, but on the open Web new information can always arrive.

Berners-Lee calls the owner-defines position tempting and logically consistent, and notes that it is how uuid URIs already work. His objection is engineering rather than philosophy: he cannot use a URI until he has definitive information from the publisher about what it identifies, and there is no moment at which that information reliably arrives.

The consequence, in his words:

Before I recommend the Vietnam War page, I have to be careful I am not recommending the Vietnam War. What do HTTP URIs Identify?, 2002

7.4 A redirect he sketched and left open

The RDF test suite used the address http://www.w3.org/2000/10/rdf-tests/TestSchema/NegativeParserTest to name a kind of software test, not a page. Ask the server for it and it answers 404, not found. It had little choice: HTTP has no way to return a class of tests, only a document. And had it returned a document, nobody could refer to that document without accidentally referring to the class of tests too.

Answering the owner-defines view, he sketches the change to HTTP that would make it workable. A new kind of redirect (a reply meaning “look elsewhere”), which he numbers 343 and names “Abstract Object, please see”, would tell a client that the thing requested is abstract and point at a document about it.

He leaves that avenue open. Chapter 8 records what the Group did: in 2005 it adopted the same mechanism using an existing code, 303 “See Other”, in place of a new 343.

7.5 The most significant piece of punctuation

One answer at the end of the note states the value of a single character:

The hash is not a minor appendage to the URI: It is the most significant piece of punctuation in the whole URIref. The hash adds a whole new level of abstraction and specification! What do HTTP URIs Identify?, 2002

The hash is what lets a document-naming system name things that are not documents, without giving up the guarantee that the part before the hash names a document. This is why he preferred hash URIs to the redirect approach, which was adopted in 2005 and now coexists with them (Figure 7.4). As the same answer ends: “But no one promised the Semantic Web would be boring.”

What happened since

  • A compromise kept his distinction. In June 2005 the Technical Architecture Group resolved the issue it had recorded as httpRange-14, adopting a runtime test rather than a rule fixed in the specification, which is the protocol-operation option in section 7.3’s table. The resolution avoided that option’s objection because a server that does nothing different still answers 200, and so is read as serving a document. It did so using a redirect closely resembling the one proposed here. Chapter 8 is Berners-Lee’s account of the resolution.
  • A note of concession was added to the page itself. By 2006 the page carried a header saying the question had been decided by the Group “in a compromise which I think works quite well”, while the argument itself was left standing.
  • Both patterns survive. Hash URIs and redirect-based URIs are both in wide use, and the split has never closed. Vocabularies that predate the resolution, including Dublin Core and Friend of a Friend, use hashless HTTP URIs for properties, which is the practice this note argues against.

Questions 5

7.1 Your address book does not list a phone number for Ann. Is it safe to conclude she has none? How is the Web like this?

7.2 The note’s first exercise gives an Amazon address for Moby Dick. Does it identify a whale, the novel, a sales page or a string of characters? When did that thing last change?

7.3 Paste http://xmlns.com/foaf/0.1/name into a browser. Did you get a property or a page about it? How could you tell?

7.4 A photograph and a written description of the same painting are served at one address. By the shared-link test, is that one document or two?

7.5 The note ends with exercises. One asks what an address ending magritte.gif identifies: a pipe, a painting, a photograph of a painting, or a file of bits? Give your answer and say which of these the Web can be vague about and which it cannot. (Hint: the note accepts the painting, the photograph and the bits, but never the pipe.)
