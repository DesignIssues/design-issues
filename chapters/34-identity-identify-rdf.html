Chapter 34

Identity: how to identify what in RDF

2008

Source Identity: how to identify what in RDF, a Design Issues note by Tim Berners-Lee, 2008-01-01. read the original

The question

Chapter 32 established that the model is a graph of statements. This note, from 1998, asks the question that immediately follows and is easy to get wrong: when a statement refers to something, what exactly is it referring to? The element in a document, the node in the graph, or the thing in the world?

Berners-Lee opens with the example that shows how invisible the problem usually is:

In most cases it seems obvious to the human reader. The jam jar label text does not (normally) read “jam jar label text” or “jam jar label” or “jam jar” but “jam”. Identity, 1998

People resolve these levels without noticing. Machines cannot.

34.1 Three things a reference might mean

For a marked-up description of a person, Berners-Lee counts the levels. The element has attributes and children. The node has properties. The person has children of quite a different kind. A reference to the same identifier could pick out any of the three.

In an ordinary programming language one would add a character to distinguish them. Here that is not available, since the aim is to do everything possible in the existing language. His solution is to distinguish by the name of the attribute doing the referring, rather than by the value: one form for a literal string, one for the document or fragment referred to, and one for the abstract node.

He notes why the middle form has to exist at all, and the reason is practical:

This is important, as for example it is bits of XML which one digitaly signs, not (in sigend XML) bits of RDF. Identity, 1998

34.2 The clash he records as a bug

A section added in February 2000 is flagged in the original as a bug in the relationship between the two layers, and it is a clean example of the interpretation problem from Chapter 24.

Take a URI with a fragment, pointing into a file that describes a person. If the file is treated as data, the fragment identifies the person. If it is treated as markup, the fragment identifies the element. Since the semantics of a fragment come from the media type, as Chapter 11 requires, the same string means two different things depending on how the document is labelled.

To have a different interpretation of a URI as a function of the notional type of the document belies the fact the point of using XML syntax for RDF was that RDF documents should be XML documents! Of course we embed RDF in regular XML documents. So this distinction is nonsense. Identity, 1998

He explains why the easy fix is not enough. The data layer could simply defer to the markup definition and refer to the node described by the element. But the data layer needs to make statements about documents and elements themselves, and the two must stay distinguishable. His own example is the one that makes it vivid: he might want to state that he wrote a snippet, and it would be tempting to say he is the author of that fragment identifier, but he is not the author of Ora Lassila.

34.3 Identifying things that have no address

The second half is the part that became standard practice, and it begins with a warning about terminology.

RDF treats people as “resources” and in using this terminolgy which normally means tautologically “things with URIs” makes people expect Ora to be synonymous with his web page or his mailbox. This is not of course good design. Identity, 1998

The method he proposes instead is to identify a thing by a property that happens to be unambiguous, rather than by giving it an address it does not have.

He is clear that shortcuts are sometimes needed, and equally clear about what they cost. Where a compound property collapses the two steps, there is no node for the author at all, and the fact that a person wrote the book and has that mailbox must be expressed somewhere else. The schema is a good place, because it makes the expansion evident to any processing machinery.

He also declines, twice and explicitly, to settle which properties should be treated as identifying, calling it a rat hole that is not core to the discussion. That restraint is the same one as Chapter 22: the mechanism can be specified without settling the philosophy.

What happened since

  • The mechanism was standardised. Inverse functional properties, which formalise “no two things share this value”, are part of OWL, a W3C Recommendation of February 2004, and identifying a person by a hashed mailbox became the standard practice in the Friend of a Friend vocabulary.
  • The fragment clash was resolved by media type. Registering data-carrying media types with their own fragment rules settled which interpretation applies, which is Chapter 11’s axiom doing the work it was designed for.
  • The rat hole stayed open. Which properties may be treated as identifying is still decided per vocabulary and per application, and incorrect assumptions remain a standard source of bad merges.
  • The privacy cost arrived later. Identifying people by an unambiguous property makes records joinable across datasets by design, which is useful for integration and is exactly the mechanism Volume VII worries about.
