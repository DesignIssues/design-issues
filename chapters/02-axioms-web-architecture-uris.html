Chapter 2

Axioms of Web architecture: URIs

1996

Source Axioms of Web architecture: URIs, a Design Issues note by Tim Berners-Lee, 1996-12-19. read the original

The short version

A web address looks like the location of a file on somebody’s disk. The Web’s design treats it as something simpler and stronger: an identifier that means the same thing to everyone, given to everything worth mentioning.

This note sets out ten rules about those identifiers. Most of them are the reason a link can be sent to anybody and still mean the same thing at the other end. One, that following a link must change nothing, showed its worth in 2005, when a program that followed every link on a page deleted data on sites that had broken it.

The question

A link sent to the other side of the world takes its reader to the same thing. Nothing in the network guarantees that. A handful of rules do, rules that are, in the note’s words, “implied or stated in various specifications or in some cases simply part of the folk law of how the Web ought to be used.” Berners-Lee gathered them in December 1996 and revised the note until at least 2009. The rigour, he says, is borrowed:

Terms such as “axiom”, and “theorem” are used with gay abandon rather than precision as this not a mathematical treatise. Axioms of Web Architecture: URIs, 1996

2.1 What is on the Web

The note opens with a definition:

An information object is “on the web” if it has a URI. Objects which have URIs are sometimes known as “First Class Objects” (FCOs). The Web works best when any information object of value and identity is a first class object. If something does not have a URI, you can't refer to it, and the power of the Web is the less for that. Axioms of Web Architecture: URIs, 1996

Membership of the Web is a property of naming, not of storage, protocol, or format. Later arguments in this book about what deserves a URI, from government datasets in Chapter 53 to a person’s own data in Chapter 54, start from this sentence.

2.2 Anything can have a URI; anything that matters should

Two claims are numbered zero: they are prior to the rest.

Axiom 0, universality 1. Any resource anywhere can be given a URI. (A resource here is anything that can be named.)

Axiom 0a, universality 2. Any resource of significance should be given a URI.

The first is a claim about the design, and Berners-Lee argues for it in three steps. (1) There is no limit to the length of a URI. (2) Every URI starts with a scheme: the word before the colon, such as http or mailto, which says which rules apply to the rest. (3) So any identifier can be turned into a URI by writing it as printable characters behind a new scheme name, as ISBN: could be for book numbers.

The second is an instruction, and ten years later it became the first rule of Linked Data, the practice of publishing data with a URI for every thing (Chapter 49).

Axiom 1, global scope follows: whoever a URI is given to, and wherever, it has the same meaning. It needs no enclosing context.

2.3 The owner decides what a URI means

Axiom 2 comes in two parts because the first is vague and the author knows it. Axiom 2a, sameness: a URI will repeatably refer to “the same” thing. The quotation marks are his. Axiom 2b, identity settles it:

the significance of identity for a given URI is determined by the person who owns the URI, who first determined what it points to. Axioms of Web Architecture: URIs, 1996

The Web does not define what a URI means. The owner does, within bounds the scheme sets:

The scheme, if you like, imposes constraints within which the owner of a URI is free to define identity. Axioms of Web Architecture: URIs, 1996

Berners-Lee credits the principle to Bob Scheifler and others: define mechanisms wherever possible without defining policy. Whether a page never changes, changes daily, or comes in several formats is the owner’s business.

He then sets a moral limit on that freedom. A server often knows who is asking, and could send each reader something different.

Unless it is clearly indicated on the page (or using a future protocol), to return differing information for the same URI must be considered a form of deception. Axioms of Web Architecture: URIs, 1996

The mechanism he names is the HTTP Vary header, a line in the server’s reply saying that it depends on something in the request, such as the reader’s language. Undisclosed variation, he adds, “also of course messes up caches”.

2.4 When two URIs are one URI

The rule is unqualified: two URIs are the same if and only if they are the same character for character. Everything else is equivalence, not identity, and whether a program can tell two strings are equivalent depends on what it knows. Some equivalences follow from the standards: the Domain Name System (DNS), which turns names like example.org into network addresses, ignores case. Others need knowledge of one particular site. Figure 2.1 sets the cases side by side.

Canonicalization means rewriting a URI into one standard spelling. Because equivalence depends on knowledge, no single rewriting suits everyone, and Berners-Lee draws the consequence for cryptography:

There is, therefore, no definitive canonicalization algorithm for URIs. Generic URI handling code should handle URIs as case-sensitive character strings. It is not recommended that, for example, encryption and signature algorithms attempt to canonicalize URIs before signature, because of the arbitrariness of any attempt to define a canonicalization algorithm. Axioms of Web Architecture: URIs, 1996

2.5 Opacity: a URI is a sealed label

The opacity axiom is the easiest to break, because the string is right there to be read. To dereference a URI is to use it to fetch the thing it names. Otherwise, a program should treat the URI as a sealed label.

Axiom, opacity of URIs. The only thing a URI may be used for is to refer to an object. When not dereferencing, one should not look inside the string to gain other information.

Even when fetching, the client reads only the scheme and the authority (the part after //, usually a host name) to decide which server to contact. The rest is opaque to it.

The query string, the part after a question mark that a search form fills in, is an exception: the client constructs it. It should still stay opaque to proxies, the servers between reader and site that pass requests on and often cache copies of the replies. Figure 2.2 shows who may read what.

The note’s example is reading .html at the end of a URI as its media type, the label (such as text/html) that says what kind of file something is. The architecture guarantees no such convention: a server mapping names from an older database may produce .html by coincidence. Such information belongs in the protocol, which is what much of the HTTP header set exists to carry.

Some caches of the time broke opacity by refusing to store any URI with a question mark. Authors then added question marks to avoid caching, a convention the note warns harms sites whose query pages are perfectly cacheable.

2.6 GET, and the price of getting it wrong

Every HTTP request carries a method. Following a link sends a GET (show me this); submitting an order sends a POST (do this). A side effect is anything a request changes beyond fetching a page: an order placed, a record deleted. In 2005 a program from Google showed what the rule below protects (see What happened since).

The note derives the rule from Axiom 2a: if a URI repeatably means “the same” thing, an earlier result can be reused. Of that repeatability it says, “It leads to the whole concept of the Web as an information space rather than a computing program.” Its example of what a GET must never do:

It is wrong to represent the user doing a GET as committing to something or putting themselves on a mailing list Axioms of Web Architecture: URIs, 1996

Axiom. In HTTP, GET must not have side effects.

Axiom. In HTTP, anything which does not have side effects should use GET.

A search form only asks for information, so it should use GET, and its result then has a URI that can be bookmarked or sent on. Ignoring the first axiom, the note warns, can open a serious security hole. Figure 2.3 shows why.

The first axiom is about safety; the second is about universality. A link carries a URI and not a method, so it can only say GET. If searches used some third method, a search result could not be bookmarked or linked to.

2.7 Not the only space

Axiom 3, non-unique: URI space need not be the only universal space. To the objection that no space should be privileged, the answer is that none is: any rival universal space could contain URI space as a subset, and the two could interoperate.

This is Chapter 1’s test of independent invention, applied to the Web’s own foundation. The worked example is the international telephone system, mapped both ways, as Figure 2.4 shows.

In principle any Web object could be dialled from a telephone, and any telephone pointed to from a hypertext document. The conclusion he cares about:

So, on this last axiom rests not specifically the operation of the web, but its acceptance as a non-domineering technology, and therefore our trust in its future evolvability. Axioms of Web Architecture: URIs, 1996

The telephone returns later, to explain the slashes that mark levels of a URI’s hierarchy. As a URI, +1 (617) 253-5708 becomes phone://1/617/253-5708, and with that number as the base, a local number is the relative 861-5000. The double slash, the note says, came from the Apollo Domain network file system, which added an extra slash when extending Unix-style file names across a network; Microsoft’s NT networking uses \\ the same way. It calls it a myth that // must introduce a domain name.

2.8 Schemes promise different things

The note ends with a table comparing the limits different schemes set. Three rows are given here, in its own words with typing slips corrected. “Reuse” is whether a URI may later be given to something else; “(no dereference)” marks URIs that give nothing to fetch.

httpGeneric document as defined by publisherdefined by publisherdefined by publisher
sha1:sequence of bitsmathematically extremely unlikely(no dereference)

For http almost everything is left to the publisher. A sha1: URI is computed from the bits themselves, so uniqueness is a matter of mathematics, not promise. Reassigning a mailto: address is a social offence rather than a technical one.

What happened since

  • The syntax was standardised. RFC 3986, published in January 2005 as STD 66, replaced RFC 2396 and in practice superseded the informational RFC 1630 that Berners-Lee wrote in 1994 and quotes here. Character-for-character identity and the limits on canonicalization survive in it.
  • Vary stayed a caching tool. The Vary header was defined in HTTP/1.1 (RFC 2068, January 1997) and remains in RFC 9110. It tells caches which parts of a request affect the response.
  • The GET rule was given a name and a test case. Safe methods are specified in what is now RFC 9110, of June 2022. The Google Web Accelerator, released in May 2005, fetched the links on a page in advance. In applications that used plain links for destructive actions, it followed the deletion links and deleted data.

Connections

Questions 4

2.1 A company invents a new numbering scheme for its products. Using the three steps of section 2.2, show how its numbers become URIs. What would break if URIs had a 100-character limit?

2.2 A site uses links of the form /delete?id=7 to remove records. What happens when a browser prefetches every link on the page? Which axiom did the site break, and how should the page have been built?

2.3 Two sites link to the same URI, one believing it names a company and the other its home page. According to Axiom 2b, who decides which is right?

2.4 A news site shows each reader different stories at the same URI, chosen from their history. By the note’s standard, is that deception? What would make it honest?
