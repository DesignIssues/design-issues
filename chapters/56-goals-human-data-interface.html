Chapter 56

Goals for A Human-Data Interface

2019

Source Goals for A Human-Data Interface, a Design Issues note by Tim Berners-Lee, 2019-07-07. read the original

The question

Written as a note in 2010 and extended into a history in 2019, this is the only chapter in the collection about building software rather than specifying it. Its subject is a gap Berners-Lee names precisely:

There was, in 2010, an unfulfilled need for a powerful, friendly program to interact with data on the web. Goals for a Human-Data Interface, 2010

The diagnosis of why the document Web spread and the data Web did not is the most useful paragraph in Volume VI for anyone building anything.

56.1 What the document Web had that the data Web lacked

The document web spread by the simple method of people copying the source of each other's web pages, and getting the instant gratification of being able to see one's work in a web browser, and indeed to pass on the URL to friends and family. Goals for a Human-Data Interface, 2010

Copy, change, look, show someone. Four steps, each immediate. Against that Berners-Lee sets what the early data projects offered:

However, most of the initial Semantic Web projects (around 2000) used back-end machines with no generic user interface. Researchers, to explain data to each other, tended to use circles-and-arrows diagrams of the graphs. These, though are hopeless -- very inefficient uses of space -- when it comes to displaying data to a normal user. Goals for a Human-Data Interface, 2010

That judgement is worth pausing on in a book that has used circle-and-arrow diagrams throughout. They are good for explaining a mechanism to someone who wants to understand it, and hopeless for showing someone their address book.

What ordinary users expect instead is named concretely: an address book application, a spreadsheet, a music library. Lists of properties, tables, forms, faceted views. And the note concedes what those have that the data Web did not:

The different apps are islands, with no links between them, but they do give a user experience which users seem to use. Goals for a Human-Data Interface, 2010

56.3 Two design principles

The first is stated as a prohibition, and it is the rule most data tools break:

While RDF buffs may revel in the URIs of nodes, users do not. User experience should not include naked URIs. Goals for a Human-Data Interface, 2010

Everything in Volume II argued that identifiers are the foundation. This says the foundation must not be visible. The two are consistent: a person sees a name and a picture, and the identifier is what makes the software able to find them.

The second principle is what makes the first possible. The vocabulary is used as the bridge between a mathematical graph and something displayable: it says what a thing is, what to call the relation, what may be edited. Without it the interface has nothing but circles and arrows, which is where the note started.

56.4 The audience, and the ambition

The target user is described with unusual care, and the choice explains the whole design:

A spreadsheet user is an interesting example: they spend a lot of effort in some cases getting the computer to do what they want, and work at quite a high level of abstraction. In fact they tend to pour their energy into a spreadsheet creating tables and relations about which the computer itself does not understand the semantics. Goals for a Human-Data Interface, 2010

Spreadsheet users are already modelling the world. They already build relations, at a high level, with enormous effort. What they lack is any way for the machine to know what those relations mean, and therefore any way to share them except by sending the file.

The goal that follows is one sentence and is the most demanding requirement in the book:

A major goal is that the software should allow users to be as powerful as possible without having to write their own code. Goals for a Human-Data Interface, 2010

What happened since

  • The program became infrastructure. The library it grew into underlies Solid applications, and its panes and widgets are how most Solid interfaces are built, which is a longer life than most research tools.
  • The no-code ambition arrived elsewhere. Tools that let people build relational applications without writing code became a large industry through the 2010s, reaching the audience section 56.4 names, without linked data underneath.
  • The naked URI rule is still broken everywhere. Data tools routinely show identifiers to users, and the interfaces that do not are usually the ones people actually use.
  • Query by example did not spread. Finding a shape and asking for everything like it remains rare outside specialist tools, though it is what most people want when they say they want to search.
