Chapter 69

Client-Side Certificates

2015

Source Client-Side Certificates, a Design Issues note by Tim Berners-Lee, 2015-03-28. read the original

The short version

A person proves who they are to a website with a password, which is sent to the site and stored there. The browser could instead keep a private key, give the site the matching public key, and sign a random challenge from the site, so the secret never leaves the person’s machine. Berners-Lee asks browsers to make this easy, and to show which identity is in use.

The question

The last of the four notes of March 2015 asks why the Web authenticates one side of a conversation well and the other side badly. Berners-Lee grants the case for anonymity before making his argument:

When you are browsing the news and interacting with incoming information, you may be happy not to be identified or even keen to be anonymous. There are times, though, when you want to be well identified yourself, whether moving money around at the bank or chatting with friends. Web Security - Client side certs, 2015

The question is why, in those cases, we still use passwords.

69.1 The comparison

A client certificate is, in the note’s words, one of the “Public Key certificates used by the browser to authenticate the user”: that is, to prove to a site who the user is. It rests on a key pair: a private key that stays with its owner, and a public key that anyone may hold, which can check a signature made with the private key but cannot make one.

The note’s central passage lays out everything wrong with a password simply by describing what one is:

People call client certificates unfashionable and hard to use, he notes, yet say they hate passwords. His summary:

Public key cryptography is a really wonderful gift from mathematics. We should be making better use of it. Web Security - Client side certs, 2015

69.2 Six things a browser would have to do

The note is unusual in the collection for being a feature specification.

FunctionWhat it means for a person
Create a key pair and keep it locallyOn the laptop, phone or a hardware device
Choose which identity to use for a site, and remember itWith enough shown to tell one from another
Show who the user is logged in as, near the addressBeside where the site’s own identity is shown
Log outDrop the credentials, optionally choose another identity
Manage those preferencesEditable when the user gets muddled
Back up and synchronise keys, selectivelyMarked for extra credit; some keys should never leave one machine

The third reveals the asymmetry most sharply. A browser shows who the site is, prominently, and shows nothing about who the user is being.

The complaint about how identities are presented is the kind of detail that decides whether a feature is usable:

Make sure the certificates are labelled in a way that makes them distinct -- not all just labelled with my name (duh!). Web Security - Client side certs, 2015

What web developers need

The note’s further points include:

  • Label each certificate by the party that signed it or, where it is a WebID, by the domain of the WebID.
  • Give a web app a way to find out which certificate the user chose to reach a given resource.
  • When a page makes a new key with <keygen>, the HTML element that asked the browser to generate a key pair, fire an event or Promise so the page can carry on with its workflow.

69.3 The refusal

The note ends with a section titled “Just do it”, directed at a habit rather than at a technology:

Many of the things which I hear people wish for, mentioned in this article or not, are often put out into the conversation but with a sigh and the caveat that "It would be nice, but that's not how browsers work". Web Security - Client side certs, 2015

His answer is an observation about the material rather than an appeal:

The bowsers are code, in many cases open source code. They are being changed all the time. Unlike a decade ago, they are also being upgraded all the time, because of the need for security-related bug fixes, and so a new idea can be tried out in browsers really fast. Web Security - Client side certs, 2015

The closing instruction is four words: “Let’s just change it.” It reads as optimism or exasperation, and possibly both.

69.4 Why this closes the set

The four notes together make one argument. Each finds a place where the machine’s model of a social arrangement is narrower than the arrangement:

ChapterWhat the system assumesWhat is actually true
66Trust flows only from a certificate authorityPeople trust others because they met them, know them or work for them
67Security is marked in the address, by the s in httpsEncryption is a fact about the connection, not the name
68A party is a domain nameA party can be a path within a site
69Only the site needs strong proof of identityThe user needs it too, at the bank or among friends

In each case the narrowing is invisible because it has been there since the beginning.

What happened since

  • The mechanism was replaced rather than fixed. WebAuthn, a W3C Recommendation of March 2019, gives the properties of the bottom lane of Figure 69.1.
  • The interface requirements were met. Passkeys, announced by Apple, Google and Microsoft in May 2022, supply most of what section 69.2 lists, with the operating system rather than the browser doing the work. Synced passkeys do leave the machine, which the note warns against for some keys.
  • The key element the note asks for is still missing. As of 2026, no major browser shows, beside the site’s identity, which identity the user is currently presenting.
  • The old mechanism was removed. <keygen> was removed from Chrome in version 57 (March 2017) and from Firefox in version 69 (2019), before its replacement was widely usable.
