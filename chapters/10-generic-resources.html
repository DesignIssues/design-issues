Chapter 10

Generic resources

1996

Source Generic resources, a Design Issues note by Tim Berners-Lee, 1996-03-01. read the original

The question

This note is older than most of Volume II and is presupposed by all of it. Written in 1996, it carries two status lines added at different times, and the second is unusually insistent:

This is an important axiom of web design, which must be understood for new designs to use URIs and HTTP properly. Generic Resources, note added 2000

The question it answers is what a URI identifies when the thing identified does not have one fixed sequence of bits. The answer supplies the notion of “document” that Chapter 7 depends on, and the reason content negotiation exists at all. Berners-Lee records that this was the thinking behind HTTP content negotiation in 1992.

10.1 A ladder, not a pair

The note opens with a distinction and immediately refuses to let it be binary. A resource may correspond to exactly one possible bit stream: the text of an Internet RFC is the example, and it will always have the same checksum. Or it may be generic, well specified as a concept but not specified closely enough to fix the bits.

The illustration is a ladder of four rungs, each more specific than the last: the Bible; the Bible in the King James Version; that version in English; and one particular ASCII rendering of it. Each rung may have a URI of its own, and the relation between rungs is genericity.

Ownership decides where on the ladder a given URI sits:

Each resource may have a URI. The authority which allocates the URI is the authority which determines wo what it refers: Therefore, that authority determines to what extent that resource is generic or specific. Generic Resources, 1996

This is Chapter 2’s identity axiom applied to a particular question, and it is why the answer to “how much may this URI’s content vary?” is always “ask the publisher”.

Berners-Lee is careful that this is not a design decision he is making:

This model is more of an observation of a requirement than an implementation decision. Multilevel gnericity clarly exists in all our current life with books and electronic documents. Adoption of this model simply follows from the rule that Web design should not arbitrarily seek to constrain life in general for its own purposes. Generic Resources, 1996

10.2 Four dimensions

The useful empirical claim of the note is that genericity, for electronic resources, turns out to run along a small number of axes, and that the number being small is itself significant.

The inference he draws from the smallness is a design instruction:

The fact that there are such a small number of dimensions currently apparent sugests that Web software should handle them individually in its interface with the user, even though the architecure should handle them as a single concpet. Generic Resources, 1996

One mechanism underneath, four controls on top. The architecture negotiates; the interface offers a language menu.

10.3 Derivation is not genericity

A short section makes a distinction that is easy to lose. When a document is translated, one language version may have been the source, but it need not have been: a specific version may derive from unrelated or multiple sources. The derived-from relation is therefore interesting and separate, and Berners-Lee declines to fold it into genericity.

The discipline matters because the two relations answer different questions. Genericity answers “is this an acceptable thing to serve for that URI?” Derivation answers “where did this come from?” A system that conflates them will serve a translation as though it were authoritative.

10.4 Saying it in metadata

The rest of the note is proposals, and they are useful mainly as a record of what was being attempted. Two kinds of statement are wanted: which dimensions a URI is generic in, and how two resources are related along a dimension.

The first was proposed as a vary= field in an HTTP URI: header, written as URI: http//foo.com/bar/baz vary=time,language. Berners-Lee notes that this is a statement about the relationship between the URI and the resource, and points back to the quality-of-service argument of Chapter 3.

The second was proposed as typed links, and later, in a section added in September 2000, as an RDF vocabulary. That vocabulary defines classes for invariance, TimeInvariant, LanguageInvariant, ContentTypeInvariant, and Fixed as a subclass of all three, together with properties such as isLanguageSpecificVersionOf. Berners-Lee notes that the ontology does not cover the target-medium dimension, which is the one HTTP never negotiated either.

What happened since

  • Three dimensions shipped; the fourth went elsewhere. Content negotiation for media type, language and encoding is specified in what is now RFC 9110, of June 2022. Target medium was never negotiated in HTTP and was handled by CSS media queries instead, first a W3C Recommendation in June 2012.
  • The vary= proposal became something narrower. The Vary response header exists, but it describes which request headers affect the response for cache purposes. It does not state the publisher’s commitment about how much a resource may vary, which is what this note asked for.
  • Negotiation lost ground to distinct URIs. Publishers largely chose to give each language and each format its own address, with rel="alternate" links between them, because separate URIs can be linked to, indexed and cached. That is the ladder of section 10.1 made explicit rather than negotiated.
  • The genericity ontology was not widely adopted. The vocabulary at w3.org/2006/gen/ont is little used. The distinctions it draws are now usually made informally, or not at all.

Connections

Questions 4

10.1 The note claims genericity is observed rather than designed. Give a kind of resource whose variation does not fit any of the four dimensions, and say whether it is a fifth axis or a case of derivation.

10.2 Publishers largely chose separate URIs over negotiation. State the strongest argument for negotiation that this outcome discards.

10.3 A URI is Fixed in the sense of section 10.4. What does that commit the publisher to, and what could a client safely do that it otherwise could not?

10.4 Explain why conflating derivation with genericity would let a system serve a translation as authoritative, using an example.
