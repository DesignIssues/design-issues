Chapter 68

The Same Origin Policy - Origin Granularity

2015

Source The Same Origin Policy - Origin Granularity, a Design Issues note by Tim Berners-Lee, 2015-03-28. read the original

The question

The third of the 2015 notes opens with a question that sounds abstract and turns out to govern how every website is laid out:

You can't discuss authentication of parties without discussing what constitutes a party. Granularity of web sites, trust and the Same Origin Policy, 2015

The browser’s answer is the domain name. Berners-Lee’s objection is that the identifier already contains a second hierarchy, which the browser ignores, and that ignoring it forces the wrong shape on everything built above.

68.1 Two hierarchies, one used

That privacy consequence is stated by Berners-Lee in terms that make the stakes concrete:

It reveals to anyone looking a reader's DNS requests, not just that the reader is going to the innocuous camps.org site but to the web site of notorious activist Jane Smith. The reader's privacy is being whittled away a little more. Granularity of web sites, trust and the Same Origin Policy, 2015

68.2 Why the path hierarchy was already there

The note’s strongest point is historical. Making the path hierarchy visible was a deliberate early decision, and it already carries delegation everywhere except in the browser’s security model.

Berners-Lee lists what the file system provides when addresses map onto it: permissions inherited down a tree, and access rules at a point in the tree governing everything below it and nothing above. He calls this very useful, and gives the reason:

It allows things to be embedded within the system. It allows a [reverse] proxy within the web site to map arbitrary branches of the tree onto internal or external services. Granularity of web sites, trust and the Same Origin Policy, 2015

68.3 The case that shows the cost

The worked example is a board using an outside discussion tool, mounted inside its own site. What one wants is for the outside tool to be unable to read the board’s papers, which sit elsewhere in the same tree.

The browser cannot express that. So the tool is given a subdomain, or it is hosted by its supplier entirely, and Berners-Lee names what has been lost:

where there in no reference at all to the actual trust structure, and the camps.org board have to trust that any AcmeDiscss.com scripts can read their data. Granularity of web sites, trust and the Same Origin Policy, 2015

The arrangement that actually obtains, the tool’s supplier hosting the board’s pages under the supplier’s own domain, inverts the relationship: the party being engaged for one small purpose becomes the party the data belongs to.

68.4 A general caution about identifiers

One sentence generalises past the argument, and it is a rule worth carrying into any addressing scheme:

In general, it is dangerous when the URI is made opaque in any way. Sometimes it is necessary -- the best of many bad choices. Granularity of web sites, trust and the Same Origin Policy, 2015

He then names the two places where opacity was accepted, and the second is striking. The letter discussed in Chapter 67 is one. The other is the domain name itself, which he calls the massive opaqueness, because it is the path by which the user’s trust in the session travels at all.

The recommendation that closes the note is correspondingly broad: investigate ways of letting trust pass down the path hierarchy as well as the domain, and move away from reliance on domain names generally.

What happened since

  • The boundary moved, repeatedly. Site isolation work from 2018 onward refined what counts as a party, introducing distinctions between an origin and a registrable domain, which is the symptom Chapter 67 names: a boundary that can never be placed correctly.
  • Path-based boundaries were never added. Trust still derives from the authority alone, so the contortion of Figure 68.1 is still required.
  • The privacy leak was partly closed. Encrypted name lookup, standardised from 2018, hides requests from the network, though the server name is still visible in most connections.
  • Embedding a supplier’s tool under your own tree stayed impossible. Third-party components are hosted by their suppliers or served from a subdomain, which is the arrangement section 68.3 describes.
