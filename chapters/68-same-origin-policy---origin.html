Chapter 68

The Same Origin Policy - Origin Granularity

2015

Source The Same Origin Policy - Origin Granularity, a Design Issues note by Tim Berners-Lee, 2015-03-28. read the original

The short version

Web pages carry small programs, called scripts, that run in the browser. A script from one site must not read another site’s data, so the browser needs a rule for what counts as one site.

That rule is the Same Origin Policy: two addresses are one party when they share an origin, meaning scheme, host name and port. In practice the host name, such as camps.org, decides.

Berners-Lee’s complaint is that the path, the slashed part after the host name, is a hierarchy too. The browser ignores it, so sites must contort their addresses.

The question

The third of four related 2015 notes opens with a question that turns out to govern how every website is laid out:

You can't discuss authentication of parties without discussing what constitutes a party. Granularity of web sites, trust and the Same Origin Policy, 2015

The browser’s answer is the domain name.

68.1 Two hierarchies, one used

A web address contains two trees. The host name, also called the authority, is a tree read right to left: org, then camps.org, then the subdomain campsunshine.camps.org. The path, everything after the first single slash, is a tree read left to right.

The browser uses only the first. Berners-Lee notes it even ranks names within it: an application at mit.edu is assumed able to reach data from scripts at csail.mit.edu, not the reverse. The path gets no such treatment, so giving Jane Smith her own scripting space means rewriting her address.

Relative links matter because they let a family move its pages to a home server, or work offline. The fourth cost is the one nobody intends. Before fetching a page, the browser makes a DNS lookup, asking which machine serves the host name, usually unencrypted; the path travels inside the encrypted connection.

It reveals to anyone looking a reader's DNS requests, not just that the reader is going to the innocuous camps.org site but to the web site of notorious activist Jane Smith. The reader's privacy is being whittled away a little more. Granularity of web sites, trust and the Same Origin Policy, 2015

68.2 Why the path hierarchy was already there

The note’s strongest point is historical. Making the path hierarchy visible with the slash was a very early decision, and servers use it to hand out control.

In a classic Apache server, addresses map onto Unix folders, and permissions are inherited down the tree. An .htaccess file in a folder controls everything below it, nothing above. A reverse proxy, the site quietly passing one branch of its addresses to another service, builds on this. Berners-Lee calls it very useful:

It allows things to be embedded within the system. It allows a [reverse] proxy within the web site to map arbitrary branches of the tree onto internal or external services. Granularity of web sites, trust and the Same Origin Policy, 2015

68.3 The case that shows the cost

The camps.org board proxies an outside meeting tool into https://camps.org/board/AcmeDiscss/stuff. Its papers sit at https://camps.org/board/papers, under the same parent. The tool’s scripts should not read the papers, but to the browser both are one origin.

So the tool gets a subdomain, or its supplier hosts it, and Berners-Lee names what is lost:

where there in no reference at all to the actual trust structure, and the camps.org board have to trust that any AcmeDiscss.com scripts can read their data. Granularity of web sites, trust and the Same Origin Policy, 2015

68.4 A general caution about identifiers

One sentence generalises to any addressing scheme:

In general, it is dangerous when the URI is made opaque in any way. Sometimes it is necessary -- the best of many bad choices. Granularity of web sites, trust and the Same Origin Policy, 2015

He names two accepted opacities. The s in https, discussed in Chapter 67, is one. The other is the domain name itself, which he calls the massive opaqueness, because it is the path by which the user’s trust in the session travels at all.

The recommendation that closes the note is correspondingly broad: investigate ways of letting trust pass down the path hierarchy as well as the domain, and move away from reliance on domain names generally.

What happened since

  • The boundary moved, repeatedly. Chrome turned on Site Isolation by default on desktop in 2018, keyed on the registrable domain (such as camps.org) rather than the full origin: the symptom Chapter 67 names, a boundary that can never be placed correctly.
  • Path-based boundaries were never added. Trust still derives from the authority alone, so the contortion of Figure 68.1 is still required.
  • The privacy leak was partly closed. DNS over TLS (RFC 7858, 2016) and DNS over HTTPS (RFC 8484, October 2018) encrypt the lookup. The server name is still sent in the clear when the connection opens, unless Encrypted Client Hello is used.
  • Embedding a supplier’s tool under a site’s own tree stayed impossible. Third-party components are hosted by their suppliers or served from a subdomain, which is the arrangement section 68.3 describes.
