Chapter 6

Levels of Abstraction: Net, Web, Graph

2007

Source Levels of Abstraction: Net, Web, Graph, a Design Issues note by Tim Berners-Lee, 2007-10-23. read the original

The short version

An abstraction is a way of working that lets someone forget the machinery underneath it. The Web stacks four of them: cables, then computers, then documents, then the things the documents are about. A user may ignore every lower layer except in two cases: when something breaks, and when trust is in question. For trust, the web address itself says who is responsible.

The question

Nine years after the survey of Chapter 5, Berners-Lee wrote this note with an unusually frank status line: it was written, he says, in response to another round of circular discussions of Web architecture. It is short, it contains no new mechanism. It supplies a reason for the layering.

The claim is that the Web’s layers are not layers of technology. They are layers of social responsibility, and each one borrows the accountability of the one beneath.

6.1 Three refusals

The note advances by rejecting three answers in turn, naming each step by what no longer has to be thought about.

Not the wires

When computers were connected by telephone lines, one ran a program to connect to a particular machine, and to reach a third machine one had to know how to drive the second. Mail travelled by machines calling each other at night, and addresses named the route: Berners-Lee gives the example timbl@mcvax!cernvax!cernvms, in which each ! separates one machine on the path from the next.

The Internet removed the wires from the picture. Two inventions did it: DNS, which names computers, and TCP/IP, which breaks messages into packets and finds the route itself.

Not the computers

That power was not usable by ordinary people until the Web, whose insight he states as a slogan: it is not the computers which are interesting, it is the documents. The user is then in a web of interconnected documents and need not think about the protocols underneath.

Not the documents

The Semantic Web’s insight is the same move again: it is not the documents which are interesting, it is the things they are about. A reader of a page about a protein is usually interested in the protein. In business and science the customers, products, genes and proteins are the objects of interest, and a good browser would show information about the thing, merged from many sources. What the user sees is then a web of connections between things, which the note illustrates with a chain: this person is a customer who made this order which includes this item which is manufactured by this facility, and so on.

6.2 The two exceptions

Each layer can be ignored except in two cases, debugging and trust. Figure 6.2 sets out what each question looks like at each layer.

The first exception is debugging. When something fails, the user must be able to lift the hood and determine at which layer it failed: whether the connection broke locally or in the middle of the network, whether the URI was wrong or the server erred, whether the document was fetched correctly but lacked the data.

The second exception is trust, and Berners-Lee gives it more weight:

The information you are browsing comes from a particular server, whose name has registered against a particular person or organization. The trust you put in that information is related to who that organization is. It is the serving organization which is responsible for keeping the URIs you bookmark today alive tomorrow -- and some are better at it than others. Phishing attacks succeed when people are fooled into thinking it is an organiztion you trust when it isn't. Levels of Abstraction: Net, Web, Graph, 2007

A phishing attack is a fake page, usually reached from a deceptive email, that poses as an organisation the reader trusts in order to collect passwords or payment details. It works precisely by attacking the trust exception. Provenance, the record of where a piece of information came from and who stands behind it, is therefore the one thing a user cannot be allowed to forget.

6.3 The seams are visible in the identifier

Each join between layers is legible in the URI itself. In 

http://acme.example.com/products/machin/truc

the owner’s domain name, acme.example.com, is part of the name of the document, so the company is identifiably responsible for supporting that document. In 

http://acme.example.com/products/machin/truc#part3

the name of the document is part of the name of the thing. The part after the # picks out something within or described by the document, and everything before it is the document’s own name.

The thing is identified as the thing described by that document: a gene as defined in the Gene Ontology, a shared public catalogue of gene names, a protein as defined in a particular taxonomy, a citizen as defined in a particular glossary. A thing may have many URIs, but a URI of this form says whose account of the thing is being used.

Berners-Lee adds a parenthesis that has become a chapter of its own. Since 2005 there have been URIs for things not explicitly bound to a document, which require the server to name a suitable document at request time. He calls this more complicated and moves on. Chapters 7 and 8 are what lies behind the parenthesis.

6.4 The conclusion, which is about people

The web of things is built on the web of documents, which is built on the web of computers controlled by Domain Name owners, which itself is build on a set of interconnected cables. This is an architecture which provides a social backing to the names for things. Levels of Abstraction: Net, Web, Graph, 2007

The note spells out what that social backing buys. Because each layer rests on a named party, people can find out the social side of the things they deal with, not only the raw data: provenance, trust, persistence, licensing and appropriate use. And when things do not work, they can work out what has gone wrong, because the layering makes clear who is responsible.

Its central sentence:

The value of this architecture is that each layer leverages the social components of the lower layer's architecture. Levels of Abstraction: Net, Web, Graph, 2007

Read from the bottom up, as in Figure 6.3, the chain of borrowed trust runs like this:

  1. A registry binds the domain name to a party.
  2. So the domain owner is accountable for what its computers serve.
  3. So a document published under that domain is trustworthy to the degree the owner is.
  4. So a name for a gene, built from that document’s name, is trustworthy to the degree the document is.

Take away the accountability at any level and the levels above lose their footing. This is why Chapter 3 concluded that naming is a contractual matter.

What happened since

  • The trust exception failed in the field. Extended Validation (EV) certificates, a costlier kind of security certificate issued only after checking the organisation’s legal identity, were the mechanism for showing a user which organisation stood behind a page, typically as a company name beside the address bar. Chrome 77 (September 2019) and Firefox 70 (October 2019) removed that prominent EV display, having concluded that users did not act on it.
  • The parenthesis became a decade of argument. The Technical Architecture Group’s resolution of the issue known as httpRange-14, in June 2005, established the 303 redirect convention for URIs denoting things that are not documents: asked for such a URI, the server answers with the status code 303 (“See Other”) and the address of a document about the thing. Practice afterwards split between that pattern and hash URIs, which, like the #part3 example above, put the thing’s name inside a document’s name. Chapters 7 and 8 take this up.
  • The third layer arrived partially. Schema.org, launched in June 2011, put structured descriptions of things on a large fraction of pages, and search engines consume them. The browser showing a user a merged view of a thing, which this note describes, remains uncommon outside specialist tools.
  • Layer separation weakened elsewhere. Content delivery networks, of which Akamai, founded in 1998, was an early large one, and the later move of sites onto shared cloud hosting mean that the domain owner named in a URI is frequently not the party running the machines that serve it. That complicates the inference from name to responsibility that the whole argument rests on.

Connections

Questions 4

6.1 A link to a recipe gives an error. Using the layers, list in order where the fault could be.

6.2 A small shop’s site is hosted by a big cloud company. Whose name is in the URI, and who actually runs the machines?

6.3 In …/truc#part3, which organisation answers for what part3 means? How do you know?

6.4 Browsers removed the Extended Validation indicator after concluding users did not use it. Does that refute the claim that trust is an unavoidable exception to the abstraction, or only the claim that the browser is where it should be shown?
