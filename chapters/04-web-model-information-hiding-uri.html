Chapter 4

The Web Model: Information hiding and URI syntax

1998

Source The Web Model: Information hiding and URI syntax, a Design Issues note by Tim Berners-Lee, 1998-01-29. read the original

The short version

Put a link to section 3 inside a page, then move the page to a new address. The link still works, and the page was never edited. Had it needed editing, a digital signature on it would have broken. Berners-Lee’s 1998 note explains why it works: the software that fetches a page and the software that finds a place inside it are kept from knowing about each other.

This chapter is about where those dividing lines run, and why drawing them there is a large part of why the Web’s separate parts could go on being revised without one revision breaking the others.

The question

Why can HTTP, HTML and new document formats each be revised without breaking the others? The note’s answer is that the module boundaries were drawn in the right places early on, and it says where. Its subject is information hiding.

Berners-Lee numbered the note zero in his axioms sequence, though it came more than a year after the Axioms note of Chapter 2. That note describes what URIs are; this one describes the machine that consumes them.

4.1 Three parts that do not share what they know

The note puts modularity in human terms. The Web’s parts are independent: “There is knowledge they have individually but do not share”, and equally “There is knowledge their designers had individually but did not share”. That is information hiding: each part knows only what it needs, so the others can change without it noticing. The model applies it to a browser, or to anything else that follows a link, by dividing it into three parts.

Berners-Lee states the arrangement as two axioms:

The access machinery does not need to look at the fragment ID.

The presentation object does not need to know the URI of the resource.

And derives from them the claim that matters for everyone who writes specifications:

The specifications for access protocols are independent of the specifications for fragment identifiers. The Web Model, 1998

4.2 Why the fragment stays on the client

The immediate payoff is a link within the same page, such as <a href="#notes">. It specifies only a fragment, and because the hash syntax is universal across every scheme, the object can follow it without consulting the access code. An author can therefore write internal links without knowing where the document will be served, and move it without editing it.

Signed documents

Berners-Lee credits Jim Gettys with the observation that makes this more than a convenience: editing a signed document to fix its own links would break the signature. A document self-consistent independently of its namespace can be signed once.

Room to evolve

The second payoff is evolutionary, and he is emphatic about it. Because no access specification refers to fragment semantics, a new media type may invent whatever notion of a view or a part suits it, and a new way of fetching documents need not care what kinds of document travel over it.

This has already (1998) proved incredibly enabling to the community, as HTTP has advanced in parallel with many other ways of accessing data, and the number of exciting media types has grown very rapidly, and will be the key to many new revolutions built on top of the basic Web idea. The Web Model, 1998

Later formats used that freedom. A PDF can be opened at a page with #page=5, a convention recorded in RFC 3778 (2004), and a video clipped to seconds 10 to 20 with #t=10,20, from W3C Media Fragments (2012). Neither changed HTTP.

Webizing

A name #alice, used inside http://example.org/people, can be written http://example.org/people#alice, and then means the same thing anywhere. Webizing a language, he says, does this to every name that was global only within one document: append the document’s URI and a hash. New applications can then be built, like the hypertext Web, just by introducing new types of document. This is the mechanism of Chapter 6 and of Volume IV.

Where the axiom bites

The independence has a cost, which the note flags in passing. Because each media type defines its own fragments, a server that negotiates content, sending a PDF where the link’s author saw HTML, can deliver a document in which #section3 means nothing. Of such negotiation the note says “you run a risk & should warn the client”.

4.3 Why relative resolution is universal

Suppose Ann writes a book as files on her disk. Chapter one, at file:///home/ann/book/ch1.html, links to chapter two with only href="ch2.html", a relative reference giving just the part of the address that differs. Chapter one’s own address is the base URI; the application follows the link by replacing the last part of the base with ch2.html.

A design decision is recorded here that could have gone the other way. The application could have passed both the relative reference and the base to the access module, letting each scheme define its own resolution algorithm. Instead, one algorithm was made common to all schemes.

The justification has the same shape as the one for fragments. Linked sets such as a book’s chapters move between file systems, HTTP space and FTP space constantly, and universal rules mean they need not be modified when they do. Berners-Lee adds the caveat: moving half a set to one place and half to another still breaks the links.

4.4 The scheme, and why it must not be spent

The last section of the note is a warning.

The access scheme is by definition the highest point of flexibility. The Web Model, 1998

It is the escape hatch. If the whole Web developed a problem that existing protocols could not solve, a new space could be created, and Berners-Lee trusts this would work because it already had for Gopher and FTP:

If you have ported a concept between environments in the past, then there is a better hope that you can in the future. The Web Model, 1998

The danger is that spending the hatch destroys it:

If we use this extension point frivolously, ironically, it will cease to work. The Web Model, 1998

If many schemes are introduced, the space of scheme names becomes a namespace with all the properties that make namespaces hard:

  • clashes between names destroy interoperability;
  • ownership of names becomes commercially valuable;
  • fair management becomes both essential and difficult.

Worse, software would be needed to look up schemes and fetch handlers for them, which means something like DNS, so that the top level of the namespace becomes, in effect, DNS or something like it:

What happens if later DNS needs to be replaced? There is no top-level extension switch left. The world is stuck with whatever form of access-scheme name service exists. The Web Model, 1998

The conclusion is procedural: access schemes should not be open to trivial extension, and should be extended only by new standards with full open review. He does not rule new schemes out. He accepts data:, which puts a small document inside the URI itself, as genuinely new and orthogonal to HTTP, but suggests that many other proposed schemes would be better expressed as extensions within HTTP.

A space first, a protocol second

A distinction softens this. A scheme names a part of the URI space first, and a protocol only second, so the protocols can be replaced while the names stay the same: a new DNS protocol could take over gradually without any http: address changing. His analogy is the telephone:

When touch-tone dialing was introduced, the telephone numbering system remained the same. The Web Model, 1998

4.5 Why “resource” and not “document”

The note closes with the etymology. The first Web specification said Universal Document Identifier. The IETF discussion changed “document” to “resource” on two grounds: documents did not obviously cover films and sounds, and URIs exist for endpoints such as mailboxes and login ports, which are not documents at all. The word then picked up two further senses.

SenseIntroduced byCovers
“resource”The IETFAnything with a URI, including mailboxes (mailto:) and login ports (telnet:)
“resource”RDFAnything at all: the class of which every class is a subclass
“information resource”The Technical Architecture Group (a later addition to the note)Document-like things, the narrower original sense

Three meanings, one word, and the reader of any given specification must determine which is in force. The narrow, document-like sense matters, and the note’s section on the information resource says why: a document is the unit for reference and retrieval, “but also the unit of ownership, license to use, payment, confidentiality, endorsement, etc.” However far the technical notion is stretched, those social uses must still be supported, “so we can’t mess with it too much.”

What happened since

  • The independence axiom was written into the standard. RFC 3986, of January 2005, specifies that a fragment’s meaning is defined by the media type of the retrieved representation.
  • The client-side fragment was abused, then replaced. Single-page applications encoded application state in fragments, and Google’s AJAX crawling scheme made a convention of it from 2009 until deprecating it in October 2015. The History API’s pushState method restored a distinct URI per view.
  • New fragment conventions kept arriving, as predicted. Text fragments, addressing a passage by its words, shipped in Chrome in 2020, again with no change to HTTP.
  • The scheme warning was borne out by mobile. Applications claimed custom schemes in large numbers through the 2010s, and collided as the note warned: any application could register any scheme, and resolution was undefined. Both major platforms retreated to verified https links, Universal Links on iOS and App Links on Android, both introduced in 2015. Each checks a file served from the link’s domain, so which program opens a link is now settled by DNS names, much as the note foresaw.
