Chapter 46

Limiting the damage of an inconsistency

2010

Source Limiting the damage of an inconsistency, a Design Issues note by Tim Berners-Lee, 2010-06-26. read the original

The short version

In classical logic, once two contradictory statements are both accepted, anything can be proved. The Web is certain to contain contradictions. The answer is that nothing on the Web is believed just because it is there: it is believed only for a reason, for a limited purpose, and for a limited time.

The question

This note answers the objection many people raise, and Berners-Lee states it in the reader’s own voice before answering:

What, many people ask, will happen when this huge mass of classical logic meets its first inconsistncy? Surely, once you have one staement that A and another somewhere on the web that not A, then doesn't the whole system fall apart? Surely, then you can deduce anything you want? Inconsistent data, 1998

The objection is correct about logic and wrong about what a system does with documents.

46.1 Where the objection goes wrong

Suppose a naive logic engine holds both “the meeting is on Tuesday” and “the meeting is not on Tuesday”. By ordinary inference it can then prove that the moon is made of cheese, or anything else. Logicians call this the principle of explosion.

The fear would be valid, Berners-Lee grants, if every assertion in the world stood on an equal footing. Some imagine that an RDF parser, the program that extracts statements from a document, will scoop every fact off the Web into one massive set of beliefs. Real systems will not work that way. The correction is a chain: a fact is asserted in an expression (a single statement), which is part of a formula (a group of statements), which is found by parsing a document. Any reason to believe the document lies in metadata, a statement about it found in another document. And the sentence that does the work:

There is no a priori reason to believe any document on the web. Inconsistent data, 1998

46.2 Trust first, or trust last

The note names two designs. Working forwards starts from a configuration page, a document the system’s owner has chosen as its starting point. Working backwards starts from a global index, a search service that lists every document mentioning a given term. Working backwards reads documents its owner never chose, so the trust check at the end is all that stands between a stranger’s page and an answer.

46.3 Scoping trust to a key and a form

Digital signature adds security: a document signed with a key carries a mark only that key’s holder can make. A checksum is a short fingerprint computed from a document’s exact contents.

First, an endorsement must record the checksum the document had when it was believed. Endorse a URL, and whoever later edits that page inherits the endorsement; endorse a checksum, and any change breaks it. Second, a rule says what to believe. Its bluntest form trusts a key for everything:

“whatever any document says so long it is signed with key 57832498437”. Inconsistent data, 1998

In practice, Berners-Lee says, authorities are trusted only for specific purposes, and the rule must be narrowed to match. His examples trust one key only to say who is a member of W3C, and another only to say who is an IBM employee.

Trust is granted not to a party but to a party for a purpose, and that narrowness is what limits the damage.

46.4 The choice he does not make

Here he is undecided: “There is a choice here, and I am not sure right now which appeals to me most.”

RuleCost
Believe statements of the form “X is a member of W3C” signed with the W3C keyBureaucratic: only that exact wording counts, so an equivalent statement phrased differently will not match
Believe statements of that form that can be inferred from what the W3C key signedThe inconsistency trap: after one conflicting pair, every statement of that form follows

The first gives up something we normally rely on: being able to replace any set of formulae with another set deducible from it. He calls this very messy. In the second, once a contradiction can be deduced from what one key signed, “the key is completely broken. Of course, only that key is broken, so a trust system can remove any reason it has to trust that key.” The catch:

However, the attacked system may not realize what has happened before it has been convinced that the sun rises in the west. Inconsistent data, 1998

Can trust in a key be limited while information is still processed consistently? “Yes - maybe - there are many.” His way out is to limit the kinds of inference rule that may be used, as knowledge-representation systems with limited logics already do. The cost: a general proof engine must either be told the permitted rules as data, or have each limited reasoner built in, though perhaps a single limited reasoner would serve: “Maybe we only need one.”

46.5 Contradictions that are only out of date

The last section addresses a source of apparent contradiction that is not an attack at all, and opens with the dialogue characters of Chapter 29:

Tortoise: What's the time, Achilles?
Achilles: Five past ten, my friend. [They chat for a minute]
Tortoise: What is the time, Achilles?
Achilles: Six minutes past ten, Mr. Toroise.
Tortoise: But Achilles, you just told me just a minute ago it was five minutes past ten. How can I ever believe you again? Inconsistent data, 1998

Both answers were true when given. People and documents change status, and the contradiction comes from forgetting when each statement was made.

Expiry

The first remedy is an expiry date on everything, as an HTTP server can already send with a resource: the Expires header was in HTTP/1.0 (RFC 1945, 1996). All conclusions drawn from a document are cancelled when its date arrives, unless a fresher copy says the same thing. Statements should also be fully qualified. On the Semantic Web, “It is rainy” becomes something like: at 09:41 EST on Monday 24 January 2000, measurement gauge 5 at Dublin Airport read rain as having fallen in the last hour. A fuzzy system would conclude Dublin is wet; a classical one, only that at least once it rained somewhere in Dublin. Qualified this way, the statement does not go out of date; a later reading adds to it rather than contradicting it.

Writing the slack into the rule

The second remedy applies far beyond this subject: make the looseness in the real system visible. Instead of a rule that any employee of any W3C member organisation may register, the registration engine is told that anyone may register who, at some time in the last two months, worked for an organisation that was, at some time in the last two months, a W3C member.

If an organisation drops its membership, the system need not propagate that instantly: the slack has been written down. Berners-Lee also expects time-unaware reasoners fed data with expiry dates, their results used only while all the inputs are still valid.

The note ends: “time-aware systems may contain nested time-unaware systems, and probably vice-versa.” The Web never has to be consistent, only what a system has chosen to believe, for now.

What happened since

  • Trust scoped by purpose became standard. X.509 certificates carry an extended key usage field (RFC 5280, 2008) limiting what a key is trusted for; OAuth 2.0 (RFC 6749, 2012) grants tokens limited scopes.
  • Endorsing by checksum became ordinary. W3C Subresource Integrity (2016) lets a page load a script only if its hash matches.
