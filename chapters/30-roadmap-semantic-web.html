Chapter 30

A roadmap to the Semantic Web

1998

Source A roadmap to the Semantic Web, a Design Issues note by Tim Berners-Lee, 1998-09-09. read the original

The short version

A page on the Web is written for a person to read. A machine can fetch it and display it, but it cannot answer a question about what the page says, because nothing in the page tells it which words are prices and which are dates.

This chapter is the first full plan for fixing that: a stack of layers, each one useful on its own before the layer above it exists. Its central bet is a modest one. The system is never asked to work out an answer from scratch; it only checks a proof that someone hands it.

The question

The companion to Chapter 5, written the same month of September 1998 and spun off from it because the subject needed more room than a survey could give. Its own description of its standing is candid:

A road map for the future, an architectural plan untested by anything except thought experiments. Semantic Web Road map, 1998

It is the first full statement of the Semantic Web as a programme rather than an idea.

30.1 The problem being solved

The diagnosis has not aged:

One of the major obstacles to this has been the fact that most information on the Web is designed for human consumption, and even if it was derived from a database with well defined meanings (in at least some terms) for its columns, that the structure of the data is not evident to a robot browsing the web. Semantic Web Road map, 1998

Berners-Lee sets aside the artificial intelligence problem of training machines to behave like people. The Semantic Web instead develops languages for writing information in a form machines can process. Chapter 31 makes the negative case.

30.2 The layers

Berners-Lee justifies the base by minimalism. A universal web of assertions must rest on a model general enough that any application maps onto it, and generality forces simplicity. An assertion is a single statement, such as this page’s author is Alice. Quotation is a statement about a statement: Bob says that this page’s author is Alice. The base contains these two things only. Quotation is there early for two reasons: it will be needed later anyway, and most early applications are metadata, data about data, where statements about statements are basic even before logic arrives.

The base layer has no negation (saying something is not so) and no implication (if one thing holds, then another does). So, given a set of facts, it is always easy to say whether a question can be answered. Nothing can be intractable, meaning it would take impossibly long to work out.

Schema

A schema declares a new property and constrains how it is used, typically what kinds of thing it applies to. That allows simple checks: that a driver’s licence has the name of a person, and not a model of car, as its name. The schema language is kept deliberately weak.

Conversion

Two applications seldom use the same vocabulary, the set of terms their data is written in. The conversion layer states rules for translating one into another. It is allowed implication but still no negation. The note’s example is three databases built independently and put on the Web (Figure 30.2).

Logic

The logical layer adds “not” and “and”, then “for all x”. With these a document can carry general rules. Where a Library of Congress schema says “author” and a British Library one says “creator”, a small piece of RDF can state that for any person x and resource y, if x is the author of y then x is the creator of y.

Signature

For reasoning to take trust into account, public keys become first-class objects, things the logic can talk about, and the model records which key signed which assertion. Proof checking then verifies signatures as well as logic. It matters once proofs exist, but can be developed in parallel.

30.3 Why bother at the bottom

If an application’s data is simple, why express it in this model at all? The answer is the argument for the whole enterprise:

The answer is that we expect this data, while limited and simple within an application, to be combined, later, with data from other applications into a Web. Semantic Web Road map, 1998

The example is access control, where a decision may combine privacy preferences, group membership and data typing, each trivial alone and none sharing a format with the others. Chapter 37 works it through in detail.

30.4 Proof, and the asymmetry that makes it work

The most important design decision in the roadmap is a restriction, and it separates this plan from the artificial intelligence projects it is compared to. The system is required to validate proofs, not to find them.

Someone granted access to a site is given a document explaining to the server why they should have it. The proof is “a chain [well, DAG] of assertions and reasoning rules”, with pointers to the supporting material. The note expects the same of privacy and most electronic commerce:

The HTTP "GET" will contain a proof that the client has a right to the response. the response will be a proof that the response is in deed what was asked for. Semantic Web Road map, 1998

Finding a proof for an arbitrary question is intractable; checking one that arrives with the request is not. Chapter 31 makes the point at length.

30.5 Engines of the future

The closing sections are the most speculative. Indexes of terms, Berners-Lee expects, will let the Web be searched “as though it were one giant database, rather than one giant book”. He then proposes joining two kinds of engine that had each failed alone (Figure 30.4).

The estimate of how deep the combined engine must go is modest and specific:

many real life problems can be solved using just a few (say two) steps of inference out on the wild web, the rest of the reasoning being in a realm in which proofs are give, or there are constrains and well understood computable algorithms. Semantic Web Road map, 1998

He states the limit plainly: no machine will guarantee to answer arbitrary questions.

What happened since

  • The lower layers shipped. RDF, for assertions, became a Recommendation in February 1999; RDF Schema, for schema, in February 2004; OWL in the same month, whose equivalentProperty states exactly the conversion of Figure 30.2; and SPARQL, for queries, in January 2008. The plan was executed upward, in order, over a decade.
  • The proof layer did not. No interoperable proof exchange format was standardised. The asymmetry of section 30.4, which the roadmap treats as its central bet, was never cashed.
  • The search-plus-logic engine arrived in another shape. Large knowledge graphs behind search, beginning with Google’s in May 2012, combine indexing with structured data at exactly the scale described here, without the proof machinery.

Questions 5

30.1 The base layer has no negation. Give a useful statement you cannot make without it, and say which layer supplies the means.

30.2 Validating a proof is cheap; finding one is not. Name an application where the proof can plausibly arrive with the request, and one where it cannot.

30.3 Quotation is put in the base layer for two reasons. State both, and say which would justify it alone.

30.4 Berners-Lee guesses that two steps of inference on the open Web are enough for many real problems. Why does each extra step multiply the work a search-plus-logic engine must do?

30.5 Write the single equivalence statement that widens the search for Fred from employees to friends. Then say why the figure needs two.
