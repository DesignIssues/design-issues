Chapter 30

A roadmap to the Semantic Web

1998

Source A roadmap to the Semantic Web, a Design Issues note by Tim Berners-Lee, 1998-09-09. read the original

The short version

In 1998 Berners-Lee pictured a Web where a request for a page could carry a proof of the right to see it, and the page could come back with a proof that it was what had been asked for. First, machines had to be able to read the Web at all. A page is written for a person; nothing in it tells a machine which words are prices and which are dates.

This chapter is the first full plan for that: a stack of layers, each useful before the one above exists. It puts off the hard problem: the system never works out an answer from scratch, only checks a proof someone hands it.

The question

It is the companion to Chapter 5, written the same month of September 1998 and spun off from it because the subject needed more room than a survey could give. It is candid about its standing:

A road map for the future, an architectural plan untested by anything except thought experiments. Semantic Web Road map, 1998

30.1 Pages written for people

The diagnosis has not aged:

One of the major obstacles to this has been the fact that most information on the Web is designed for human consumption, and even if it was derived from a database with well defined meanings (in at least some terms) for its columns, that the structure of the data is not evident to a robot browsing the web. Semantic Web Road map, 1998

Rather than train machines to behave like people, the Semantic Web develops languages for writing information in a form machines can process. The payoff, the note says later, is a Web searched “as though it were one giant database, rather than one giant book”.

30.2 Each layer useful on its own

The base layer gives every application a common form. It is kept tiny because every application has to be able to write its data in it; the more things a format must fit, the less it can assume. It holds two things only: the assertion, a single statement such as this page’s author is Alice, and quotation, a statement about a statement: Bob says that this page’s author is Alice. Quotation comes early because most early applications are metadata, data about data.

The base layer has no negation (saying something is not so) and no implication (if one thing holds, then another does), so whether a question can be answered from a set of facts is always easy to settle. Nothing can be intractable, taking impossibly long to work out.

Schema

The schema layer adds the first check on what is said. A schema declares a new property and constrains how it is used, typically what kinds of thing it applies to: a driver’s licence must have the name of a person, and not a model of car, as its name. The schema language is kept deliberately weak.

Conversion

The conversion layer adds a way across from one application to another. Two seldom share a vocabulary, the set of terms their data is written in, so this layer states rules for translating one into another. It is allowed implication but still no negation. The note’s example is three databases built independently and put on the Web, joined through a zip, a US postcode (Figure 30.2).

Logic

The logic layer adds general rules: one statement that covers every case. It brings “not”, “and” and “for all x”. Where a Library of Congress schema says “author” and a British Library one says “creator”, a small piece of RDF, the note’s format, settles it: for any person x and resource y, if x is the author of y then x is the creator of y.

Signature

The signature layer adds the question of who said it. For reasoning to take trust into account, a public key becomes a thing the logic can talk about, and the model records which key signed which assertion. Proof checking then verifies signatures as well as logic. This work can proceed in parallel with the other layers.

30.3 Why bother at the bottom

If an application’s data is simple, why express it in this model at all? The answer argues for the whole enterprise:

The answer is that we expect this data, while limited and simple within an application, to be combined, later, with data from other applications into a Web. Semantic Web Road map, 1998

The example is access control, where a decision may combine privacy preferences, group membership and data typing, each simple within its own application, and combined only on the Web.

30.4 Check the proof, don’t find it

Finding proofs has no perfect algorithm, and “we do not tackle that problem”; the other party need only validate a proof, which “is trivial.” A proof here is a list of signed statements plus the rules that join them, which anyone can re-check step by step.

Someone granted access to a site is given a document explaining to the server why they should have it. The proof is “a chain [well, DAG] of assertions and reasoning rules” (a DAG is a chain that may branch and rejoin), with pointers to the supporting material. The note expects the same of privacy and most electronic commerce:

The HTTP "GET" will contain a proof that the client has a right to the response. the response will be a proof that the response is in deed what was asked for. Semantic Web Road map, 1998

30.5 Engines of the future

Indexes of RDF objects rather than words, Berners-Lee expects, are what will make the Web searchable like a database. He then proposes joining a search engine, which covers much of the Web but has no notion of correctness, with a logic engine, which is correct but lost in the mass of data (Figure 30.4).

The number of steps matters because each step out on the Web may follow every link from every result of the step before. Suppose each result had a hundred links: two steps would mean ten thousand fetches. The note ends on the limit and the prize:

Though there will still not be a machine which can guarantee to answer arbitrary questions, the power to answer real questions which are the stuff of our daily lives and especially of commerce may be quite remarkable. Semantic Web Road map, 1998

What happened since

  • The lower layers shipped. RDF became a W3C Recommendation (finished-standard status) in February 1999; RDF Schema and OWL in February 2004, OWL’s equivalentProperty stating exactly the conversion of Figure 30.2; and SPARQL, for queries, in January 2008.
  • The proof layer did not. Proofs were built in research, including cwm’s (Chapter 40), and Appel and Felten’s “proof-carrying authentication” (1999) attached proofs to requests in the same spirit. But no proof exchange format was standardised or widely deployed.
  • Prices and dates became readable. Schema.org, launched by Google, Microsoft and Yahoo in June 2011, is how pages now tell search engines which words are prices, dates and ratings.
  • The search-plus-logic engine arrived in another shape. Large knowledge graphs behind search, beginning with Google’s in May 2012, combine indexing with structured data, as the note proposed, without the proof machinery.
