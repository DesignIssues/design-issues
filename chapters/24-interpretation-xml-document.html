Chapter 24

The Interpretation of an XML document

2002

Source The Interpretation of an XML document, a Design Issues note by Tim Berners-Lee, 2002-01-01. read the original

The question

Chapter 17 established that one document may carry several vocabularies. This note, from January 2002, asks the question that leaves open, and it asks it in the bluntest possible form:

If one party sends another an XML document, how does one say what it means? The Interpretation of XML documents, 2002

The trouble is not that the answer is hard to find. It is that there are too many places to look, and no rule about which one wins.

24.1 The problem: specifications that fight

Berners-Lee credits Paul Prescod with the list of places one might look for how to process a document: the document type declaration, the top-level namespace, a schema reference, other namespaces declared at the root, any attribute on the root element, or anything at all in the document.

With six candidate authorities and no precedence rule, the failure mode is not ambiguity but combat:

In fact the general problem is that without any overall architecture, one can write specs which battle each other. “The X attribute changes the meaning of the Y attribute”, “The Z attribute restores the meaning of the X attribute irrespective of any Y attribute” and so on. The Interpretation of XML documents, 2002

Each specification is written by a group that is reasonable on its own terms. The conflict appears only when two of them meet in one file, which is exactly the case namespaces were created to permit.

24.2 Two models

The proposal sometimes made was a separate processing-model language, so that a document would have no meaning of its own until an external definition said how to process it. Berners-Lee rejects this and argues there is only one generic model that preserves the properties a multi-namespace system needs.

24.3 XML functions

The model needs one escape hatch, and the note names it. Some foreign elements are not data but instructions that yield more document when elaborated: an inclusion that pulls in another file, or a transform written as its own result. Berners-Lee calls these XML functions and argues that any supporting application must recognise them in default processing, because they change what the document is before anything else can decide what it means.

The two cases he works through are the literal result element as stylesheet, where a transform is written as an example of its own output, and inclusion. Both are elements whose whole purpose is to be replaced by something else, which is why they cannot be left to a later stage.

24.4 The need to quote

The section that gives the argument its force is about writing about markup. A tutorial on a transform language must contain examples of that language which are shown and not run. Under the pipeline model there is no way to say so: whatever stage handles transforms will find the example and act on it. Under the top-down model the element containing the example can declare that its contents are quoted.

This is why Berners-Lee calls the alternative dangerous rather than merely wrong. A processor that executes quoted material is executing content that its author never intended to be live, which is a description of a class of vulnerability rather than a stylistic complaint.

24.5 The conclusion

The top-down processing model for XML as an architectual principle resolves many of the questions which remain unanswerable with pipelined processing. In fact, consideration of the example shows that pipeline processing could be actually dangerious, producing errors and possibly security issues, in the case of generally nested XML technologies of the types discussed. The Interpretation of XML documents, 2002

The note also leaves an issue explicitly unresolved, which is worth recording because so few of these notes do: references to siblings, where one part of a document refers to another part that has not yet been interpreted.

What happened since

  • The question was overtaken. The mixed-namespace XML documents this note is about did not become the ordinary way to publish, and the branch that won, described in Chapter 23, has no namespaces to mix.
  • The pipeline model was standardised anyway. XProc, a language for XML processing pipelines, became a W3C Recommendation in May 2010, which is the approach argued against here.
  • The security concern was correct in general. Processing document content that its author intended as data remains a standard vulnerability class, most visibly in XML external entity handling, and the defence is the one implied here: nothing nested acts without permission from what contains it.
  • The quoting problem recurs everywhere. Template languages, configuration formats and prompt construction all need a way to mark a region as data rather than instruction, and the ones that lack it fail in the way section 24.4 describes.

Questions 4

24.1 List the six places a processor might look for how to interpret a document, and say which one a top-down model uses.

24.2 Write a small document that shows an example of a transform without executing it. What in the format lets you do so?

24.3 Berners-Lee calls inclusions and transforms XML functions and says they must be handled before anything else. Explain why, using the definition of a function as something that returns more document.

24.4 Take a format you use that mixes data and instructions. Does it let an author mark a region as quoted? If not, describe the failure.
