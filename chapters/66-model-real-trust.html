Chapter 66

Model Real Trust

2015

Source Model Real Trust, a Design Issues note by Tim Berners-Lee, 2015-03-28. read the original

The short version

Browsers trust a website only if a big certificate company vouches for it. But people trust others for many reasons: they met them, they know them, they work for them. Berners-Lee argues the browser should let people record those reasons, rather than treat everything outside the company chain as an attack.

The question

Volume VII opens with one of four related notes written in February and March 2015, each marked as a personal view, not a formal one of W3C. Berners-Lee calls this the most philosophical of the four, and its question is simple. People trust things for many different reasons. Does the machine let them say so?

66.1 Four ways people actually trust

When a browser connects securely to a site, the site shows a certificate: a document that ties the site’s name to a public key. The site keeps the matching secret key; only the holder of that secret can answer the browser’s challenge, so the browser knows it is talking to the named site.

The browser accepts it if a certificate authority it already trusts has signed it. Browsers ship with a list of these, the root store, so trust flows down a chain.

A self-signed certificate is one the owner signs for themselves. Browsers show an alarming warning for it, however well the user knows the owner.

A bank appears twice: trusted through an authority, or as a peer, when both sides sign contracts face to face and can exchange keys directly. Whatever the relationship, the note says, the user must be able to add that certificate because of it.

66.2 The objection

The complaint is about whose interests the default serves. In the quotation, PKI (public key infrastructure) means the certificate-authority system of 66.1.

It is at the moment a breakage in the system that browser manufacturers are fighting tooth and nail to stop people doing anything useful with an unsigned or a self-signed certificate. This is, with all due respect, playing into the hands of the corporate trust structure, PKI, which of course benefits from being used to convey these trust paths. Web Security - Model Real Trust, 2015

Three reasons are given for calling this inappropriate. Routing a family server’s trust through a commercial hierarchy is expensive. It misrepresents why the server is trusted. And it is a security liability:

The PKI system has many weak points, and in fact is a security liability for me to use it for something where I should be using more intimate key exchange system. Web Security - Model Real Trust, 2015

Root stores hold authorities in many countries, some hacked from time to time. Trusting a family’s server through them imports everybody else’s risk.

66.3 What he asks for instead

No, it should be enabled, and a great user interface provided for me, the user, to control and review the process. Web Security - Model Real Trust, 2015

The note’s own case is MIT, which distributes self-signed certificates to its staff. He has a close relationship with MIT and can walk into its offices, so accepting that one certificate is reasonable. Browsers meet such a certificate with a full-page warning, the way past it hidden behind an Advanced button.

The demand is for an interface, not a protocol change: accept a key, record why, review it later.

66.4 The common thread

All four notes make the same claim: the system models one kind of trust and treats every other kind as an error.

Chapter 37 warned against joining the machine loop to the social loop at every rung. This is the opposite failure: the machine admits one social arrangement only.

What happened since

  • Free certificates removed the cost argument. Let’s Encrypt issued its first certificate in September 2015 and made hierarchy-backed certificates free. That answered the expense objection and none of the others.
  • The weakest-authority problem was mitigated rather than solved. Certificate Transparency, public append-only logs of every certificate issued, was first specified in RFC 6962 (June 2013) and revised as RFC 9162 in December 2021, both as experimental RFCs. It makes certificates issued to the wrong party detectable after the fact, without changing who must be trusted.
  • Personal and peer trust moved elsewhere. Messaging applications that let two people compare keys supply the peer and personal patterns of Figure 66.1 outside the browser entirely.
