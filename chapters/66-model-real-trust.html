The question

Volume VII opens with one of four related notes written in March 2015, all carrying the same unusually careful disclaimer: personal view only, not a formal view of the Director, the Technical Architecture Group or the Consortium, offered as a contribution to the discussion.

Berners-Lee describes this one as the most philosophical of the four, and its question is simple. People trust things for many different reasons. Does the machine let them say so?

66.2 The objection

The complaint is not about cryptography but about whose interests a default serves:

It is at the moment a breakage in the system that browser manufacturers are fighting tooth and nail to stop people doing anything useful with an unsigned or a self-signed certificate. This is, with all due respect, playing into the hands of the corporate trust structure, PKI, which of course benefits from being used to convey these trust paths. Web Security - Model Real Trust, 2015

Three reasons are given for calling this inappropriate. Routing a family server’s trust through a commercial hierarchy is expensive. It misrepresents why the server is trusted. And it is a security liability:

The PKI system has many weak points, and in fact is a security liability for me to use it for something where I should be using more intimate key exchange system. Web Security - Model Real Trust, 2015

That last point is the technical heart of the argument. A hierarchy is only as strong as its weakest authority, and Berners-Lee notes that root stores contain authorities in many countries which have from time to time been hacked. Trusting your own family’s server through that chain does not add security; it imports everybody else’s risk.

66.3 What he asks for instead

No, it should be enabled, and a great user interface provided for me, the user, to control and review the process. Web Security - Model Real Trust, 2015

The demand is for an interface, not a protocol change. The mechanism to accept a key because you know whose it is exists already. What is missing is any way for a person to record that they did so, review it later, or explain to the machine why.

66.4 Why this comes first

The note names what the other three do: one explores the granularity of server-side applications, one the lack of support for client certificates, and one the decision to mark security in the identifier. All three are instances of the same claim, that the system models one kind of trust and treats every other kind as an error.

The argument connects back to Chapter 37, which warned against joining the machine loop to the social loop at every rung. This is the opposite failure. Here the machine loop admits exactly one social arrangement, a commercial hierarchy, and a person whose actual relationship is of another kind has no way to say so.

What happened since

  • Free certificates removed the cost argument. Let’s Encrypt, which the companion note mentions as a project, issued its first certificate in September 2015 and made hierarchy-backed certificates free, which answered the expense objection and none of the others.
  • Self-signed certificates became harder, not easier. Browser warnings grew more severe and harder to bypass through the late 2010s, which is the opposite of what section 66.3 asks for.
  • The weakest-authority problem was mitigated rather than solved. Certificate Transparency, standardised as RFC 9162 in December 2021, makes misissuance detectable after the fact without changing who must be trusted.
  • Personal and peer trust moved elsewhere. Messaging applications with key verification, and later decentralised identifiers, supply the peer and personal patterns of Figure 66.1 outside the browser entirely.

Connections
