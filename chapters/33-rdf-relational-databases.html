Chapter 33

RDF and Relational databases

1998

Source RDF and Relational databases, a Design Issues note by Tim Berners-Lee, 1998-09-01. read the original

The question

Written in September 1998 as a parenthesis to Chapters 5 and 30, this note answers the practical question that decides whether any of the plan matters: what happens to the data that already exists? Almost all of it is in relational databases, and Berners-Lee is explicit that reaching it was the point:

Indeed, one of the main driving forces for the Semantic web, has always been the expression, on the Web, of the vast amount of relational database information in a way that can be processsed by machines. Relational Databases on the Semantic Web, 1998

33.1 The mapping

The correspondence is stated in three lines and is exact enough to implement from.

33.2 One difference, and it is the whole difference

The comparison with entity-relationship modelling gets a yes and no. The model is great as a basis for such modelling and more general, because it is used for other things too. The change is small and consequential:

The RDF model is the same, except that relationships are first class objects: they are identified by a URI, and so anyone can make one. Furthurmore, the set of slots of an object is not defined when the class of an object is defined. Relational Databases on the Semantic Web, 1998

The consequence is that a relationship between two things may be stored apart from any information about either of them, which object-oriented systems generally assume is impossible. The example is the one Berners-Lee returns to often: someone defines a vehicle as having wheels, a weight and a length, and does not foresee colour. That does not stop anybody else asserting that a given car is red, using a colour vocabulary from elsewhere.

33.3 What a database does that a graph does not

The note is careful about what relational systems are good at, and the description is fair. Tables hold many records with the same properties, an individual cell is rarely thought of alone, queries join tables and yield tables, and the software is optimised for operations on a few tables some of which are very large.

Two further observations survive well. The first is about typing. Codd’s original model included datatyping with inheritance, intended to be implemented more fully than it was, so a shoe size and a house number may both be integers and nothing prevents joining on them. Practical systems leave it to the application to only do things that make sense, and Berners-Lee notes what changes on the Web:

Once a database is expreted onto the Web, it becomes possible to do all kinds of strange combinations, so a stronger typing becomes very useful: it becomes a set of inference rules. Relational Databases on the Semantic Web, 1998

The second is about primary keys, and it is the naming problem of Chapter 3 arriving in a new place. A primary key identifies a row, and can change without changing the row’s identity: a person may change their name. Cascading updates preserve referential integrity locally and cannot work across the Web. He lists the three options honestly: use a row identifier, constrain the key not to change, or put up with links breaking.

33.4 Two kinds of schema

A short observation explains why the two worlds feel so different, and it is about numbers rather than technology. There will be relatively few document schemas, and many sites will export documents defined by the same one, which is what provides interoperability. Database schemas are created independently per database:

Even if a million companies clone the same form of employee database, there will be a million schemas, one for each database. Relational Databases on the Semantic Web, 1998

From which he draws a modest role for the new technology: it may simply express the equivalence of terms between those million schemas. That is the conversion layer of Chapter 30, and it is still where the work is.

33.5 Exposing a database

The rest of the note is a strawman URI layout, giving addresses to the catalogue, schema, database, table, column, row, cell and arbitrary query, with a later revision based on code Dan Connolly implemented. Berners-Lee flags his own uncertainty in the margins and asks the question that matters: is a query on a primary key really an identifier? Is extracting a single cell?

His ruling is the axiom of Chapter 2 applied to databases. A URI should never refer to the results of a table-changing operation, and a general query should use the question mark convention or be posted rather than fetched.

One practical note closes it, and it is the same advice as Chapter 26: export a derived view rather than the internal storage, so that the external form can be persistent and suit the consumer while the internal one stays efficient and suits you.

What happened since

  • The mapping was standardised twice. Direct Mapping of Relational Data to RDF and R2RML, a customisable mapping language, both became W3C Recommendations in September 2012. The three-line correspondence of section 33.1 is the direct mapping almost verbatim.
  • Querying across both became routine. Systems that answer graph queries by translating them into SQL against an unchanged database are now ordinary, which is the arrangement this note sketches.
  • The primary key problem was solved by convention. Practice settled on surrogate keys and stable identifiers, which is the first of the three options offered here.
  • The million schemas are still there. Mapping between independently designed schemas remains largely manual, and is the main cost of every data integration project.
