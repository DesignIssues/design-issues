Chapter 57

Linked Data Shapes, Forms and Footprints

2019

Source Linked Data Shapes, Forms and Footprints, a Design Issues note by Tim Berners-Lee, 2019-04-26. read the original

The short version

A shape says what a piece of data must contain. A form is how a person sees and edits it. A footprint says where a new item is saved, and what its address will be. One example, an address book, runs through all three.

The question

Written in April 2019, this note poses a problem the earlier chapters of Volume VI left open, and states it as a tension rather than a task:

In a world of linked data, in which anyone can say anything about anything, how do we build systems in which users and apps are easily allowed to express useful, helpful things? Linked Data Shapes, Forms and Footprints, 2019

Freedom to say anything makes the data Web work. It also makes applications hard to write, because an application needs to know what it will get.

57.1 Why the existing tools do not answer it

The schema languages of Volume IV, RDF Schema and OWL, let a program draw conclusions from data, and say what makes no logical sense. OWL can say that nobody is their own parent, so data claiming it is nonsense; it cannot say a contact form should ask for a phone number. So they limit what may be written only indirectly.

So they can in a rather weak way be used to guide a user interface. But that won't do what we need. Linked Data Shapes, Forms and Footprints, 2019

Schema.org, a shared list of suggested properties used by search engines, is closer, and still not enough.

57.2 Three technologies, three questions

The note answers with three technologies, each for one question. Shapes have established languages, SHACL and ShEx; forms have a draft vocabulary; footprints, in 2019, were only an idea.

57.3 What a shape is for

Shape languages are described by what they are for:

Shapes languages can be used to validate existing data to make sure it will work before processing, to validate submitted data from an external source, and so on. They can be used in effect to define an Application Program Interface: The application program using this interface must provide data in this shape, and will get data in this shape. Linked Data Shapes, Forms and Footprints, 2019

An Application Program Interface is an agreed way for programs to exchange data. A shape is how two parties make that agreement, without limiting what anyone else may say.

In the note’s address book, a full name with no space in it triggers a warning, not a failure, with the message that such names are typically, not always, wrong. Unlike a simple list of field types, a shape carries severity and an explanation a person will read.

Shapes and forms compared

Shapes and forms look alike but, the note insists, differ:

57.4 Why footprints are the hard one

A shape describes data that exists. A form collects data from a person. Both assume somebody has decided where the result belongs. In a pod, a person’s own online store of data (Chapter 54), that decision is not obvious. Chapter 50 gave a protocol for how to write to a server; nothing said where.

If each application writes where its own files go, the store collapses into one folder per application. If it writes to a shared place, it must know which place, and how to name the new item, so that the next application can find it.

A worked footprint

The note sketches a rule for the address book. When a user adds a group named n to an address book whose address is u, the group’s address is dir(u) + 'Group/' + munge(n) + '/index.ttl#this'. Here dir() trims the last part off an address, leaving its folder, and munge() cleans a name of characters that do not belong in an address. A .ttl file holds linked data in the Turtle format.

Once a link exists, applications follow it:

Because URIs in the web of linked data are primary, footprints should only be used to create a new link where old data does not exist. Linked Data Shapes, Forms and Footprints, 2019

An application must never use the rule to guess that something already exists at an address. That is what separates a footprint from a hard-coded folder.

57.5 One shape, many footprints

One shape can be stored under many footprints. That makes no difference to reading data, which needs only the shape; it matters only when creating data, which needs a footprint to say where it goes.

57.6 Finding where a person keeps things

The note ends, mostly open, with discovery: how a system finds where a user keeps their stuff. It names three places to look, all reached from the user’s WebID, the address that identifies them.

Much collaboration happens in teams and projects, so groups get the same routes:

Whenever there is a path to find public things related to a user, and a similar path to find private things related to a user, then the same path should be made for groups in which the user is active. Linked Data Shapes, Forms and Footprints, 2019

What happened since

  • Shapes were already standardised. SHACL was a W3C Recommendation (July 2017) when this was written. ShEx was published by a W3C community group, not as a formal standard.
  • Footprints did not become a standard. Solid’s type index, older than the note, answers part of the question. From about 2020 the Solid community drafted Shape Trees and an Application Interoperability specification for the same placement problem.

Questions 5
