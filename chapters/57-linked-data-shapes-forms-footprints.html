Chapter 57

Linked Data Shapes, Forms and Footprints

2019

Source Linked Data Shapes, Forms and Footprints, a Design Issues note by Tim Berners-Lee, 2019-04-26. read the original

The question

Written in April 2019, this note poses the problem that all of Volume VI has been walking towards, and states it as a tension rather than a task:

In a world of linked data, in which anyone can say anything about anything, how do we build systems in which users and apps are easily allowed to express useful, helpful things? Linked Data Shapes, Forms and Footprints, 2019

Unlimited freedom to say anything is what makes the data Web work. It is also what makes writing an application on top of it hard, because an application needs to know what it is going to get.

57.1 Why the existing tools do not answer it

Berners-Lee is careful about what the schema languages of Volume IV do and do not do. They tell you what implications can be drawn, and what makes no logical sense. So they constrain what may be written only indirectly, by declaring some things false.

So they can in a rather weak way be used to guide a user interface. But that won't do what we need. Linked Data Shapes, Forms and Footprints, 2019

A language that tells you what would be nonsense cannot tell you what a form should ask for. Vocabularies that suggest which properties go with which class are closer, and still not enough.

57.2 Three technologies, three questions

57.3 What a shape is for

The constraint languages are described by what they can be used for rather than by what they are, and the list is the practical answer to why one would bother:

Shapes languages can be used to validate existing data to make sure it will work before processing, to validate submitted data from an external source, and so on. They can be used in effect to define an Application Program Interface: The application program using this interface must provide data in this shape, and will get data in this shape. Linked Data Shapes, Forms and Footprints, 2019

That last clause is the important one. In a world where anyone may say anything, a shape is how two parties agree what they will actually exchange, without either constraining what anyone else may say.

The worked example is an address book, and one detail in it is worth extracting because it shows what these languages can express that a type system cannot. A constraint on a full name warns, rather than failing, when the name contains no space, with the message that full names without spaces are typically, not always, wrong. Severity is part of the constraint, and so is the explanation a person will read.

57.4 Why footprints are the hard one

A shape describes data that exists. A form collects data from a person. Both assume somebody has decided where the result belongs, and in a personal store that decision is not obvious.

The question a footprint answers is what an application should do the first time it needs to write something. Put it where its own files go, and the arrangement of Chapter 55 collapses into folders per application. Put it in some shared place, and it must know which place, under what name, described how, so that the next application can find it.

This is the difference between a protocol for writing, which Chapter 50 supplies, and a convention about where writing goes, which nothing supplied. Two applications can both speak the protocol perfectly and still be unable to see each other’s data.

57.5 The shape of the problem, generally

The three technologies correspond to three separations the book has made before. Shapes are about machines agreeing, which is Chapter 21’s conformance term. Forms are about people, which is Chapter 56. Footprints are about placement, which is the question Chapter 37 warned about when it said not to confuse what is said with where it is stored.

The distinction holds for any system where several programs share a store. Agreeing a format is not the same as agreeing a layout, and a system that settles the first and leaves the second produces programs that cannot cooperate for reasons neither author anticipated.

What happened since

  • Shapes were standardised twice. SHACL became a W3C Recommendation in July 2017 and ShEx was published as a community specification, and both are used to validate data before processing.
  • Forms remained bespoke. Driving a user interface from a vocabulary is done in Solid’s own libraries and almost nowhere else; most applications still hard-code their forms.
  • Footprints did not become a standard. Solid’s type index answers part of the question, and where a given application should put a new thing is still largely convention.
  • The general problem is now widespread. Shared stores written by many programs, from note systems to knowledge bases, all hit the placement question, and mostly answer it with per-application folders, which is the outcome this note is trying to avoid.
