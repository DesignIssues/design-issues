Chapter 27

Metadata Architecture

1997

Source Metadata Architecture, a Design Issues note by Tim Berners-Lee, 1997-01-06. read the original

The short version

Metadata is data about things, written so that a program can use it. Berners-Lee lays down two rules. First, metadata is ordinary data, so it can live inside a page, travel with it, or sit in a separate document, and it can itself be described. Second, it is a set of separate statements, none of which overrides another. The names for kinds of statement are URIs, so anyone can invent one.

The question

This note, begun in January 1997, opens Volume IV because it is where the Semantic Web starts, though it does not use the phrase. Berners-Lee says so himself in a preface added later: it was written before the roadmap of Chapter 30 and introduces the same ideas, in the historical order they arose at the Consortium. There the first driving application of machine-readable data was endorsement labels: ratings such as “suitable for children” attached to pages.

The definition it gives is narrower than the word’s ordinary use, and the narrowing is the point.

27.1 The definition, and the word doing the work

Metadata is machine understandable information about web resources or other things Metadata Architecture, 1997

When a browser fetches a page, the server also sends lines such as Date: and Expires:. Those lines are metadata: data about the page, written so that a program can act on them. Berners-Lee immediately says which part of the definition matters (“software agents” are programs acting on someone’s behalf):

The phrase “machine understandable” is key. We are talking here about information which software agents can use in order to make life easier for us, ensure we obey our principles, the law, check that we can trust what we are doing, and make everything work more smoothly and rapidly. Metadata Architecture, 1997

The clause “or other things” is the seed of Volumes IV to VI. Metadata began as data about web resources, but it should in future describe anything: people, things, concepts and ideas. The design keeps that in mind.

27.2 The first axiom, and its consequence

Axiom. Metadata is data.

Information about information counts in all respects as information. Two consequences follow. The first is that metadata can live anywhere, in the three places of Figure 27.1. (An HTML page’s head is the undisplayed part holding its title; HTTP headers are the lines the server sends ahead of the page.)

The second consequence is recursion without hierarchy. Metadata may itself have an owner and an expiry date, so there is meta-metadata (data about the metadata), but the architecture does not distinguish many levels. It says metadata is data and lets the rest follow. It is the same move as Chapter 3’s refusal to distinguish names from addresses: one kind of thing, not a tower of kinds.

27.3 The second axiom: independent assertions

Axiom. The architecture is of metadata represented as a set of independent assertions.

Two assertions about the same resource stand alone. Taken together they simply mean “this AND that”, and AND does not care about order, so a collection of assertions is an unordered set. The consequence is a prohibition, and it rules out a great deal of existing practice:

This design decision rules out for example, in simple sets of data, assertions which are somehow cumulative or later ones override earlier ones. Each assertion stands independently of others. Metadata Architecture, 1997

Configuration files where later rules override earlier ones are excluded. Chapter 32 shows that such constructs, written out as independent statements, are usually a large nested conditional the specification never admitted to.

27.4 Assertions have a shape

An assertion has a type, a subject and parameters (the other things the statement mentions), as a sentence has a verb, a subject and an object. The note writes (A u1 p q…): A names the type, u1 is the URI of the subject, and p, q are the rest. An assertion that a resource has a named property, such as its author, is an attribute. Who said it, and when, are usually left implicit.

Links are assertions too

A link is an assertion relating two resources: the triple (A u1 u2) of a relationship type and two URIs, as in the versioning example of Figure 27.3. Names for types must come from a global space, because anyone may coin one, and that means URIs. The triple of Chapter 32 is already here.

27.5 Self-describing information

The note’s central goal explains why this was worth doing. Berners-Lee wants data that “carries a reference to the specification of the semantics” of its assertions: each type of statement points, by URI, to its own definition. A program meeting an unfamiliar type can follow that link and extend what it understands, rather than guessing.

PICS (the Platform for Internet Content Selection, W3C’s endorsement label format) is the note’s running example. The rest of the note, rough by its own account, covers label syntax, authorship, manipulating labels without knowing their vocabulary, and ordering. The generalisation survived. PICS did not.

What happened since

  • The general form replaced the specific one. RDF became a W3C Recommendation in February 1999, generalising the label idea into assertions about anything. PICS was superseded, with POWDER (a W3C Recommendation of 2009) taking over its job of describing groups of pages; the architecture described here outlived its first application by decades.
  • All three placements survive. Metadata in the document, in the transfer and in a separate description are still the three options, now as embedded structured data, HTTP headers, and separately published descriptions.
  • The authorship question was never fully answered. Who is making a statement, which section 27.2 flags as needing rationalisation, remains the weak point: much published metadata carries no indication of who asserted it, which is why Chapter 37’s treatment of trust matters.
  • Ordering never went away. Even in 1997 the note listed HTTP header lines as ordered; order-dependent formats remain common, and the diagnosis in Chapter 32 still applies to them.

Connections

The quality-of-service metadata asked for in Chapter 3 and the genericity metadata of Chapter 10 are both instances of this architecture. Questions 5

27.1 Metadata is data, so metadata can describe metadata. Show that this does not produce an infinite regress by writing three levels (for instance: a page; a review of the page; the date the review was written) and saying where it stops.

27.2 Take a metadata format you use. Which of the three placements does it use, and who is making the statement in each case?

27.3 The independence axiom rules out later-overrides-earlier. A file says allow everyone then deny Bob. Rewrite it as statements that mean the same whatever order they are read in.

27.4 “Machine understandable” is doing the work in the definition. Give an example of information about a resource that is not metadata under this definition, and say why.

27.5 The note compares a label to the label on a jam jar. Why does a label not need to name its subject?
