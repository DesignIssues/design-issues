Chapter 43

Design alternatives considered in Notation3

2002

Source Design alternatives considered in Notation3, a Design Issues note by Tim Berners-Lee, 2002-03-01. read the original

The short version

Why writing “whose email is this?” is harder than writing “x’s email”, and why a mailing list is not a list: stored as a list, equal sets look different.

The question

English says “x’s boss’s home’s phone” easily. “Whose boss’s home’s phone is this number?” comes out clumsier. Berners-Lee wanted Notation3 (N3) to say both in a few characters, and tried notations borrowed from programming, old email addresses, units of measure, directory paths and English. He kept this record of still-open choices “to save me going over the reasons again and again.”

43.1 Easy forwards, awkward backwards

In RDF, data is a graph: things joined by labelled links. Each label is a property, such as email or boss. Moving along links is traversal: given an expression for a person, write one for the thing one email link away.

Berners-Lee sets the criteria first:

“Neat”? Compact, powerful, simple, naturally understandable because of metaphors with existing use of similar syntax. Alternative design choices in Notation3, 2002

Borrowed syntax costs less to learn. Forward traversal follows a link the way it points; backward traversal asks what points here. His instinct is that forward is the more common need.

43.2 Nine notations, each borrowed from somewhere

Ending in email instead of phone, the chain can be written x.boss.home.email (programming), email of home of boss of x (English), x's boss's home's email (English again) or x'boss'home'email (Ada). The note weighs nine candidate notations, each borrowing a metaphor. In the keyword row below, :joe :son thatWhich :girlfriend :jane says Joe’s son is the one whose girlfriend is Jane. On a blackboard, Berners-Lee noticed, “% and of look pretty similar”, so % might serve as of. The note then sorts the candidates by two questions: does the operator come before or after the term, and which way does it travel?

The note’s verdict on its own grid: “it can be really difficult to read the backward traversal in english.”

One way round: a backward step along email is a forward step along its inverse, as long as readers can tell whether ^email is shorthand or a real, named property.

43.3 When a list is really a set

A later section, dated 2005, argues for adding sets, and the argument is empirical:

It turns out that in many cases in applications we have seen, containers are in fact logically unordered sets, not ordered lists. Whether it is mail addresses on a mailing list, or rows in a database, or statements in an N3 formula, the order is immaterial, and something can occur in the set once or not at all. Alternative design choices in Notation3, 2005

Using a list for a set has three costs:

  • Two lists with the same members in different orders are not evidently the same, so comparison falls to the application.
  • That it is really a set lives only in documentation or people’s heads.
  • Implementations cannot use ready-made code built for sets.

Sets need what lists have: a form in statements, and a shorthand.

What was proposed

For statements, the note borrows from OWL, the W3C’s vocabulary for classes: [ owl:oneOf (1 2 3) ] is the class whose members are exactly 1, 2 and 3, in any order. The shorthand was harder; of seven syntaxes tabled:

SyntaxForAgainst
(1, 2, 3)Almost no new punctuationParser must look ahead a whole expression
($ 1 2 3 $)Otherwise just like a listNone recorded
{$ 1, 2, 3 $}Curly braces are conventional for setsBraces already mean formulae (a quoted group of statements)
@Set{1, 2, 3}Just a new keywordNone recorded

To “look ahead” is to read on past the opening bracket before knowing what is being parsed. The note records that “The current choice is {$ 1, 2, 3 $}”, with dollar signs to tell a set from a formula. A harder question stays open: does {$ :a, :b, :c $} say that the three are different things? Suppose :a and :b turn out to be the same person. If the names are taken as distinct, the set has three members and can be counted, but merging two sets (union) or finding their common members (intersection) needs to know which names are the same. If not, union is safe but counting is not: in cwm’s equality-aware mode, learning that two names are equal would “in some cases reduce the number of members of a set”. A set of three becomes a set of two.

43.4 Forced choices and matters of taste

Here the choices are still soft, so one can see which were forced. Take Sandro Hawke’s idea: make sets and formulae the same thing, since a formula is just a set of statements. Berners-Lee finds it “inherently appealing in its symmetry”. But N3 statements have no opening mark, and so the parser could not know in advance which it was reading; and { :x }, already valid N3 as a statement with no triples, would overlap with set syntax. Not fatal, he says, but harder. The parser outweighed the symmetry.

English, like many systems including the Web, “is optimized for forward traversal”. A Web page knows what it links to, not what links to it.

What happened since

  • Caret and slash arrived in the query language. Property paths became part of SPARQL 1.1, a W3C Recommendation of March 2013. They use ^ for an inverse step and / for a sequence: two of the candidates weighed here.
  • No set literal was standardised. RDF 1.1 and Turtle, both W3C Recommendations of February 2014, kept ordered collections and rdf:Bag, an unordered container that allows duplicates, so still not a set, but added no set syntax or semantics.
