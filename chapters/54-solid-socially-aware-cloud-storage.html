Chapter 54

Solid: Socially Aware Cloud Storage

2009

Source Solid: Socially Aware Cloud Storage, a Design Issues note by Tim Berners-Lee, 2009-08-17. read the original

The short version

Your photographs live with the photograph company. Your messages live with the messaging company. Each of them holds a piece of your life, none of them can see the others, and leaving any of them means losing what you kept there.

This note asks what happens if you turn that inside out: your data in one place that you control, and applications as things that come and go. It is the founding document of the project its author has worked on ever since.

The question

This is the founding document of the project that occupied Berners-Lee for the following fifteen years, written in August 2009 and still being edited in 2023. Chapter 50 established that data can be written back. This asks who may write it, and answers by separating two things the Web had bolted together.

Crucial design issues are that principals (users) and groups are identifies by URIs, and so are global in scope, and that elements of storage are access controlled using those global identifiers. Socially Aware Cloud Storage, 2009

54.1 The diagnosis

The note begins with an unusually careful description of the architecture it means to replace, and it is fair to it. A site stores state and serves scripts. Users have an identity on the site. The site manages access with some flexibility. Applications are usable because much of the work happens in the browser.

The problem is stated as a consequence rather than a complaint:

However, the javascript of the web site is is the only thing which accesses the user's data stored on that site. Indeed, for security purposes, scripts from other sites are deliberately prevented from accessing it. Socially Aware Cloud Storage, 2009

The isolation is not an oversight. It is the same-origin policy of Chapter 68 working exactly as designed, and it has the effect that your data is reachable only by the application that stored it.

The consequence for cross-site access is precise, and Berners-Lee names the class of flaw:

Because the functionality of an application (such as looking at photos) is on a given web site, when the user wants to use that application to access photos on another site, the first site must get access to the second site on the user's behalf. This is a more complex form of authentication, and is subject to "confused deputy" attacks. Socially Aware Cloud Storage, 2009

Delegated access schemes tackle this, and his objection to them is not that they fail but what they require: the site receiving the data must be completely trusted.

54.3 The three benefits, and the one that is really an argument

Berners-Lee lists what the separation buys, and the second is the one the whole of Volume VI has been building towards:

It allows the data from various applications to be cross-linked, at great derived extra value, breaking down the silos described above. Socially Aware Cloud Storage, 2009

The first is control: the user decides who may read what, whatever applications they use. The third is about markets, and it is an argument about barriers to entry:

It allows innovation in the market for applications, because the bar far launching an app is far lower, as the app can run in he open data cloud. Socially Aware Cloud Storage, 2009

An application that need not run servers or hold anybody’s data can be written by one person and given away. Chapter 50’s stated goal, that application growth becomes dramatic once storage is decoupled from deployment, rests on this.

54.4 The risk, stated plainly

The note does not oversell. Applications run with the user’s credentials, and Berners-Lee says what follows:

This of course allows as bad app to do bad things. However, because the data is stored in a storage the user controls, the risk of information misuse by those that run unscrupulous web sites is reduced. Socially Aware Cloud Storage, 2009

The hazard is not removed but moved. In the site model the risk is that a company you cannot inspect holds your data forever. Here the risk is that a program you ran once did something you did not intend, to data you still hold. The second is the failure mode of an operating system, and it is at least the kind of problem people know how to reason about.

54.5 Different lifetimes

A short observation closes the argument and explains why coupling the two was always awkward:

The persistence of applications and data may be very different. Socially Aware Cloud Storage, 2009

A long-established application may be used for an ephemeral conversation. A throwaway application may be written to solve a short-term problem with data that must be kept for decades. Binding the two together forces the shorter lifetime on both, which is why leaving a service means losing what you made with it.

What happened since

  • The project was built. Solid produced a specification, a protocol version 0.9 in December 2021, servers and applications, and a company founded in 2018 to commercialise it.
  • The identifier problem was solved twice. WebID and later decentralised identifiers both give people URIs, which is the requirement this note opens with.
  • Regulation arrived at the same goal. Data portability rights, in European data protection law applicable from May 2018, address the silo problem by compelling export rather than by decoupling storage.
  • The market in applications has not appeared. The prediction of section 54.3 is the part still outstanding: storage did not become a commodity, and most people’s data still lives with the application that created it.
