Chapter 54

Solid: Socially Aware Cloud Storage

2009

Source Solid: Socially Aware Cloud Storage, a Design Issues note by Tim Berners-Lee, 2009-08-17. read the original

The short version

The photographs live with the photograph company, the messages with the messaging company. None can see the others, and leaving any of them means leaving behind what was kept there.

This note turns that inside out: data in one place under its owner’s control, applications that come and go. It is the design that grew into Solid.

The question

Suppose a person’s photos, friends list and messages lived in storage that person controls; any application could work on all of them. The hard part is permission: who may read or write what, when people and groups are defined on many different servers? The note (2009, edited until 2023) answers with URIs:

Crucial design issues are that principals (users) and groups are identifies by URIs, and so are global in scope, and that elements of storage are access controlled using those global identifiers. Socially Aware Cloud Storage, 2009

54.1 Why every site is a silo

Photographs kept on one site are invisible to every other site, and that is deliberate. A site stores state (everything it remembers between visits) and serves scripts, and one rule keeps each site’s data to itself:

However, the javascript of the web site is is the only thing which accesses the user's data stored on that site. Indeed, for security purposes, scripts from other sites are deliberately prevented from accessing it. Socially Aware Cloud Storage, 2009

This is the same-origin policy (Chapter 68), the browser rule that a script may read data only from its own site, working as designed. Each site becomes a silo.

Joining silos, and its costs

Joining two silos needs a go-between:

Because the functionality of an application (such as looking at photos) is on a given web site, when the user wants to use that application to access photos on another site, the first site must get access to the second site on the user's behalf. This is a more complex form of authentication, and is subject to "confused deputy" attacks. Socially Aware Cloud Storage, 2009

A confused deputy is a trusted program tricked into using its authority for someone else. Suppose a photo site may fetch Alice’s pictures from another site. A stranger’s page asks the photo site to fetch “my pictures”; the site, holding only Alice’s permission, fetches Alice’s and hands them to the stranger.

Delegated access such as OAuth lets a user grant one site specific data held by another, such as a friends list; the note finds this clumsy in some ways, and the receiving site must be completely trusted.

Nor are silos an accident. The site sells ads “because it forces the user to use its web site to access her data. It can also sell her data, index it, generate profiles of her”. The note replies: “there are other business models, and other ways of getting people to come to your site than hoarding their data.”

54.2 Storage on one side, apps on the other

The proposal holds the two apart. Storage belongs to the user, as MIT students have for years had disk space, and now web space, through Athena. Applications are programs the user runs, which visit that storage with the user’s permission. Storage becomes a commodity, as the internet provides “connectivity as a commodity independent of applications”.

The note’s analogy is the Unix file system, whose user and group names mean something only on one machine. Webizing them, Berners-Lee’s word for replacing such names with URIs that mean the same everywhere, does to users and groups what HTTP did for files.

54.3 Four reasons to pull them apart

BenefitIn plain terms
ControlThe user decides who may read what, whatever applications they use.
Cross-linkingData from different applications can point at each other.
A low bar for new appsAn app needs no servers of its own.
Separate lifetimesA short-lived app can handle long-lived data, and the reverse.
The persistence of applications and data may be very different. Socially Aware Cloud Storage, 2009

A familiar application may host an ephemeral discussion; one built for a short-term enterprise problem may handle data whose life “exceeds that of any of the applications the enterprise uses”. Decoupled, each lifetime can be managed separately. A user should also be able to delete all the data an application wrote, a convention the note recommends for applications sharing one store.

The second is where Volume VI has been heading:

It allows the data from various applications to be cross-linked, at great derived extra value, breaking down the silos described above. Socially Aware Cloud Storage, 2009

Anyone could make and sell an app, “like the 2009 iPhone app market but open”. The goal rests on this: “application growth becomes dramatic as the provision of storage is decoupled from the design and deployment of applications”.

54.4 The risk, stated plainly

Applications run with the user’s credentials, her proof of identity:

This of course allows as bad app to do bad things. However, because the data is stored in a storage the user controls, the risk of information misuse by those that run unscrupulous web sites is reduced. Socially Aware Cloud Storage, 2009

The hazard is moved, not removed: from a company the user cannot inspect to a program the user ran, the same risk as installing software on one’s own computer.

54.5 How Bob’s server decides about a stranger

Each user gets a single URI instead of a user name at each site, “or in fact one for each persona they want to have”. Ideally it is a WebID, linking a profile on the Web to a certificate, a key kept in the browser that proves which URI the user is. A group’s URI returns its members’ WebIDs. Permissions sit in access control files:

Access control files are linked data. Socially Aware Cloud Storage, 2009

An access control file (ACL) lists who may read, write or control a resource. The server trusts only what it reaches from the ACL (Figure 54.3): if Alice’s own profile claimed membership of the group, that would count for nothing.

54.6 Who tells the person in the photo?

On a central site, when A notes that picture P, taken by B, shows person C, B and C can be told at once, and site-wide indexes answer “Which picture am I in”. Across many servers, links do not run backwards by themselves. The note lists three remedies: a crawler indexes back-links; the destination collects them from the “Referer” field HTTP sends when a link is followed; or, as it proposes, the destination is told in real time.

To ask to be someone’s friend, a person appends a line to a “friend requests” file they cannot read. Generalised, this is a drop-box linked from a profile, for requests of any kind. Guarding it against spam may matter; limited to predefined forms, it is safer. But a box open to any input is what lets a new application notify anyone.

What happened since

  • The project was built. Solid produced a protocol (version 0.9, December 2021), servers, applications and a company, Inrupt, announced in 2018.
  • People got URIs. WebID (which the note relies on) and decentralised identifiers (a W3C Recommendation in July 2022) both give people URIs.
  • Regulation arrived at the same goal. European data portability rights, applicable from May 2018, compel export rather than decoupling storage.
