Chapter 5

Web Architecture from 50,000 feet

1998

Source Web Architecture from 50,000 feet, a Design Issues note by Tim Berners-Lee, 1998-09-04. read the original

The short version

Everything worth talking about on the Web should have its own address, a URI. Fetching with GET must only fetch, and any answer worth retrieving should be given an address of its own rather than hidden behind a special command. The one central weak point in the whole design is the root of the domain name system, which a single body has to run for everyone. Berners-Lee names two mistakes he wanted corrected: the separate https scheme, and the split between the messages protocols send and the documents they carry.

The question

This is the survey, and Berners-Lee explains at the start why he resisted writing it for so long:

I have resisted the urge, and requests, to try to write an architecture for a long time: This was from a feeling that a dead and therefore less valuable document must any attempt to select which, of all the living ideas, seem most stable, logically connected and essential. Web Architecture from 50,000 feet, 1998

The sentence is mangled and the meaning is clear: fixing a living thing in one document kills part of it. He wrote it anyway, presented it to the Consortium’s Advisory Committee and chairs, and kept revising it into 1999 and beyond. It is the closest the collection comes to a single statement of the whole design, and almost every later volume expands a paragraph of it.

5.1 The plan of the argument

The Web, Berners-Lee says, is a universe of network-accessible information. He divides its potential in two, and the division organises the note and much of this book: the Web is first a means of human-to-human communication, and second a space in which software agents can reach enough of what society and science contain to work alongside us.

He treats the space itself first, then its use as a human medium, then as a medium for machine reasoning. Two goals are taken for granted throughout: interoperability, and a technology that can evolve. A third is named as a core value: universality of access, irrespective of hardware, software, network, language, culture, location, or physical or mental impairment. These values, he notes, permeate the work too thoroughly to sit in any one section.

This chapter follows the first part, where the note is most settled. The second half, on data formats, XML, namespaces, the separation of form from content and the semantic web, is expanded in Volumes III and IV.

5.2 Why URIs are the foundation

The most fundamental specification, he says, is also one of the simpler ones. The argument for its primacy is not about naming but about composition:

Great multiplicative power of reuse derives from the facts that all languages use URIs as identifiers: This allows things written in one language to refer to things defined in another language. Web Architecture from 50,000 feet, 1998

A language that adopts URIs inherits whatever the URI specification says about persistence, identity and equivalence. That reference is itself a flexibility point, a place where one part can change without the others: naming can be defined once and revised separately from every language that uses it.

The guidance that follows has held up:

  • Respect the generic syntax, the shape every URI shares: a scheme, a colon, and the rest.
  • Do not introduce new schemes without due cause.
  • Do not introduce a rival scheme presenting itself as a superset of URIs, since that would make a reference require something more than a URI.
  • Give every significant object with persistent identity a URI.
  • Where a reference is needed, use a URI and do not constrain which scheme.

5.3 The centralised part

Having praised decentralisation, Berners-Lee names the exception:

The Achilles' heel of the HTTP space is the only centralized part, the ownership and government of the root of the DNS tree. As a feature common and mandatory to the entire HTTP Web, the DNS root is a critical resource whose governance by and for the world as a whole in a fair way is essential. Web Architecture from 50,000 feet, 1998

An HTTP address has two parts: a domain name delegated down the Domain Name System (DNS), and an opaque string decided by the domain’s owner, as Figure 5.1 shows.

He adds that the Consortium did not address this, except indirectly through ICANN (the Internet Corporation for Assigned Names and Numbers, set up in 1998 to oversee the DNS root). The admission is characteristic: a structural weakness is named and no solution offered.

On persistence he is equally direct. Persistent HTTP URIs are a matter of tool maturity, user education and the maturity of Web society, and moving resources is strongly discouraged. Research into naming schemes does not mean HTTP URIs cannot be persistent, nor that identifiers should be split into names and addresses: Chapter 3 in one sentence.

5.4 GET, universality, and a worked example

The axioms of Chapter 2 reappear as two rules about GET, the HTTP operation that fetches what a URI points to. First, GET must have no side effects: using it to unsubscribe someone from a mailing list or fill a shopping cart is incorrect. Second, no other side-effect-free method should be invented that returns something depending on the URI, because its results would form a separate address space. The note illustrates why this is about universality rather than tidiness:

Instead of defining a new method CVSSTAT to retrieve the code management status of a document, that status should be given a URI in the server's space, and headers used to point the aware client to it. Otherwise, we end up with a class of document which contains interesting information but cannot be linked to. Web Architecture from 50,000 feet, 1998

Links carry URIs, not methods, so nothing behind a special method can be linked to. The test is still useful: if an answer is worth retrieving, it is worth an address.

5.5 The https wart

One design decision is singled out, on architectural grounds. Because https is a space separate from http, a document served securely and the same document served insecurely are different resources with different identifiers. Berners-Lee argues that security should have been negotiated while dereferencing one identifier (following it to fetch what it names), not a fork in the namespace, and warns against the precedent: language, privacy level and other dimensions must not each acquire a scheme.

Volume VII shows him still making the complaint seventeen years later, by which time the Web had moved decisively the other way.

5.6 Messages and documents are the same thing

The most speculative section proposes collapsing a distinction:

There has been to date an artificial distinction between the transmission standards for “protocols” and “content”. In the ever continuing quest for generalization and simplification, this is a distinction which cannot last. Web Architecture from 50,000 feet, 1998

New protocols, he concludes, should be defined as exchanges of messages that are themselves XML, and indeed RDF, documents.

What the merger would gain

The gain is compositional: whatever can be done to one can be done to the other. Messages become signable because documents are, and documents become binary-encodable (packed as compact bytes) because messages are. The recursion already exists, he notes: email messages contain email messages, and business is conducted with documents carried by SMTP (the protocol that moves email) and HTTP. It nearly happened once, with HTTP messages almost defined in SGML, the older markup language from which HTML was derived.

The wish list for HTTP

The vehicle he names is HTTP-NG, a Consortium activity studying a “next generation” HTTP that might unify remote procedure calls with Web protocols. He sets out five goals:

  1. Many concurrent message exchanges over one connection.
  2. A general data typing and marshalling standard (packing structured data for the wire).
  3. A schema system able to define any remote-procedure-call interface (asking another machine to run a function and return the result).
  4. Extensions for asynchrony and streaming.
  5. A socially aware state propagation protocol, keeping copies of changing information up to date, built on top in a modular way so the basic design could be simpler than HTTP 1.1.

Later revisions record that HTTP-NG ended without momentum, while XML for remote operations between companies became prevalent around 2001 as Web Services.

What happened since

  • The DNS root question was answered, slowly. The United States relinquished its stewardship of the IANA functions (the bookkeeping of the DNS root and of protocol numbers) to the global multi-stakeholder community on 1 October 2016. Whether that constitutes governance “by and for the world as a whole in a fair way” is contested; that it was addressed at all took eighteen years.
  • The wish list was granted, in a different currency. Concurrent message exchange arrived with HTTP/2, RFC 7540 of May 2015, and HTTP/3, RFC 9114 of June 2022. Both use binary framing. Neither uses XML or RDF messages. The functional requirements were met and the representational argument was lost.
  • HTTP-NG did not survive. It closed without a successor protocol; the work was done a decade later by other groups.
  • Web Services went the other way. The XML-based remote-operation stack was built, then largely displaced through the 2010s by resource-oriented interfaces exchanging JSON, closer to his own architectural preference than the stack he expected.
  • The https objection lost. Rather than negotiating security within one namespace, the Web deprecated the insecure one. HTTP Strict Transport Security (HSTS, a way for a site to tell browsers to use only its https addresses) was published as RFC 6797 in November 2012, and Chrome began marking all plain HTTP pages as not secure in July 2018. The dimension became a scheme permanently. Chapter 67 records the author’s response.

Questions 4

5.1 Berners-Lee calls the DNS root the only centralized part of the HTTP space. Identify two further points of centralisation in today's Web (consider who issues the certificates behind https, or who makes the browsers), and say whether each is structural or contingent.

5.2 Restate the CVSSTAT argument as a general rule, then apply it to an interface you know that returns information through a method or verb other than GET.

5.3 Set out the strongest argument for the separate https scheme. What goes wrong when a page loads some parts securely and some not, and what could an attacker do if security were left to negotiation?

5.4 HTTP/2 delivered concurrent message exchange with binary framing rather than structured documents. Which of the five goals listed in section 5.6 remain unmet, and does any of them still matter?
