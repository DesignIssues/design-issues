Chapter 9

A Short History of the term "Resource"

2009

Source A Short History of the term "Resource", a Design Issues note by Tim Berners-Lee, 2009-08-01. read the original

The short version

“Resource” began life as “document”: a web address named a page. Over the years the word was stretched to mean anything. People using RDF, the Web’s language for data, then wanted plain web addresses, with no hash in them, to name people and ideas rather than pages about them. The compromise was a rule about the server’s reply. A 200 answer means the address names a page. A 303 answer says only see this other page, so the address may name something else, such as a person. Berners-Lee’s own preference is to stop saying “resource” and say Document or Thing instead.

The question

Suppose the address http://example.net/people/Pat returns a page about Pat. Does the address name the page, or Pat? Web architects had argued this at length (Chapters 7 and 8), and in 2009 a new task force was being proposed to take it up again. In August Berners-Lee sent the Technical Architecture Group (the TAG, the W3C body that advises on Web architecture) an email answering with the history of one word, “resource”, and of the several meanings it had acquired.

9.1 How “document” became “anything”

People got used to http://example.com/ being a web page and http://example.com/#contact an anchor within it: the address named a document. Then the word began to widen, in five stages.

OrderWhoWhat “resource” meant
1The first Web specificationNothing: the term was “document”, in Universal Document Identifier (UDI)
2The IETF’s online-information communityA useful thing out there: a page, a file, a film
3REST, Roy Fielding’s 2000 description of the Web’s architectural styleA time-varying mapping between a URI and a representation (the bytes a server sends back)
4RDFAnything at all; rdf:Resource is the class of everything
5The Architecture of the World Wide Web, the W3C’s 2004 summary of how the Web works“Information resource” for a page; “resource” for anything

At the IETF (the Internet Engineering Task Force, which standardises Internet protocols) the D became R; some felt “document” was not wide enough to include things like films. The URI specification, he says, wisely declined to constrain what a resource could be, which left the word open for everything that followed.

Nobody, he says, ever pinned the word down:

There was no real definition of what a resource or document was -- maybe because it seemed obvious. The HTTP spec did not even specify whether the URI denoted a person or a document about them, it just explained that the thing returned representation of the resource. A Short History of “Resource” in web architecture, 2009

9.2 What the formal definition left out

REST’s definition (an address may return different bytes at different times, and that is all) was, Berners-Lee says, good enough for HTTP, but not for describing how the Web actually worked.

A weather page’s address returns different text each day, yet always today’s weather. The formal definition captures only the first half.

The 2004 Architecture document had to add what REST left out, the social expectations:

yes, the mapping from URI to representation is a function of time, but not just any old one -- a random function is not typically very useful. There are expectations about it can change with time. Persistence, consistency, with various common patterns which allow the web to be a useful medium. A Short History of “Resource” in web architecture, 2009

9.3 The hash: a trick that worked

RDF attached itself to the Web without changing it, by a mechanism sometimes called “webizing”: giving a name that only made sense inside one file a global Web address.

The web architecture gave all these languages a common way of building a global identifier for the thing denoted by a local identifier in a given document. The semantics of the hash sign are defined web-wide to mean that “a#b” can be used to denote whatever is denoted by “b” in the document denoted by “a”. A Short History of “Resource” in web architecture, 2009

A graphics language may name lines and points this way, HTML anchors, RDF people and concepts. Berners-Lee’s verdict: it “worked a treat”. “Some of us did lots of work and made all kinds of systems which exchanged and integrated data in this way.”

9.4 Snags, a truce, and a change that was not a change

Then came two snags. First, many RDF publishers used HTTP URIs but did not put the document online, writing foo.rdf#color without ever publishing foo.rdf. Having skipped that, they had no reason to keep the hash either.

Second, the hash ties each term to the file that defines it, and for some large systems the file size was wrong either way: one term per file, or a million in one, so that looking up one meant fetching all. Others simply disliked how the hash looked. So people demanded the right to use http://example.net/people/Pat to name Pat rather than a web page about Pat.

The truce

The TAG negotiated what Berners-Lee calls a truce among three parties: the HTTP specification, the RDF systems already built, and those who wanted hashless names (Figure 9.3). Those systems took a hashless address to name a document; the danger, he writes, was “huge failures in the whole RDF world”. Berners-Lee, among others, pushed back against hashless URIs for arbitrary things, but eventually gave in.

The resulting rule, known as httpRange-14 after its number in the TAG’s list of issues, is drawn in Figure 8.2. A 200 answer, which returns the page, means the hashless URI names a document. For a person or an RDF property the server must not answer 200, but may answer 303 (See Other), pointing to a document that explains more. A 303 by itself says nothing about what the URI names.

So in response to this, the HTTP protocol was, in fact, changed.
The spec wasn't changed. A Short History of “Resource” in web architecture, 2009

The HTTP specification’s editors at the IETF “were not brought on board” to the new model. “The spec was interpreted.” What a server could be asked about widened from documents to anything; the text stayed as it was.

His verdict:

It isn't a very bad design, nor very beautiful. Other designs would have worked, but that one was the only one which didn't have major problems for some community. A Short History of “Resource” in web architecture, 2009

“Basically it works”, he adds. Reversing it would be very expensive for systems already deployed; so would going on debating it as though it were an open issue.

9.5 Two capitalised words

The note closes with a proposal, never adopted: edit the documents to use Document and Thing, and eliminate Resource. No English word fits exactly, he admits:

the web is a new system, a design in which new concepts are created, so we can't expect english words to exist to capture exactly the concepts. So we take those nearby and abuse them as little as we can as far as we can tell at the time, and then write them in initial caps to recognize that that is what we have done A Short History of “Resource” in web architecture, 2009

The capitals are an admission: the ordinary word has been bent, and the reader is told so.

What happened since

  • The word was not eliminated. “Resource” remains in the URI specification (RFC 3986, 2005), in the current HTTP specification (RFC 9110, 2022), and in RDF 1.1 (2014), carrying different senses in each.
  • The Web Ontology Language had already moved. As the note records, OWL (a W3C Recommendation since 2004) uses owl:Thing for the universal class rather than rdf:Resource: the substitution Berners-Lee recommends, made five years earlier.
