Chapter 9

A Short History of the term "Resource"

2009

Source A Short History of the term "Resource", a Design Issues note by Tim Berners-Lee, 2009-08-01. read the original

The short version

The word “resource” began life as “document”: a web address named a page. Over the years it was stretched to mean anything at all. People using RDF, the Web’s language for data, then wanted plain web addresses, with no hash in them, to name people and ideas rather than pages about them. The compromise was a rule about the server’s reply: a 200 answer means the address names a page, and a 303 answer means it names something else and points to a page describing it. Berners-Lee’s own preference, stated at the end, is to stop saying “resource” and say Document or Thing instead.

The question

Written in August 2009 as an email to the Technical Architecture Group (the TAG, the W3C body that rules on questions of Web architecture), this note is the plainest thing Berners-Lee wrote about one word that caused years of argument, recorded in Chapters 7 and 8, over whether an address such as http://example.net/people/Pat names Pat or a page about Pat. The question became possible because “resource” acquired several meanings, and each community inherited the one that suited it.

It is also the most candid chapter in Volume II: Berners-Lee describes a position he held and his decision to give way.

9.1 From Document to Thing: five stages

OrderWhoWhat “resource” meant
1The first Web specificationNothing: the term was “document”, in Universal Document Identifier (UDI)
2The online-information community at the IETF (the Internet Engineering Task Force, which standardises Internet protocols)A useful thing out there: a page, a file, a film
3REST, Roy Fielding’s 2000 description of the Web’s architectural styleA time-varying mapping between a URI and a representation (the bytes a server sends back)
4RDFAnything at all; rdf:Resource is the class of everything
5The Architecture of the World Wide Web, the W3C’s 2004 summary of how the Web works“Information resource” for a page; “resource” for anything

The letter changed from D to R because some felt “document” was not wide enough to include things like films. The URI specification then wisely declined to constrain what a resource could be, which left the word open for everything that followed.

On the gap that opened up:

There was no real definition of what a resource or document was -- maybe because it seemed obvious. The HTTP spec did not even specify whether the URI denoted a person or a document about them, it just explained that the thing returned representation of the resource. A Short History of “Resource” in web architecture, 2009

9.2 Why REST was not enough

A resource as a time-varying mapping from URI to representation was, Berners-Lee says, good enough for HTTP, but not for describing how the Web actually worked.

The address of a weather page returns different text each day, yet always today’s weather. The formal definition captures the first half of that sentence, not the second.

What was missing was the social expectation:

yes, the mapping from URI to representation is a function of time, but not just any old one -- a random function is not typically very useful. There are expectations about it can change with time. Persistence, consistency, with various common patterns which allow the web to be a useful medium. A Short History of “Resource” in web architecture, 2009

This is Chapter 3’s conclusion in a different vocabulary: a formal definition cannot say what makes a resource worth relying on, and reliance is what the Web runs on.

9.3 How the hash made local names global

The note gives the clearest statement of how RDF attached itself to the Web without changing it, a mechanism sometimes called “webizing”: giving a name that only made sense inside one file a global Web address.

The web architecture gave all these languages a common way of building a global identifier for the thing denoted by a local identifier in a given document. The semantics of the hash sign are defined web-wide to mean that “a#b” can be used to denote whatever is denoted by “b” in the document denoted by “a”. A Short History of “Resource” in web architecture, 2009

A graphics language may name lines and points this way, HTML anchors, RDF people and concepts, all without any change to HTTP. Berners-Lee’s verdict: worked a treat.

9.4 Two snags, and a concession

The two snags

First, many RDF publishers used HTTP URIs but did not put the document online, writing foo.rdf#color without ever publishing foo.rdf. Having skipped that, they had no reason to keep the hash either.

Second, the hash ties each term to the file that defines it, and for some large systems the file size was wrong either way: one file per term, each holding a single definition, or a million terms in one file, so that looking up one meant fetching all. Others simply disliked how the hash looked. For one reason or another, people demanded the right to use http://example.net/people/Pat to name Pat rather than a web page about Pat.

The truce

I among others pushed back against using non-hash URIs for arbitrary things his but eventually gave in. A Short History of “Resource” in web architecture, 2009

The specification was not changed, and its IETF editors were not brought round to the new model; it was interpreted. Berners-Lee calls the resolution a truce, negotiated by the TAG between the HTTP specification, the RDF systems already built, and the people who wanted hashless URIs for people. It is known as httpRange-14, after its number in the TAG’s list of issues.

The rule, shown in Figure 9.3: a 200 answer (“here it is”) means the hashless URI names a document. For a person or an RDF property the server must not answer 200, but may answer 303 (“see other”), pointing to a document that describes it.

Berners-Lee writes both that the HTTP protocol “was, in fact, changed” and that “The spec wasn’t changed”: the text was untouched, but a web server can now be asked about anything, not only documents. His verdict:

It isn't a very bad design, nor very beautiful. Other designs would have worked, but that one was the only one which didn't have major problems for some community. A Short History of “Resource” in web architecture, 2009

9.5 The proposal at the end

The note closes with advice never adopted and still the best available: edit the documents to use Document and Thing and eliminate Resource. He acknowledges why no English word will fit.

the web is a new system, a design in which new concepts are created, so we can't expect english words to exist to capture exactly the concepts. So we take those nearby and abuse them as little as we can as far as we can tell at the time, and then write them in initial caps to recognize that that is what we have done A Short History of “Resource” in web architecture, 2009

That is a rule for reading this whole book: every capitalised term in Web architecture is an ordinary word under protest.

What happened since

  • The word was not eliminated. “Resource” remains in the URI specification (RFC 3986, 2005), in the current HTTP specification (RFC 9110, 2022), and in RDF 1.1 (2014), carrying different senses in each.
  • The Web Ontology Language had already moved. As the note records, OWL (a W3C Recommendation since 2004) uses owl:Thing for the universal class rather than rdf:Resource: the substitution Berners-Lee recommends, made five years earlier.
  • The truce was questioned, not replaced. In 2012 the TAG issued a public call for proposals to amend the httpRange-14 resolution. Several were submitted, none was adopted, and the 200/303 rule remains the documented practice.
