Chapter 17

Extensible languages and web evolution

1998

Source Extensible languages and web evolution, a Design Issues note by Tim Berners-Lee, 1998. read the original

The short version

Real documents mix vocabularies: an invoice uses business terms for the price and a supplier’s terms for the part. Each vocabulary must be well defined, declared in the block that uses it, and marked on every name by a visible prefix. A reader must be able to tell what it may safely skip without looking anything up.

The question

Since 1989 the Web had grown on one rule inherited from email: ignore anything not understood. Growth was fast, but each new feature stayed ambiguous until a standard was agreed, which, the note says, weakened the Web’s reliability and credibility and risked permanent fragmentation. Distributed object systems had the opposite problem: well-defined interfaces, but a rigidity that helped keep them from spreading in a “web-like or virus-like manner”. In February 1998 Berners-Lee and Dan Connolly asked whether the Web could have both. The goal:

Imagine if an old version of a word processor could read a file written by a new version with partial understanding, rather than panicing that it had met a being from the future. Extensible languages, 1998

17.1 The old rule, and what it left undefined

The old rule

If you find a language element you don't understand, ignore it. Extensible languages, 1998

Even “ignore” meant two things: HTTP drops an unknown header entirely, while HTML drops an unknown tag but keeps its contents. The note’s diagnosis: “neither the specification of new elements nor the effect of ignoring them was ever clearly defined.” Its answer meets the demand that closed Chapter 16 (Figure 16.2).

The invoice

The note’s example is an invoice for an aeroplane part.

It happens on the Web too, the note adds, “as people bury private elements such as index tags and editing information inside HTML files.”

17.2 A message is an expression, not a procedure call

A procedure call is one program asking another to run a single named operation with fixed inputs, like a form with fixed fields. It is tempting to treat a message as such a call. The authors reject the analogy:

don't think of an HTTP message or an HTML document as an RPC call, but rather as the transmission of a expression in some language. Extensible languages, 1998

Extend HTML with mathematics, the note says, and an author should still be able to use HTML bold inside a formula. Nesting whole documents is not enough: names from two vocabularies must sit together in one expression. That is the first requirement.

17.3 Mixing vocabularies without silent clashes

Four words the requirements use:

TermMeaning
ElementA stretch of a document identified by a local name, such as the invoice’s cost entry
VocabularyA set of such names whose meaning is defined somewhere else, by a resource on the Web; it is in scope where its names may be used
SchemaA specific document that defines a vocabulary
Namespace (the chapter’s term)A vocabulary named by a URI, such as http://blah/currency

The note sets out seven requirements; the three on schemas come in section 17.5.

The ban on lookup (third row) is argued most sharply. In some programming languages, finding which module (separately written unit) a name comes from means reading the modules and applying priority rules. For documents that is a serious flaw:

when one module changes (without the knowledge of the designers of the other module), it can unwittingly redefine a local identifier used by the second module, completely changing the meaning of a previously written document. Extensible languages, 1998

This is why XML namespace prefixes bind directly and visibly, rather than being resolved by lookup.

17.4 Why each block declares its own vocabulary

A prefix such as f: on a tag says which vocabulary the name comes from. The note’s example binds f to a currency schema for one block, with NS:using standing in for a real syntax: 

<a:details>
  <NS:using href="http://blah/currency" as="f">
    <a:price>
      <f:chf>4.00</f:chf>
    </a:price>
  </NS:using>
</a:details>

XML Namespaces later put the binding in an attribute, holding for that element and everything inside it: 

<a:price xmlns:f="http://blah/currency">
  <f:chf>4.00</f:chf>
</a:price>

Why not declare every binding once, at the top? The note gives four reasons. The plainest is that when a name is bound close to where it is used, mistakes in hand-maintained documents are “much less likely”.

Generated documents

Many pages are assembled by programs that write one part without seeing the rest. Moving bindings to the top afterwards means buffering the whole document, which rules out pipelined processing, where each part is passed on as soon as it is produced.

Long documents

Imagine a list of suppliers, each with its own catalogue schema. With local bindings the working set, the memory held while processing, stays finite; with global bindings it grows with every page. Memory that grows with length, held for a time that grows with length, means total cost rises as the square of the length.

Joining documents

A worthy design goal, the authors suggest, is that joining any two XML documents gives an XML document. Without local scope, one must be rewritten end to end to rename clashing prefixes. XML never met that goal: two joined documents have two root elements, which XML’s basic syntax forbids.

17.5 What may be extended, and what may not

The invoice supplies the remaining three requirements. Its designer wants the item description open to any supplier’s part vocabulary, but the list of people allowed to sign closed: only Tom or Joe may sign.

So a schema language needs a way to say that a content model (the rule for what may appear inside an element) may be extended, and a way for a new schema to declare that it is such an extension. The seventh requirement makes partial understanding cheap:

It should be possible to create an original document schema such that one can determine, without access to the extension schema, which uses of extensions to that document can be ignored. Extensible languages, 1998

An invoice must be processable as an invoice without fetching anybody’s part catalogue. The note sees three ways: deduce what may be ignored from the original schema; mark it in the document through the language itself; or let the new schema say so, perhaps with mappings to “simpler expressions in better known vocabularies”. Only the first two need no new schema, and whether such marking belongs in the language or in a widely known vocabulary the note leaves open: “This design decision is not currently clear.”

What happened since

  • Namespaces shipped with local scope. XML Namespaces became a W3C Recommendation in January 1999 with prefixes bound directly and scoped to the element that declares them: requirements one to three.
  • Schemas gained ways to mark content as skippable. XML Schema 1.0 (W3C Recommendation, May 2001) lets a schema mark where foreign content may appear and be skipped (processContents="skip" or "lax"). SOAP 1.1 (2000) added the converse, mustUnderstand.

What the note does not take up is that converse: a way to say an extension must not be skipped. That is Chapter 18.
