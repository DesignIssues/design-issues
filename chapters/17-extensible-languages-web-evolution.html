Extensible languages and web evolution

Source

This chapter is about Extensible languages and web evolution, a Design Issues note by Tim Berners-Lee, dated 1998.

Read the original at https://www.w3.org/DesignIssues/Extensible.html. The Design Issues notes are Tim Berners-Lee's personal notes and are not endorsed by W3C. This book is commentary; where it quotes, it attributes.

The question

Chapter 16 ended with a demand: free extension, but with an extension mechanism that is itself well defined. This note, written with Dan Connolly in February 1998 and also issued as a W3C Note, is the specification of that demand. It is the most requirements-shaped document in the collection, and each requirement is set in its own paragraph in the original.

The authors are careful about their standing:

Whilst technically the personal opinion of the authors, it their best attempt as technical coordinators at outlining common architectural principles for W3C development. Extensible languages, 1998

17.1 What partial understanding looks like in life

The note's method is to argue from an ordinary document rather than from theory. The example is an invoice for an aeroplane part.

We are constantly handling information with partial understanding. Imagine if an old version of a word processor could read a file written by a new version with partial understanding, rather than panicing that it had met a being from the future. Extensible languages, 1998

17.2 A message is an expression, not a procedure call

Before the requirements comes a correction of the prevailing analogy. It is tempting to treat a message as a remote procedure call: a target object, one of a finite set of methods, and typed parameters. The authors reject it:

don't think of an HTTP message or an HTML document as an RPC call, but rather as the transmission of a expression in some language. Extensible languages, 1998

An expression can name functions from many interfaces at once. A procedure call names one. That difference is the whole argument, and it produces the first requirement.

17.3 Four requirements

RequirementWhat breaks without it
More than one vocabulary may be in scope at one point in a documentExtensions can only be nested, never mixed; no bold inside a formula
A vocabulary may be introduced with a purely local changeGenerated fragments cannot declare their own terms
The syntax must tie an identifier to its schema without inspecting any schemaOne module's change silently redefines another module's names
A namespace may be defined by present or future schema languagesThe definition mechanism is frozen at the level of the day

The third is argued most sharply, and names a language to avoid. Some languages let identifiers be imported so that determining which namespace a name belongs to requires reading the module interfaces and applying priority rules. Berners-Lee and Connolly point to Java as a case and to Modula-3 as the counter-example, and give the objection:

when one module changes (without the knowledge of the designers of the other module), it can unwittingly redefine a local identifier used by the second module, completely changing the meaning of a previously written document. Extensible languages, 1998

This is why XML namespace prefixes bind directly and visibly, rather than being resolved by lookup.

17.4 Why local scope, in three arguments

The case for local rather than document-wide binding is made with unusual rigour, and the second argument is the one that has aged best.

The first argument is that generated documents are assembled by programs that have no access to the rest of the document, so a fragment must be able to declare its own terms. The third is concatenation: joining two documents should be simple, and the authors suggest it would be a worthy design goal that the concatenation of any two XML documents be an XML document. Without local scope, concatenation means rewriting one document end to end to resolve clashing prefixes.

17.5 What may be extended, and what may not

The invoice returns at the end to make a distinction the requirements list would otherwise miss. The designer of an invoice may well want the item description to be extensible, so that any supplier's part vocabulary can be dropped in. The same designer certainly does not want the list of people authorised to sign to be extensible. Two constraints on schema languages follow: a way to say that a content model may be extended, and a way for a new schema to declare that it is such an extension.

The final requirement is the one that makes partial understanding cheap:

It should be possible to create an original document schema such that one can determine, without access to the extension schema, which uses of extensions to that document can be ignored. Extensible languages, 1998

An invoice must be processable as an invoice without fetching anybody's part catalogue. That is the difference between a mechanism that works offline and one that requires the network to agree with you.

What happened since

  • Namespaces shipped with local scope. XML Namespaces became a W3C Recommendation in January 1999 with prefix bindings scoped to the element that declares them, which is requirement two, and with prefixes bound directly rather than resolved, which is requirement three.
  • The ignore-without-fetching requirement did not. No mechanism was standardised for declaring which extensions may be skipped without consulting their schema. Chapter 18 is the proposal that was never taken up.
  • The concatenation goal was not met. Joining two XML documents still yields a document with two roots, which is not well formed. The problem recurs in Chapter 24.
  • The analogy was borne out elsewhere. Modern schema-on-read data formats treat a record as an expression over several independently evolving vocabularies, with unknown members carried through rather than rejected, which is section 17.2's position arriving without the XML machinery.

Questions 4

17.1 Explain why nesting one document inside another does not satisfy the same-scope requirement. Give a markup example where nesting fails.

17.2 Section 17.4 argues that global bindings make resource use rise as the square of document length. Reconstruct that argument, stating the assumption about how bindings are retained.

17.3 An invoice schema wants an extensible item description and a fixed list of signatories. Write, in any schema language you know, the distinction between the two.

17.4 The final requirement is that ignorable extensions be identifiable without fetching their schema. Name one thing this makes possible that a network lookup would not.
