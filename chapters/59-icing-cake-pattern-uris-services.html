Chapter 59

Icing on the cake pattern: URIS of services and metadata close to the URI of the target

2016

Source Icing on the cake pattern: URIS of services and metadata close to the URI of the target, a Design Issues note by Tim Berners-Lee, 2016-12-01. read the original

The short version

Put the published page’s address first. Reach every tool for that page by adding a few characters to its address, so that people and programs can always find their way between the page and its tools.

The question

A visitor on a project’s live web page wants its source, its broken links or its history. Nothing on the page says where any of that lives unless someone typed a link. Berners-Lee’s December 2016 note, its editing status marked “good enough for government work”, asks a question most projects never ask out loud: when a thing has tools attached to it, whose address comes first?

59.1 Tool first, or work first

A version control system keeps every past version of a project’s files; GitHub is the best-known web interface to one. When the project is a website, one file gets several addresses. In Berners-Lee’s example, index.html in the project myproject of the account acmedata has an editable view, a raw copy on a second domain, a hosted copy on github.io, and the live copy on the owner’s domain.

On w3.org the arrangement is reversed. The page keeps its plain address, and its tools are reached by adding a comma and a short word to the end.

59.2 Lost in both directions

Berners-Lee names two failures of discoverability, finding one address from the other, and they mirror each other. From the repository there is no rule for constructing the live site’s address, so the project must write the link into its documentation by hand. From the live site, whether on github.io or the owner’s domain, there is “no obvious way of knowing that the github site exists or of finding its URI.”

59.3 The cake and the icing

The pattern names what a system treats as primary: the repository, or the published thing:

The live data is the center. This is the cake - this is the main purpose of the site: serving the web pages. That is the cake, and everything else is icing on the cake. Icing on the cake, 2016

The advantage he claims for this is scale: because every tool hangs off the page, more can be added indefinitely, as “no one tool forces the whole URL into its own strange shape.” On w3.org the marker is a comma; the note asks that suffixes be short, simple and memorable, with a readable index of them. What matters is a fixed rule, so that anyone holding the page’s address can work out the tool’s.

The note’s appendix, a snapshot of 10 December 2017, shows that scaling: about sixteen tools on one page’s address. Five of them:

SuffixWhat it returns
,textA plain text version of the page
,checklinkThe bad links in the page
,validateThe markup errors: mistakes in the page’s HTML tags
,spellThe spelling errors
,cvslogThe log of changes to the document

59.4 Name the work, not the tool

A page at acmedata.github.io/… breaks if the project moves off GitHub; acmedata.com/… does not. This is Chapter 3’s argument about information in names: an address that names the tool which made it will eventually be wrong, while naming the work and deriving the tool’s address leaves the tool free to change.

Chapter 57 asked the same question about data: where should one application save so that another can find it? There, a second app looks in its own folder for a contact the first saved elsewhere. Like the visitor to a live page, it can fetch anything but has no rule for where to look.

59.5 Icing for machines

A comma typed by hand serves a person. Berners-Lee also wants icing for programs, in HTTP headers the reader never sees. A page supporting Memento can answer with a header such as 

Link: <…/timegate/…>; rel="timegate"

telling a browser where to find older versions. A Solid server, his personal data system, sends a rel="acl" link to the page controlling who may access a resource. Solid takes only the machine half of the pattern: its access-control specification forbids clients to compute that address from the resource’s own, so for software the link, not a guessable suffix, is the route. The note wants more: future versions of Solid “may do well to think about including icing along the lines of the hashes of subtrees, and other parts of a version control system.”

His conclusion asks for both kinds of icing: the comma for people, and a link for software. w3.org itself falls short: follow a link into its CVS, an older version control system, and the addresses look much like GitHub’s, with no way straight back. What he would like instead:

It would certainly be interesting for someone to make a web interface for a version control system which is all icing on the original cake, where at any point you can strip off the ,stuff and get back to the original file live on the web site Icing on the cake, 2016

What happened since

  • The hosted-copy pattern predates the note. GitHub Pages launched in 2008.
  • Discovery was patched, not fixed. npm’s package.json has a repository field, as the note says, but the live HTML page does not expose it.
  • Memento was already published, as RFC 7089 (December 2013).
  • Well-known locations were revised. RFC 8615 (May 2019) replaced RFC 5785 (2010). Both reserve /.well-known/ for metadata about a site, solving discovery per site rather than per document.

Questions 4

59.1 Your favourite recipe site keeps each recipe at one address. Invent comma addresses for a printable version and a shopping list. What must the site promise for them to work?
