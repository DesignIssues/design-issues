Chapter 59

Icing on the cake pattern: URIS of services and metadata close to the URI of the target

2016

Source Icing on the cake pattern: URIS of services and metadata close to the URI of the target, a Design Issues note by Tim Berners-Lee, 2016-12-01. read the original

The question

A small note from December 2016 with a status line reading “good enough for government work”, about a design decision every project makes without noticing: when a thing has tools attached to it, whose address comes first?

59.1 Two patterns

59.2 The complaint, stated twice

Berners-Lee names two failures of discoverability, and they are symmetrical:

One disadvantage of this pattern is that when you are in the project github web pages, it it is not at all obvious how to construct the URL above for the live site, and the project folks he to make an explicit link to it in their documentation. Icing on the cake, 2016

And in the other direction:

Another disadvantage is that when you are on the live site, either the acmedata.github.io site or the acmedata.com site, their is no obvious way of knowing that the github site exists or of finding its URI. Icing on the cake, 2016

He records the partial workaround honestly: a package manifest will sometimes carry the information, and in general a client fetching the page has no way to discover the link. The relationship between a published thing and the system that produced it exists in the world and not in the addresses.

59.3 Why the choice is architectural

The pattern names what a system treats as primary. In the first, the repository is the real thing and publication is an export, which is why the published address is arbitrary and the shape of the repository address is fixed. In the second, the published thing is the real thing and everything else is an accessory:

The live data is the center. This is the cake - this is the main purpose of the site: serving the web pages. That is the cake, and everything else is icing on the cake. Icing on the cake, 2016

The convention chosen matters less than the property it provides. Any character the addressing scheme reserves would do; the requirement is that adding it is a function of the address, so that a client, or a person, can derive the tool address from the work address without being told.

Berners-Lee lists what hangs off the base in his own case, and the breadth is the point: version control, access control, validation, link checking, format conversion, spell checking. Six tools, one address, no negotiation between them.

59.4 The same problem, generally

The chapter belongs in this volume because it is the placement question of Chapter 57 asked about tools rather than data. There too, a protocol for doing the thing is not enough: what is missing is a convention that lets one party find what another produced without prior arrangement.

And it is Chapter 3’s argument about information in names arriving from the other side. Putting the tool’s name in the address makes the address say which tool made it, which is information that will eventually be wrong. Putting the work’s name in the address and deriving the tool’s leaves the tool free to change.

What happened since

  • The tool-centric pattern won overwhelmingly. Publishing from a repository to a separate hosted address is how most of the Web is now deployed, with the two addresses unrelated.
  • Discovery was patched, not fixed. Conventions such as a repository field in a package manifest, or a link in a page footer, supply what this note asks for, by hand and inconsistently.
  • The general pattern persists where it was already established. Sites that adopted a suffix convention kept it, and it still allows new tools to be added without renegotiating addresses.
  • Well-known locations became the standard alternative. RFC 8615, of May 2019, reserves a path prefix for metadata about a site, which solves the same discovery problem at the site level rather than per document.
