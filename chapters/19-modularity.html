Chapter 19

Modularity

2007

Source

This chapter is about Modularity, a Design Issues note by Tim Berners-Lee, dated 2007-10-01.

Read the original at https://www.w3.org/DesignIssues/Modularity.html. The Design Issues notes are Tim Berners-Lee's personal notes and are not endorsed by W3C. This book is commentary; where it quotes, it attributes.

The question

Published on the W3C blog in January 2008 and copied here, then edited in 2010 after a comment from Noah Mendelsohn, this note has a subtitle that carries the argument:

Simple things make firm foundations Modularity, 2008

It is the only note in the collection that quotes a live specification argument at length and takes a side in it. The occasion was the state of the HTML5 draft, and the question is whether a specification that describes what browsers actually do can also be a specification other people can build on.

19.1 The tangle, in its author's own words

Berners-Lee quotes Ian Hickson, then co-editor of HTML5, describing why modularising the specification is harder than it looks. The passage is worth keeping whole, because it is a rare piece of honest engineering writing about coupling:

Note that it really isn't that easy. For example, the HTML parsing rules are deeply integrated with the handling of <script> elements, due to document.write(), and also are deeply integrated with the definition of innerHTML. Scripting, in turn, is deeply related to the concept of scripting contexts, which depends directly on the definition of the Window object and browsing contexts, which, in turn, are deeply linked with session history and the History object (which depends on the Location object) and with arbitrary browsing context navigation (which is related to hyperlinks and image maps) and its related algorithms (namely content sniffing and encoding detection, which, to complete the circle, is part of the HTML parsing algorithm). Ian Hickson, quoted in Modularity, 2008

The passage closes a circle deliberately: parsing depends on sniffing, which is part of parsing. Berners-Lee does not dispute the description. He disputes that it should be accepted.

19.2 The two reasons, and the second is the better one

The case is made briefly and in the right order:

There are lots of reasons for modularity. The basic one is that one module can evolve or be replaced without affecting the others. If the interfaces are clean, and there are no side effects, then a developer can redesign a module without having to deeply understand the neighboring modules. Modularity, 2008

Then the half that Chapter 1 calls the harder one:

The flip side is that a cleanly designed module designed as part of one system can be re-used in other systems. Modularity, 2008

Berners-Lee applies this to the drawing API introduced with the canvas element. His view is that the element belongs in the specification and the drawing API does not, and he notes that Hickson agreed in principle while observing that other parts needed splitting out more urgently and that nobody had volunteered to edit it.

The wish that follows is the reuse argument made concrete: that canvas and embedded SVG should work the same way, so that both could later be extended to three dimensions, and so that both could be plugged into other languages just as they are plugged into HTML.

19.3 Technology, not documents

One distinction saves the argument from pedantry. What matters is the independence of the technology, which need not align with the boundaries of documents. Berners-Lee then notes that it usually makes sense for them to align anyway, so that different people can review, edit and implement different parts.

19.4 Designing for a system that does not exist

The closing passage is the strongest statement in the collection of a position that appears everywhere in it:

The web architecture should not be seen as a finished product, not as the final application. We must design for new applications to be built on top of it. There will be more modules to come, which we cannot imagine now. Modularity, 2008

And the reason it matters, stated as a claim about what a clean interface gives its user:

Clean interfaces give you invariants, which developers use as foundations of the next layer. Messy interfaces introduce complexity which we may later regret. Modularity, 2008

The note ends with a request rather than a rule, which is unusual and rather disarming: let us try, as we make new technology, or plan a path for old technology, always to keep things as clean as we can.

What happened since

  • The split happened. The canvas drawing API was separated into its own specification, HTML Canvas 2D Context, and other parts of the monolith followed. HTML itself moved to the WHATWG Living Standard, where the material is maintained as one document with separately maintained companion specifications.
  • The circle was not broken. Parsing, scripting and navigation remain mutually dependent in the way Hickson described, and the dependency is now specified precisely rather than removed.
  • The reuse argument was vindicated. Custom elements and the shadow DOM, shipping from around 2016, gave the Web a way to plug components into HTML and into each other, which is the property section 19.2 asks for, arrived at by a different route.
  • The ladder kept extending. HTTP/2 and HTTP/3 replaced the lower layers without changing the URI-to-representation mapping above them, which is the invariant this note says clean interfaces provide.

Questions

19.1 Hickson's passage closes a circle. Identify the smallest change to the Web platform that would open it, and say what it would break.

19.2 Berners-Lee separates independence of technology from separation of documents. Give a case where one specification should define two independent technologies, and one where the reverse holds.

19.3 Take a module in a system you know. Could it be lifted into a different system unchanged? If not, name the dependency that prevents it.

19.4 The note claims clean interfaces give developers invariants. Name an invariant you rely on, and say what would have to change for it to fail.
