Chapter 19

Modularity

2007

Source Modularity, a Design Issues note by Tim Berners-Lee, 2007-10-01. read the original

The short version

HTTP carries HTML, images and much else without changing, because it never needs to know what it carries. The core parts of the HTML5 draft (parsing, scripts, windows, history) depended on one another in a circle. Berners-Lee asked for separable pieces, such as the canvas drawing commands, to be split out. The Web works because each layer (IP, TCP, HTTP) offers a simple interface to the next.

The question

HTTP has carried HTML, then images, PDF, SVG and JSON, each announced by a label such as image/png, without itself being changed for any of them. In 2007 the HTML5 draft was the opposite. Its editor, Ian Hickson, described a circle in which parsing, scripts, windows, history and navigation each depend on the next, and back to parsing. Berners-Lee’s response, a short W3C blog post in January 2008, has a five-word subtitle:

Simple things make firm foundations Modularity, 2008

The question is whether the parts that differ in kind, such as canvas drawing, can be lifted out so that each can change, and be reused, on its own. (The note was edited in 2010 after a comment from Noah Mendelsohn.)

19.1 The tangle, as HTML5’s editor described it

Ian Hickson, then co-editor of HTML5, explained why modularising HTML is harder than it looks:

Note that it really isn't that easy. For example, the HTML parsing rules are deeply integrated with the handling of <script> elements, due to document.write(), and also are deeply integrated with the definition of innerHTML. Scripting, in turn, is deeply related to the concept of scripting contexts, which depends directly on the definition of the Window object and browsing contexts, which, in turn, are deeply linked with session history and the History object (which depends on the Location object) and with arbitrary browsing context navigation (which is related to hyperlinks and image maps) and its related algorithms (namely content sniffing and encoding detection, which, to complete the circle, is part of the HTML parsing algorithm). Ian Hickson, quoted in Modularity, 2008

ParsingReading the page’s text into a structure the browser can work with
Script, document.write()A program in the page that can write more page while the page is still being read

Berners-Lee does not argue with the description. He asks for the parts that can be separated to be separated, quoting Laurens Holst’s point that modular pieces would be easier to grasp for reviewers and implementers.

His example is the canvas element: a blank rectangle in a page that a script can draw on. Its drawing commands work differently from the rest of HTML, which mostly sets and reads values in the markup. So does another part of the draft, a database inside the browser.

The element belongs in HTML, he argues, but the drawing commands belong in a separate document. Hickson agreed they should be split out in the long term, but said there were “much higher priority items” for anyone willing to edit. The W3C did later publish them separately; what happened to that split is at the end of this chapter.

19.2 Change and re-use: one property, two sides

There are lots of reasons for modularity. The basic one is that one module can evolve or be replaced without affecting the others. If the interfaces are clean, and there are no side effects, then a developer can redesign a module without having to deeply understand the neighboring modules.

The flip side is that a cleanly designed module designed as part of one system can be re-used in other systems. Modularity, 2008

Clean edges let a part be swapped out and, for the same reason, carried somewhere else.

The canvas request has this second side too: canvas and SVG should embed in HTML in just the same way, so both could be plugged into other languages.

19.3 Splitting a technology is not splitting a document

What matters, the note says, is the independence of the technology. Two later examples show the difference: HTML5 put two technologies, a markup language and a drawing interface, into one document; HTTP/1.1, one technology, was split across six RFCs in 2014. Berners-Lee adds that it usually makes sense for the boundaries to align anyway, so that different people can review, edit and implement different parts.

19.4 Designing for a system that does not exist

The note’s reason is a ladder: “The IP is simple, and so TCP can be powerfully built on top of it.” TCP’s simple byte stream in turn carries HTTP, and HTTP’s simple mapping of URIs to labelled data carries hypertext, data and scripting. The ladder is not finished:

The web architecture should not be seen as a finished product, not as the final application. We must design for new applications to be built on top of it. There will be more modules to come, which we cannot imagine now. Modularity, 2008

The note adds: “We should expect there to be many developers to come who will want to use the platform without looking under the hood.” They stand on an invariant, a promise that holds whatever happens above it. For HTTP: give it a URI and it returns data labelled with how to read it. HTTP/2 changed how messages are framed, and HTTP/3 (2022) moved HTTP off TCP, yet pages and links did not have to change.

Clean interfaces give you invariants, which developers use as foundations of the next layer. Messy interfaces introduce complexity which we may later regret. Modularity, 2008

It ends with a request rather than a rule:

Let us try, as we make new technology, or plan a path for old technology, always to keep things as clean as we can. Modularity, 2008

What happened since

  • The split happened, then was undone. The W3C published HTML Canvas 2D Context separately, as a Recommendation in 2015. In 2019 the W3C and WHATWG agreed that the WHATWG HTML Living Standard is authoritative, and it defines the canvas drawing commands inside HTML; in 2021 the W3C marked its separate Recommendation superseded.
  • The circle was not broken. As of 2026 the HTML Living Standard still specifies parsing, scripting and navigation as mutually dependent, in the way Hickson described.
  • A related kind of reuse arrived. Custom elements (page authors’ own tags) shipped in Chrome in 2016, a way to plug components into HTML.
  • The ladder kept extending. HTTP/3, standardised in 2022, runs over QUIC rather than TCP.
