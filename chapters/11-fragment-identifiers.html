Chapter 11

Fragment identifiers

1997

Source Fragment identifiers, a Design Issues note by Tim Berners-Lee, 1997-04-08. read the original

The question

Chapter 4 established that the fragment identifier stays on the client and that access specifications and fragment specifications are independent. This note, written in April 1997, says what follows from that: who decides what a fragment means, and what the decision makes possible.

It opens by correcting its own title, which is the sort of thing that makes these notes worth reading:

The URI reference is a thing you build by taking a URI for an information object, adding a “#” sign and then a Fragement identifier. (The last term is historical, so try not to thinl of it necessarily identifying a fragment). URI References: Fragment Identifiers on URIs, 1997

It is badly named, he says, because it can identify anything. The rest of the chapter is about how much work that misnomer turned out to do.

11.1 The axiom

One sentence carries the chapter:

Axiom. The significance of the fragment identifier is a function of the MIME type of the object.

Berners-Lee draws out the two consequences immediately. The fragment is opaque to the rest of the client: the HTTP engine can assume nothing about it. And the server is not even given it.

That second clause is the one people forget. A fragment is not sent over the network. It is applied after the response arrives, by whatever software was selected to handle the media type that came back.

11.2 The invitation to invent

Berners-Lee spends most of the note on what the axiom permits, and the list reads as a set of predictions:

for a 3D object the fragment ID could give a viewport. For a music object, the Fragment ID could give a section in time, or a set of parts, or it could include a suggested tempo. For future versions of HTML, the fragment ID could be made more powerful to include a range or “ladder” reference to a part or parts of the SGML element tree by position. A very useful fragment ID for plain text would allow ranges to be quoted by line and character number URI References: Fragment Identifiers on URIs, 1997

The procedural consequence follows, and it is the note’s concrete recommendation:

The fragment ID spec for a new MIME type should be part of the MIME type registration process. URI References: Fragment Identifiers on URIs, 1997

11.3 Why RDF namespaces end in a hash

The section on the Semantic Web is the argument Chapter 7 would restate at length five years later, and it is sharper here because it is shorter.

A fragment on an RDF document identifies not a part of the document but whatever thing the document describes under that name. Why must it be a fragment? Because a hashless HTTP URI necessarily identifies a document: a client that understands HTTP can conclude that much from the protocol alone, and can conclude it even if the owner runs no server, since a 404 is still a statement about a document.

This means that identifiers for arbitrary RDF concepts should have fragment identifiers. This, in turn, means that RDF namespaces should end with “#”. URI References: Fragment Identifiers on URIs, 1997

This inference is what the resolution of Chapter 8 overturned. The 2005 compromise denies the premise: a client may not conclude from the protocol alone that a hashless URI names a document, only from a 200 response. Reading the two chapters together shows exactly which sentence had to give way.

11.4 The bug he recorded and did not fix

The note contains one of the collection’s rare admissions of an unresolved defect, flagged in its own heading as a known bug. If content negotiation selects between media types that do not share a fragment specification, a fragment valid for one may be meaningless in the other.

Berners-Lee dates the change in severity himself. In 1997 it did no harm, because HTML was effectively the only type that used fragments and others ignored them, and falling back from a view to the whole document was acceptable. In a passage added around 2001 he notes it has become more of a problem, and records the proposal that the requested fragment be sent to the server as a hint so that the two could negotiate an equivalent.

That proposal was never adopted. The fragment is still not sent.

11.5 Two kinds of bookmark

A closing section raises a user-interface consequence that has never been addressed. When a fragment is attached to a URI that is generic in any dimension, the fragment may fail to denote anything in some specific version. Berners-Lee argues the client should therefore offer a choice: a bookmark to the whole living document, a bookmark to a specific part of a frozen version, or something between.

No browser offers it. The problem is real and is usually met by the link silently landing at the top of the page.

What happened since

  • The axiom is normative. RFC 3986, of January 2005, specifies that fragment semantics are defined by the media type of the retrieved representation, and RFC 6838, of January 2013, requires media type registrations to state fragment identifier considerations. Section 11.2’s recommendation became process.
  • The predictions came true, one at a time. Media Fragments URI 1.0 became a W3C Recommendation in September 2012, giving time ranges and spatial regions. Text fragments, addressing a passage by quoting its words, shipped in Chrome in 2020, which is the plain-text range proposal arriving twenty-three years late.
  • The hash-only rule for vocabularies did not hold. The resolution of June 2005, described in Chapter 8, permitted hashless URIs for things, which is the practice section 11.3 argues against.
  • The known bug is still open. Fragments are still not sent to the server, and negotiation across types with incompatible fragment schemes still silently degrades to the whole document.

Questions 4

11.1 The fragment is never sent to the server. Name two things this makes impossible and one privacy property it provides.

11.2 Section 11.3 argues that a hashless HTTP URI necessarily names a document, even when no server runs. Reconstruct that argument, then say precisely which step the 2005 resolution denies.

11.3 Design a fragment identifier syntax for a media type you work with. State what it must not assume about HTTP.

11.4 The two-kinds-of-bookmark problem has never been solved in any browser. Propose an interface for it, and say why the absence of one has cost so little.
