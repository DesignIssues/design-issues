Chapter 11

Fragment identifiers

1997

Source Fragment identifiers, a Design Issues note by Tim Berners-Lee, 1997-04-08. read the original

The short version

In an address such as https://en.wikipedia.org/wiki/World_Wide_Web#References, the part after the # is the fragment. The browser keeps it and never sends it to the server. Once the document arrives, the browser decides what the fragment means from the kind of file that came back. So each new kind of file can invent its own meaning for #, and if the server switches formats, the link can quietly stop working.

The question

Chapter 4 established that the fragment identifier stays on the client and that access specifications and fragment specifications are independent. This note, written in April 1997, asks who decides what a fragment means, and what that decision makes possible.

It opens by correcting its own title:

The URI reference is a thing you build by taking a URI for an information object, adding a “#” sign and then a Fragement identifier. (The last term is historical, so try not to thinl of it necessarily identifying a fragment). URI References: Fragment Identifiers on URIs, 1997

That loose word let # name parts of pages, moments in videos, and things that are not documents at all.

11.1 The axiom

Axiom. The significance of the fragment identifier is a function of the MIME type of the object.

A MIME type is the label a server attaches to say what kind of data it is sending, such as text/html for a web page or application/pdf for a PDF.

Two consequences follow. The fragment is opaque to the part of the browser that fetches documents, which he calls the HTTP engine. And the server is not even given it: the fragment is applied after the response arrives, by whatever software handles the returned type (Figure 11.1).

11.2 The invitation to invent

Most of the note is about what the axiom permits, and reads as predictions:

for a 3D object the fragment ID could give a viewport. For a music object, the Fragment ID could give a section in time, or a set of parts, or it could include a suggested tempo. For future versions of HTML, the fragment ID could be made more powerful to include a range or “ladder” reference to a part or parts of the SGML element tree by position. A very useful fragment ID for plain text would allow ranges to be quoted by line and character number URI References: Fragment Identifiers on URIs, 1997

Most of the list has since been built, though not always as he imagined:

1997 predictionWhat exists now
A viewport into a 3D objectNothing standard
A section in time of a music objectMedia Fragments (2012): #t=10,20 for seconds 10 to 20 of audio or video
A range of an HTML documentText fragments (2020): #:~:text= picks out a passage by quoting its words, rather than by position in the element tree
Line and character ranges in plain textRFC 5147 (2008): #line=10,20 and #char= for text/plain; text fragments also serve

The note’s concrete recommendation follows:

The fragment ID spec for a new MIME type should be part of the MIME type registration process. URI References: Fragment Identifiers on URIs, 1997

11.3 Why RDF namespaces end in a hash

This is the argument Chapter 7 would restate at length five years later. A fragment on an RDF document identifies not a part of the document but whatever thing the document describes under that name. Why must it be a fragment? The reasoning runs in three steps:

  1. Asking for an http: address always gets back a document, a message about a document (that it has moved, say, or is unavailable), or nothing at all.
  2. So an http: address without a hash names a document. A client can conclude this from the protocol alone, even if no server runs, because an error saying the document is unavailable is still about a document.
  3. So a person, a dog or a concept cannot have a hashless address of its own. It needs a # name inside a document.

Concretely, http://example.org/people names the document, and http://example.org/people#alice names Alice herself, the person the document describes. For a vocabulary, whose terms are all built on one shared prefix called its namespace, the consequence is direct:

This means that identifiers for arbitrary RDF concepts should have fragment identifiers. This, in turn, means that RDF namespaces should end with “#”. URI References: Fragment Identifiers on URIs, 1997

This inference is what the resolution of Chapter 8 overturned. The 2005 compromise denies step 2: a client may conclude that a hashless URI names a document only from a successful response, not from the protocol alone.

11.4 The bug he recorded and did not fix

The note flags one unresolved defect as a known bug. It concerns content negotiation: a server may hold one document in several formats and pick one per request. If the formats do not share a fragment specification, a fragment valid in one may be meaningless in the other, as Figure 11.3 shows.

In 1997 it did no harm, because HTML was effectively the only type that used fragments, and falling back to the whole document was acceptable. In a passage added around 2001 Berners-Lee notes it has become more of a problem. He records proposals to add the fragment to the HTTP request, and suggests that warnings sent with the response, or new protocols that pass the fragment as a hint, could let server and client negotiate an equivalent fragment.

None of these was adopted for the Web. The fragment is still not sent.

11.5 Two kinds of bookmark

A closing section raises a user-interface consequence. Many addresses are generic: their content can change by language, version or format, so a fragment may denote nothing in some specific version. The client, he argues, should offer a choice: a bookmark to the whole living document, a bookmark to a specific part of a frozen version, or something between.

No browser offers it; the link usually just lands at the top of the page. Some sites offer half the choice themselves: Wikipedia’s “Permanent link” points to one fixed revision of an article, and GitHub can link to a file as it stood at a specific commit. Both are the “frozen version” bookmark, supplied by the site rather than the browser.

What happened since

  • The axiom is normative. RFC 3986, of January 2005, specifies that fragment semantics are defined by the media type of the retrieved representation, and RFC 6838, of January 2013, gives every media type registration template a field for fragment identifier considerations.
  • The predictions came true, one at a time. Media Fragments URI 1.0 became a W3C Recommendation in September 2012, giving time ranges and spatial regions. Text fragments, addressing a passage by quoting its words, shipped in Chrome in 2020: the HTML range proposal arriving twenty-three years late, by quoted words rather than by position in the element tree. Line and character ranges for plain text came with RFC 5147 in April 2008.
  • The hash-only rule for vocabularies did not hold. The resolution of June 2005, described in Chapter 8, permitted hashless URIs for things, which is the practice section 11.3 argues against.
  • The known bug is still open. Fragments are still not sent to the server, and negotiation across types with incompatible fragment schemes still silently degrades to the whole document.

Questions 4

11.1 The fragment is never sent to the server. Name two things this makes impossible and one privacy property it provides.

11.2 Section 11.3 argues that a hashless HTTP URI necessarily names a document, even when no server runs. Reconstruct that argument, then say precisely which step the 2005 resolution denies.

11.3 Design a fragment identifier syntax for a recipe, a spreadsheet or a map. State what it must not assume about HTTP.

11.4 The two-kinds-of-bookmark problem has never been solved in any browser. Propose an interface for it, and say why the absence of one has cost so little.
