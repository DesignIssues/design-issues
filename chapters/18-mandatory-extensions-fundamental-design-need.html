Chapter 18

Mandatory extensions: A fundamental design need

2000

Source

This chapter is about Mandatory extensions: A fundamental design need, a Design Issues note by Tim Berners-Lee, dated 2000-01-01.

Read the original at https://www.w3.org/DesignIssues/Mandatory.html. The Design Issues notes are Tim Berners-Lee's personal notes and are not endorsed by W3C. This book is commentary; where it quotes, it attributes.

The question

This is the shortest note in the collection, four hundred and forty-eight words, and it names the gap that Chapters 16 and 17 both circle without closing. Free extension lets anything be added. Nothing lets a publisher say that an addition must be understood.

Berners-Lee states the cost in one sentence, and the sentence is worth reading twice:

Historically the lack of such a “mandatory field” has led to a complete inabaility to get any particular guaranteed behaviour be clients on the web. Mandatory extensions, 1998

Not reduced reliability. A complete inability. If every extension may be ignored, then no extension may be relied upon, and the set of things a publisher can count on is frozen at whatever was in the base specification.

18.1 The requirement

The demand is small and is stated twice for emphasis. A language must provide not only for its own extension but for a way to say whether a given extension is optional. Berners-Lee calls this a fundamental key to smooth evolution from one version of a language to the next, and notes that it can be done term by term or in bulk for a whole language, stated in the document or in the schema.

The note was written when XML namespaces were arriving, and the complaint is that they solve half the problem:

XML provides in Namespaces a standard way of extending languages. It should also, in my opinion, provide a standard way to specify mandatopry or optional extensions. Mandatory extensions, 1998

18.2 Three things to do with something you do not understand

The heart of the note is a taxonomy so small it can be held in the head, and it is more useful than its length suggests. Meeting an element it does not recognise, a processor has exactly three sound options, and which one is correct depends entirely on what the element means.

The examples in the figure are his. A logical negation must stop a processor, because ignoring it inverts what the document says. A comment may be dropped whole. Emphasis should be unwrapped, since the text inside it still belongs to the document.

The observation that matters is that the markup gives no clue which is which. The rule inherited from Internet mail always chooses the third. That is correct for presentational markup, harmless for comments, and dangerous for anything that changes meaning.

18.3 Sublanguages

The second proposal is smaller and has had a longer afterlife. Berners-Lee wants a language to be able to declare itself a sublanguage of another:

The simple assertion that language A is a sublanguage of language B means that the writer's intent is preserved if a dpcument in language A is converted into a document in language B just by relabelling every term as being from langauge B. Mandatory extensions, 1998

A receiver that knows only B can then process a document in A by treating the namespace as though it were B. The practical constraint he attaches is the important part: the assertion must be simple enough to put in the document, so that the receiver need not dereference a schema to act on it.

This is the same instinct as the last requirement of Chapter 17. Whatever a processor needs in order to cope with the unfamiliar should travel with the document, not wait at the end of a network request.

What happened since

  • The proposal was not adopted for XML. No standard way to mark an extension mandatory or ignorable was added to XML or to namespaces. The gap this note names is still open.
  • It was adopted almost everywhere else. HTTP had the Mandatory extension mechanism under discussion when this was written, and the pattern survives in modern protocols: critical extensions in X.509 certificates, which fail validation when unrecognised, and TLS extensions with defined must-understand behaviour, both implement exactly this distinction.
  • The three-way taxonomy became ordinary practice. Forward-compatible binary formats distinguish fields that may be skipped from those that must be understood, and carry the distinction in the encoding rather than in a schema, which is what section 18.2 asks for.
  • HTML chose the third option permanently. The HTML5 parsing rules, specified from 2008 onward, define unwrapping behaviour for unknown elements exactly, which removes the ambiguity without supplying the mandatory flag.

Connections

The inability this note names is the disadvantage of free extension recorded in Chapter 16, and the requirement it makes is the one Chapter 17 stops short of. The tolerance principle that produced the old rule is Chapter 1, and its reconsideration is Chapter 23.

Questions 4

18.1 Take a markup or data format you use and find an element or field for which each of the three behaviours would be correct. What in the format, if anything, distinguishes them?

18.2 A publisher wants to add a feature that consumers must not ignore. Under free extension, what can the publisher do instead, and what does it cost?

18.3 The sublanguage assertion must be simple enough to travel in the document. Write such an assertion, and say what a receiver can safely do with it.

18.4 X.509 marks some extensions critical, so an unrecognised one fails validation. Explain why a certificate can afford this and a Web page cannot.
