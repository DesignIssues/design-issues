Chapter 3

The Myth of Names and Addresses

1996

Source The Myth of Names and Addresses, a Design Issues note by Tim Berners-Lee, 1996-12-19. read the original

The short version

Everybody has clicked a link and got an error page. The usual diagnosis is that web addresses are merely addresses, and that what we need instead are proper names, which would stay with a thing wherever it went.

This chapter argues that the distinction is a myth. Two of Berners-Lee’s own stories turn it upside down. In one, a server’s owners could promise that its IP address would last, but could not yet say what its name would be. In the other, information on the Web’s first server had to give up its name although the information itself was unchanged. What replaces the distinction is a genuine dilemma that technology alone cannot settle.

The question

People designing the Web had argued at length over whether it needed two kinds of identifier: names, which stay with a thing for life, and addresses, which change when it moves. Berners-Lee records that the word “identifier” had been chosen precisely to side-step the question, and that the evasion failed:

historically, that did not prevent a quagmire of circular discussion which in some circles paralyzed any forward progress. The Myth of Names and Addresses, 1996

This note, written in December 1996 as the second of his axioms of Web architecture, sets out to end the argument. It proposes no new naming scheme; it replaces a distinction with a trade-off.

3.1 Names stay, addresses move: the belief

The belief is learned young and from good examples. Computing students are taught that a name is something a person chooses and reads, while an address is something a machine uses to find a location: a variable called total in a program versus the memory slot where it sits. The lesson generalises to two kinds of object: names, which follow a thing wherever it resides, and addresses, which change when it moves.

The Internet supplies the most familiar case. A domain name such as pegasus.cs.foo.edu is meant for people. To use it, a computer asks a directory server run by Foo University, which answers with a number called an IP address, written as four numbers such as 192.0.2.17. The network’s routers, the machines that pass messages along, then use that number to find a particular computer. So the domain name looks like the name and the IP address looks like the address.

Berners-Lee’s counter is that the distinction is an illusion produced by not looking far enough down. The only true location is a point in physical space, and between it and anything one would call a name or an address there is a long chain of look-ups. The domain name is one step in that chain; the IP address is simply the next. Even an IP address can be given to another machine, though only one nearby in the network, because part of the number says where to route. A filename, likewise, is looked up through directory tables to find the places on a disk that hold the file.

From which he draws the generalisation that replaces the distinction:

we see that the constraint on how you can re-use an address is a function of what information is in the address. The Myth of Names and Addresses, 1996

3.2 Two names that hung on who was in charge

The Australian server. In the early days Berners-Lee kept a list of every Web server he knew of. A group in Australia sent details of a new server of botanical information, giving its IP address. He asked for its domain name instead. They replied that the domain name would depend on which university department ended up responsible for the server, which a reorganisation had left unsettled, but that they could guarantee the IP address would stay the same for a long time. The address was the part they could promise; the name was the part they could not.

info.cern.ch. The first Web server, at CERN, held among much else the master list of Web servers. When coordination of the Web moved from CERN to MIT and the new World Wide Web Consortium (W3C), the information came to be maintained in America while its name still said CERN. CERN then asked that the name no longer be used, since it could not take responsibility for content it did not control. It also had a standing policy that its names must never point at machines off its own site. Every link into info.cern.ch had to be changed to point into w3.org.

In both stories, the name depended on a claim about authority, and the authority changed or was unsettled.

3.3 Reading a URI for its future breakages

Berners-Lee then takes a typical student address of the period, produced by servers that simply mapped URLs onto the file system, and pulls it apart: 

http://pegasus.cs.foo.edu/disk1/students/romeo/cool/latest/readthis.html

Of each segment he asks what change in the world would make it wrong (Figure 3.3). Some verdicts are blunt: disk1 is “clearly a mistake”, and of cool and latest he says the student “has not been very wise with his choice of path name”. The final .html names a format, which makes it awkward to offer the content in another format later, such as audio for blind readers. Even romeo is a weak point: if the document is published or handed to another maintainer, the name must change, as info.cern.ch’s did.

The surprise is the verdict on the segment that says nothing:

Perhaps the unlikely to change piece of information in the URL “readthis” as it contains no information at all, just like the proverbial “click here”. Effectively, it is a random name assigned to the document and as such, is perhaps the safest part of the path. The Myth of Names and Addresses, 1996

Meaninglessness is durability; the rest of the note formalises this. The same game, the note adds, can be played “with almost any name and address in any system”.

3.4 The naming problem: lookup or longevity

To dereference a name is to use it to fetch the thing named, by asking whoever is responsible for it. That is what a browser does with a link. Berners-Lee states the dilemma:

The naming problem: if you put information in a name, it decreases its longevity; if you don't you can't dereference it to a resource. The Myth of Names and Addresses, 1996

Dereferencing requires information. Many names are handed out hierarchically, each level by the authority above it, and the look-up follows the same path. Berners-Lee’s analogy is a street name: to find out where the new “North Street” is in a small town, one asks that town for the definitive answer. In the same way, to find pegasus.cs.foo.edu one must ask a server controlled by Foo University. The information in the name is what routes the question.

The alternative exists. Every e-mail message carries a Message-ID, a string that need only be unique. It cannot be used to fetch the message, because there is nobody to ask. What it does support is equality: two copies with the same Message-ID are the same message. Within a finite collection, such as one mailbox, one can also look a message up by it; on a global scale one cannot. Berners-Lee suggests such strings be called identifiers rather than names.

3.5 Persistence is a contract

Two ends of the scale

Berners-Lee tests the information-free end of the scale in Figure 3.4 and rejects it. One could keep a worldwide hash table, in effect one giant shared list of randomly generated names, each pointing to its resource. That would work technically, but it would impose one funding model and one quality of service on everybody, with no way to pay more for a name that lasts longer.

At the other end sit hierarchical systems such as the domain name system. Here a name leads to an authority, and the only way to keep the name working is a contract with every organisation involved in looking it up. He sketches what such a contract might look like: the Foo University alumni association runs a service offering names such as 

http://alumni.foo.edu/1998/romeo/202-aab

to any graduate who pays their dues, and keeps each one working indefinitely, “perpetual care” in the note’s phrase, in return for an endowment, a lump sum paid once and invested so that its income covers the cost for ever. Persistence, in other words, is a contract between organisations, not a property of a protocol.

Organisations dissolve, but one can take over another’s archives. For that he floats a mechanism the Web never adopted in that form: a syntax for putting a date into a domain name, so that an agent failing to resolve info.cern.ch could look for info.cern.ch.1994 and find the archive server holding that space as it then stood.

Two proposals

The note makes two proposals. The first is that a new URI scheme’s specification should describe the name-like and address-like properties of its identifiers, so that users know what to expect. That turns the name/address split into a scale to be documented. The second concerns how long a name will last, a quality of service whose standard levels, he suggests, librarians and archivists are suited to define:

Metadata should be used to express the quality of service for the binding between a URI and a resource. The Myth of Names and Addresses, 1996

A name, in this view, lasts only as long as somebody’s promise to keep it working, and that promise is itself worth stating.

What happened since

  • The name and address split was decided by disuse. The Uniform Resource Name effort produced RFC 2141 in 1997 and a revision, RFC 8141, in April 2017, but URN schemes never became the general answer. HTTP URIs carried both roles, which is the outcome this note argues for.
  • Paid persistence arrived, as a contract. The Handle System and the Digital Object Identifier, with the International DOI Foundation founded in 1998, supply exactly what is described here: an organisation funded to keep resolution working, with the fee attached. The technology is secondary to the undertaking.
  • Time-based access was built, differently. RFC 7089, published in December 2013, specifies Memento, which asks for a resource as it was at a given datetime using a header rather than a dated hostname. The requirement Berners-Lee described was met; his syntax was not.
  • The second anecdote acquired an ending. CERN restored the first website in 2013 and served it again under info.cern.ch, in a project marking twenty years since CERN released the Web software into the public domain in April 1993. The URI outlived the reorganisation that retired it, because an organisation chose to make it so.

Questions 4

3.1 If “readthis” is the safest part of the path, why not name everything with random strings? Answer using the naming problem as stated.

3.2 In both anecdotes the responsible party changed while the information kept its identity. Describe a third case from your own experience, and identify which segment of the identifier carried the authority claim.

3.3 A Digital Object Identifier such as 10.1000/182 begins with a registrant prefix (here 10.1000), which is information about authority. By the argument of this chapter, what threatens its longevity, and what mitigates the threat?

3.4 Berners-Lee rejects a global hash table of random names because it imposes one funding model. Who would pay to keep such a table running? Does the same objection apply to content-addressed systems, where a file’s name is computed from its contents?
