Chapter 38

Interpretaion properties for units and languages

2000

Source Interpretaion properties for units and languages, a Design Issues note by Tim Berners-Lee, 2000-02-28. read the original

The question

This note ends with a line its author wrote to himself and never acted on:

@@@Needs circle-and-arrow pictures for each attempt. Interpretation properties, 1998

Figure 38.1 supplies them. The question is small to state and turns out to reach everywhere: how do you record that a string is in a particular language, or is a measurement in particular units, or is an encoding of something else?

The answer generalises into a modelling pattern that applies far beyond the notation it was written for.

38.1 Three attempts

Berners-Lee works the problem by getting it wrong twice, which is why the note teaches better than a statement of the answer would.

The first attempt’s flaw is expressive. A language tag hung on the person cannot record two names in two languages, and since the tag is not obviously attached to the name, automatic processing is ruled out. Berners-Lee notes why it persists anyway: it keeps the structure flat, and older header formats can express nothing else.

The second attempt’s flaw is that it asserts something false. He tests it with one word:

After all, the string “Tim” - is that English (short for Timothy? or French (short for “Timothé”)? Interpretation properties, 1998

A system asserting that the string itself is fundamentally English would simply not be representing the case.

38.2 The pattern, named

Natural languages, encodings, and similar relationships between one abstract thing and another, are best modeled in RDF as properties. I call these Interpretation properties in that they express the relationship between one value and that value interpreted (or processed in the imagination) in a specific way. Interpretation properties, 1998

Once the pattern is named, it turns out to be everywhere: a base-sixty-four encoding, a hash, a canonicalisation, a type coercion from a moment in time to a date, a measurement in particular units. Each is a relation between a thing and a representation of it under some reading.

38.3 What it buys: nesting

The payoff is that interpretation properties compose, and composition records order without anybody having to specify it in prose.

Berners-Lee gives an example that nests canonicalisation inside hashing inside encoding, and says what it states: that a given string is the base-sixty-four encoding of the hash of the canonicalised form of a page. Then the comparison that makes the case:

Compare this withe the HTTP situation in which the headers cannot be nested, and the encodings and compression and other things applied to the body are mentioned as unordered annotations, and the spec has to provide a way of making the right conclusion about which happened in what order. Interpretation properties, 1998

This is the fourth symptom from Chapter 32, cured. Where a flat format must push the ordering into the specification’s fine print, nested interpretation properties carry it in the data.

38.4 Where it fails

The note is unusual in reaching a negative conclusion about its own proposal, and saying so in the summary.

Representing the interpretation of one string as an abstract thing can be done easily with RDF properties. This helps make a clean accurate model. However, using the concept for datatypes in RDF is incompatible with RDF as we know it today. Interpretation properties, 1998

The obstacle is structural. Modelling the representation explicitly requires an extra node between the thing and its string, and the ordinary way of writing data does not have one. Berners-Lee considers changing how every literal is parsed, so that each gets an abstract node, and calls the prospect frightful. He considers treating every literal as standing for the set of all things it could represent, and calls that frightful too, because equality stops working as it did.

The section ends with a note to himself, dated January 2001, that there is no clear way forward. The problem was real and the pattern was right and the two could not be reconciled in the notation available.

38.5 The list of questions worth keeping

Before giving up, Berners-Lee sets out what any datatype designer is actually choosing between, and the list is the most portable thing in the note.

QuestionWhy it matters
Can you tell the type from the representation in every case?Decides whether a parser needs a schema
Are values of different datatypes distinct? Is 1 the same as 1.0?Decides what equality means
Is the set of datatypes extensible?Decides whether anyone else may add one
Does representation equality imply value equality?Decides whether comparison may be textual
Does value equality imply representation equality?Decides whether a canonical form is required

He records that the answers the day’s datatype system gave were no, yes, yes, yes, no, and the snag that follows: you cannot compare two values unless you know their datatypes.

What happened since

  • The incompatibility was resolved by changing the model. RDF 1.1, a W3C Recommendation of February 2014, made every literal carry a datatype and made language-tagged strings a datatype of their own, which places the reading on the literal rather than between the thing and the string. Attempt two won, formalised.
  • The pattern survived where it was needed most. Units of measure, which the note adds in 2006, are still modelled as a relation between a quantity and a number, because the alternative genuinely does not work: ten is not a length.
  • Nesting stayed the right answer for encodings. Signature and hashing formats describe canonicalisation, digest and encoding as an ordered chain, which is section 38.3’s argument.
  • The flat-header problem persists. Unordered annotations describing an ordered process remain common, and the ordering is still carried in prose.

Connections

The symptom this chapter cures is the last of the four in Chapter 32, and the graph model it works in is the same.
