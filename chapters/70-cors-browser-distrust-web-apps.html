Chapter 70

CORS: Browser Distrust of Web Apps

2018

Source CORS: Browser Distrust of Web Apps, a Design Issues note by Tim Berners-Lee, 2018. read the original

The short version

Browsers treat every web app as hostile: a script may talk only to the site it came from, unless other servers opt in with CORS headers. Extra rules for logins and caches made opting in hard. Berners-Lee calls it the web’s worst design.

The question

Open government data can be readable by anyone in a browser tab and yet out of reach of a web app. Berners-Lee’s note of July 2018 explains how that came about, and calls the design responsible “the worst piece of design in the whole web”. It opens with a borrowed image:

Ted Nelson talks about the two gods of Literature, the reader and the writer. They are each invincible: the writer can write whatever they want, and the reader can if they chose read nothing the writer has written. Here we have though three gods, the reader, the writer and the spy, and none of them are omnipotent. Authorizing Web Apps and CORS, 2018

70.1 Every app presumed an attacker

The browser’s operating principle is rarely written down:

The assumption that a web browser makes is that whenever the user is using a web app, that the web app is trying to attack the user. Authorizing Web Apps and CORS, 2018

So the browser limits the app and gives it only “limited error messages or information about the way it is being disabled”, a silence that returns in Section 70.7:

This is therefore a very hostile environment for which to program, unless the app is something rather trivial which does not access data on the web. Authorizing Web Apps and CORS, 2018

70.2 The attack that caused it

The note traces this to cross-site scripting (XSS), using the name loosely: textbook XSS injects script into a trusted site. A script is a small program a page carries and the browser runs.

Forbidding scripts all network access could not stand: a bank’s own page must fetch more data from the bank. So a script may talk freely to its own origin, the protocol and domain of an address (say, https://www.bankofamerica.com), and to nothing else: the same-origin policy of Chapter 68.

This allows banks to work pretty well. Authorizing Web Apps and CORS, 2018

70.3 What the wall shut out

The wall also blocks good apps: a tool that checks another page cannot read it. And when governments began publishing open data, there was “a flourishing of sites which loaded data from many different sites and provide a ‘mashup’ of the data — a combined visualization of data from many sources …”. Such sites, the note says, no longer work.

Chapters 51 and 53 argue for exactly this combining.

70.4 The shape of the problem

Mapped onto the attack (the book’s reading), the three gods become:

CharacterIn the attackWhat they want
The readerAliceTo use any app on any data she can reach
The writerThe site or app she chose to useTo fetch and combine data for her
The spyMalloryTo borrow Alice’s access and carry data away

Chapter 54’s design keeps each person’s data in their own store, so an app reading it always reaches across origins. Every mechanism should stop the spy without disabling the other two, yet the browser distrusts the writer, the party Alice chose.

70.5 Opting in, one header at a time

A browser cannot tell a private webcam from open government data, and webcams could not be changed, so publishers must opt in under Cross-Origin Resource Sharing (CORS) by adding a header, a labelled line sent with a reply:

HeaderMeaningExample from the note
Access-Control-Allow-Origin: *Any origin may read thisPublic data
Access-Control-Allow-Origin: a named originOnly that origin may read thisA bank letting its credit card company’s code reach customer data

For publishers this meant “a huge amount of work”, which “in many cases for many reasonable reasons was not done, leaving the data available to browsers, but unavailable to web apps”: the paradox of the opening.

Even ordinary reply headers, such as Link, are hidden unless the server lists them in yet another header. The browser may also first send a preflight request (HTTP OPTIONS). The console may show one request, but the round trips have increased.

70.6 The twist: logins break the simple fix

The designers feared * was a “footgun”, something system managers could too easily shoot themselves in the foot with by putting it on pages tailored to each user. So browsers refuse it when a request carries credentials, such as a login; the server must name the origin exactly.

That splits the web in two: requests sent with a login, and requests sent without. A code library that asks the browser to fetch something cannot know whether a login will be attached, so it cannot rely on *. Public data servers were therefore told to copy back whatever origin asked (origin reflection): active code, not a configuration line. “There was a campaign to explain this to data publishers, and code snippets were widely distributed.”

Berners-Lee proposes a fixed header, PUBLIC_AND_UNCUSTOMIZED, instead. A manager who put it on private or personalised data, he argues, would have no one else to blame. “But that is not how CORS was done.”

70.7 Public data, cached once per app

Browsers keep copies of replies in a cache; a copy marked for origin A, reused for an app from B, is blocked “to the puzzlement of user and developer”. One more header, Vary: Origin, makes the cache keep a copy per origin.

An epilogue adds a last straw: Chrome 59, and Firefox in July 2018, reused cached replies across origins despite Vary: Origin.

The verdict: “The CORS design most [sic] go down in history as the worst piece of design in the whole web.”

Against that background Solid (Chapter 54) must be “immune to XSS attacks”, with data “public and private under user’s control”, and apps “deemed trustworthy by various different social processes”.

What happened since

  • The cache bug was reported again. On 12 July 2019 Michiel de Jong published “CORS bug in several browsers”, cited in the note’s follow-up, and opened bugs with Chrome and Firefox.
  • A header name. The header that exposes reply headers, Access-Control-Allow-Headers in the note, is Access-Control-Expose-Headers in the specification.
