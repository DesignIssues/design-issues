Chapter 70

CORS: Browser Distrust of Web Apps

2018

Source CORS: Browser Distrust of Web Apps, a Design Issues note by Tim Berners-Lee, 2018. read the original

The question

Written in July 2018 and described as a very much simplified backgrounder, this note explains the mechanism that makes the architecture of Chapter 54 difficult to build. It opens with a borrowed image and then adds a third figure to it.

Ted Nelson talks about the two gods of Literature, the reader and the writer. They are each invincible: the writer can write whatever they want, and the reader can if they chose read nothing the writer has written. Here we have though three gods, the reader, the writer and the spy, and none of them are omnipotent. Authorizing Web Apps and CORS, 2018

70.1 The assumption

The browser’s operating principle is stated in a form most people who write applications have never seen written down:

The assumption that a web browser makes is that whenever the user is using a web app, that the web app is trying to attack the user. Authorizing Web Apps and CORS, 2018

Not may attack: is attacking. And the consequence Berners-Lee draws is about what it is like to build anything in that environment:

This is therefore a very hostile environment for which to program, unless the app is something rather trivial which does not access data on the web. Authorizing Web Apps and CORS, 2018

The second clause is the one that matters for Volume VI. An application that touches only its own server is fine. An application whose whole purpose is to work with data held elsewhere is programming against a system designed to stop it.

70.2 The attack that caused it

The first instinct, Berners-Lee says, may have been to forbid a script any network access at all, and that clearly could not stand: a bank’s own page must fetch more data from the bank. So the rule became one of sameness. A script from a domain may talk freely to that domain, and to nothing else.

This allows banks to work pretty well. Authorizing Web Apps and CORS, 2018

70.3 What it forbids

The note then asks the question that the rest of Volume VI depends on: are there uses where this does not work? Two are given, and both are things one would want.

The first is a service that assesses another page, which cannot reach the page it is meant to assess. The second is the one that dates the note and explains its tone:

When a large amount of open public data started to become available from governments and so on, there was a flourishing of sites which loaded data from many different sites and provide a “mashup” of the data — a combined visualization of data from many sources which would typically l was to insights that you would not get from one data source alone. Authorizing Web Apps and CORS, 2018

Combining data from several sources is the entire argument of Chapters 51 and 53. The browser’s default forbids it, and the mechanism named in the title is the permission a server must grant to allow it: the data’s owner must say, explicitly, that other origins may read it.

70.4 The shape of the problem

The three figures of the opening are what makes the note more than a description. Nelson’s pair are each invincible in their own domain. Adding a third party who wants to observe or divert makes all three fallible, and every mechanism described here is an attempt to constrain the third without disabling the first two.

The result is a default of distrust applied to the party the user chose to use. Chapter 54’s response is to move the data out from behind the boundary entirely, so that an application reaching the user’s own storage is doing the ordinary thing rather than the forbidden one.

What happened since

  • The permission became universal and awkward. Granting cross-origin access is now routine for any public data service, and misconfiguring it remains one of the most common causes of both broken applications and accidental exposure.
  • The boundary kept being redrawn. Cross-origin isolation policies introduced from 2020 added further headers a site must set, which is the symptom Chapter 67 names.
  • The mashup era ended. Combining data from many sources in the browser largely gave way to combining it on a server, partly for this reason.
  • The attack class survived every mitigation. Script injection remains among the most common vulnerabilities, addressed now by content policies and template escaping rather than by origin rules alone.

Connections

The policy this describes is Chapter 68, and the architecture it obstructs is Chapter 54. The delegated access it replaces is discussed there too. Combining data from many sources is Chapters 51 and 53, and the confused deputy problem is Chapter 37.
