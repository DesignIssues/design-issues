Chapter 70

CORS: Browser Distrust of Web Apps

2018

Source CORS: Browser Distrust of Web Apps, a Design Issues note by Tim Berners-Lee, 2018. read the original

The short version

Browsers treat every web app as hostile: a script may talk only to the site it came from. Servers must opt in, with CORS headers, before other apps may read their data. Extra rules for logins and caches made opting in hard. Berners-Lee calls it the web’s worst design.

The question

A simplified backgrounder from July 2018 on the mechanism that makes Chapter 54’s architecture hard to build. It opens with a borrowed image, and adds a third character.

Ted Nelson talks about the two gods of Literature, the reader and the writer. They are each invincible: the writer can write whatever they want, and the reader can if they chose read nothing the writer has written. Here we have though three gods, the reader, the writer and the spy, and none of them are omnipotent. Authorizing Web Apps and CORS, 2018

70.1 The assumption

The browser’s operating principle is rarely written down:

The assumption that a web browser makes is that whenever the user is using a web app, that the web app is trying to attack the user. Authorizing Web Apps and CORS, 2018

So an app is untrusted, limited, and told little about why it is blocked:

This is therefore a very hostile environment for which to program, unless the app is something rather trivial which does not access data on the web. Authorizing Web Apps and CORS, 2018

70.2 The attack that caused it

The attack behind this is cross-site scripting (XSS). A script is a small program a page carries and the browser runs.

Forbidding scripts all network access could not stand: a bank’s own page must fetch more data from the bank. So a script may talk freely to its own origin, the protocol and domain of an address (say, https://www.bankofamerica.com), and to nothing else: the same-origin policy of Chapter 68.

This allows banks to work pretty well. Authorizing Web Apps and CORS, 2018

70.3 What it forbids

Two wanted uses are forbidden. A service that assesses another page cannot reach it. The second is the one the note dwells on:

When a large amount of open public data started to become available from governments and so on, there was a flourishing of sites which loaded data from many different sites and provide a “mashup” of the data — a combined visualization of data from many sources which would typically l was to insights that you would not get from one data source alone. Authorizing Web Apps and CORS, 2018

Such a site, the note says, typically no longer works. Combining sources is the argument of Chapters 51 and 53; the browser forbids it unless the data’s owner opts in (section 70.5).

70.4 The shape of the problem

The note’s three gods map onto the attack:

CharacterIn the attackWhat they want
The readerAliceTo use any app on any data she can reach
The writerThe site or app she chose to useTo fetch and combine data for her
The spyMalloryTo borrow Alice’s access and carry data away

Every mechanism should stop the spy without disabling the other two, yet the browser distrusts the writer, the party Alice chose. Chapter 54 moves the data out from behind the boundary, so an app reaching the user’s own storage does the ordinary thing.

70.5 How permission is granted

A browser cannot tell a private webcam from open government data, and webcams could not be changed, so publishers must opt in under Cross-Origin Resource Sharing (CORS) by adding a header, a labelled line sent with a reply:

HeaderMeaningExample from the note
Access-Control-Allow-Origin: *Any origin may read thisPublic data
Access-Control-Allow-Origin: a named originOnly that origin may read thisA bank letting its credit card company’s code reach customer data

Reply headers are blocked too, even ordinary ones such as Link, unless the server lists them in another header (the note uses Access-Control-Allow-Headers; the specification’s name for this job is Access-Control-Expose-Headers). The browser also first sends a hidden preflight request (HTTP OPTIONS), an extra round trip.

70.6 The twist

Fearing * was a “footgun” managers would put even on per-user pages, the designers made browsers refuse it when a request carries credentials, such as a login; the server must name the origin exactly.

That splits the web in two: requests sent with a login, and requests sent without. A code library that asks the browser to fetch something cannot know whether a login will be attached, so it cannot rely on *. Public data servers were therefore told to copy back whatever origin asked (origin reflection): active code, not a configuration line.

Berners-Lee proposes a fixed header, PUBLIC_AND_UNCUSTOMIZED, instead:

where the system manager would have no one else to blame for sing it on any resource which was secret, or was customized with a user's identity? One might of thought. But that is not how CORS was done. Authorizing Web Apps and CORS, 2018

70.7 Vary: Origin and the cache

Browsers keep copies of replies in a cache; a copy marked for origin A, reused for an app from B, is silently blocked. One more header, Vary: Origin, makes the cache keep a copy per origin.

The verdict:

The CORS design most go down in history as the worst piece of design in the whole web. Authorizing Web Apps and CORS, 2018

An epilogue adds that Chrome 59, and Firefox in July 2018, reused cached replies across origins despite Vary: Origin. Solid must be built on this ground.

What happened since

  • The cache bug was reported again. On 12 July 2019 Michiel de Jong published “CORS bug in several browsers”, cited in the note’s follow-up, and opened bugs with Chrome and Firefox.
  • The boundary kept being redrawn. Firefox 79 (July 2020) and Chrome 92 (July 2021) made a page set the Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers before using shared memory between scripts.
  • The attack class survived. The OWASP Top 10 of 2021, a widely used ranking of web security risks, placed Injection, which includes cross-site scripting, third.
