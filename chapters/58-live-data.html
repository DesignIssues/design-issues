Chapter 58

Live data

2021

Source Live data, a Design Issues note by Tim Berners-Lee, 2021-10-20. read the original

The question

Written in October 2021, this short note adds the last missing piece to the architecture of Volume VI. Data can be read, written and arranged. What remains is telling the other reader that it changed.

Live update turns what might have been once a read-only web and is now with Solid common login and access control and HTTP PUT a read-write web, into a live-read-write web Live Data, 2021

58.1 Why not just ask again

58.2 The use case he thinks people underestimate

Collaborative editing is the obvious application and the note says so. Then it argues that the obvious case is the least interesting one:

But the ability to simply have any two displays on sync across the planet when on person is (say) dragging a marker across a map and the other person is watching, synchronized shopping lists, suggest that the value of live update could inspire many moore things than editing documents. Live Data, 2021

A shopping list is the example worth keeping. It is not a document being co-authored. It is a small piece of shared state that two people in different places both act on, and which is wrong the moment it is stale. Most shared data is like this.

58.3 Notification is a spectrum

A short passage puts the mechanism in a family, and the range is wider than people usually consider when they say notification:

MechanismLatency
An event inside a running programEffectively instant
A socket message across the networkOf the order of a tenth of a second
A text or mail messageSeconds to hours
A subscription to a feed of articlesWhenever you look

Berners-Lee sets the target explicitly at the fast end, ideally of the order of a hundred milliseconds, and notes that one could imagine mail carrying aggregated heaps of update messages. Chapter 64 is what the slow end of this spectrum became.

58.4 The developer should not have to think about it

The section on frameworks makes a claim about where this capability belongs, and it is the same argument as Chapter 19:

Where we have build development kit stacks and libraries which provide this automatically so that the developer does not have to do anything special, just turn it on, that is ideal. Live Data, 2021

Two solutions are described. One builds the ability to refresh into each widget. The other, which Berners-Lee attributes to the popular framework of the day, has the developer write a function from data to interface and then re-runs that function whenever the data changes.

The second is the more interesting because it removes the problem rather than solving it. If the interface is a function of the data, there is no update logic to get wrong; there is only the function, and a system that reapplies it.

58.5 What it points towards

The conclusion names the two limitations that the next design would have to remove, and both are structural rather than incremental:

The first is topology. The current arrangement is a hub and spoke, with a server in the middle and clients around it. Other topologies would allow peers to update each other directly.

The second is offline operation. Sending the change rather than a notice, as Chapter 45 argued, is what allows a client to work while disconnected and reconcile afterwards, which is what the conflict-free replicated data structures Berners-Lee names are for.

He closes by declining to let the limitations obscure the achievement: the current functionality already gives a lot of value. A hub-and-spoke system that only says something changed is enough to make a chat application, a shared notepad, and two maps that move together.

What happened since

  • The protocol was replaced with a general one. The Solid Notifications Protocol, published in 2022, supports several delivery channels rather than one socket, which is the spectrum of section 58.3 turned into a specification.
  • Sending the change won generally. Conflict-free replicated data types became the standard basis for collaborative editing and local-first software through the 2020s, which is the direction this note points at and the architecture it does not yet have.
  • Local-first became a movement. The principle that an application should work offline and reconcile later, named here as a future goal, acquired a literature and a community of practice.
  • The framework argument was settled. Rendering an interface as a function of state is now the dominant model, which makes live data an ordinary property of an application rather than a feature.
