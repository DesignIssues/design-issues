Chapter 58

Live data

2021

Source Live data, a Design Issues note by Tim Berners-Lee, 2021-10-20. read the original

The short version

Solid can tell an application when the data it is showing has changed. In 2021 the message says only that something changed, and the application must reload everything. Berners-Lee wants the message to carry the change itself, which would also open the way to working offline and to devices updating one another directly.

The question

Written in October 2021, this short note adds the last missing piece to the architecture of Volume VI. Data can be read, written and arranged. What remains is telling the other reader that it changed.

Live update turns what might have been once a read-only web and is now with Solid common login and access control and HTTP PUT a read-write web, into a live-read-write web Live Data, 2021

58.1 Why not just ask again

When one person changes a list stored in a Solid Pod, how does another person’s screen find out? The simplest answer is polling: the application asks the server “has it changed?” every few seconds.

The alternative is subscribing (publish/subscribe, or pub/sub): the application keeps a connection open and the server speaks first when something happens.

Solid already subscribes, using a WebSocket: a network connection that stays open so that either side can send at any time. Berners-Lee calls it basic but effective. In 2021 the server sends only a bare ‘PING’ notification that the resource has changed, and the application then fetches the whole resource again. He wants the server instead to send a PATCH, a message carrying only the change, to reduce both the bandwidth and the number of round trips between client and server.

58.2 The use case he thinks people underestimate

Collaborative editing is the obvious application and the note says so. Then it argues that the obvious case is the least interesting one:

But the ability to simply have any two displays on sync across the planet when on person is (say) dragging a marker across a map and the other person is watching, synchronized shopping lists, suggest that the value of live update could inspire many moore things than editing documents. Live Data, 2021

He adds people wrestling over where an event should go in a calendar, each using a different calendar program. The shopping list is the example worth keeping: not a co-authored document but a small piece of shared state, wrong the moment it is stale. Most shared data is like this.

58.3 Notification is a spectrum

A short passage places the mechanism in a wider family:

MechanismSpeed, in his words
An event inside a running program (DOM events in a web page)more or less instant
A message across the network (web sockets)fairly rapid
SMS and email messagesslower
Subscribing to a feed of news articles (NNTP, the old Usenet news protocol)the slow end

He sets the target at the fast end, ideally of the order of 100 milliseconds, and notes that one could imagine email carrying aggregated heaps of update messages. Chapter 64 is what the slow end became.

58.4 The developer should not have to think about it

The section on frameworks says where this capability belongs:

Where we have build development kit stacks and libraries which provide this automatically so that the developer does not have to do anything special, just turn it on, that is ideal. Live Data, 2021

He describes two ways of doing it. Solid’s own interface library, solid-ui, builds the ability to refresh into each widget. React has the developer write a function from data to interface, and re-runs that function whenever the data changes.

Take the shopping list. The data is milk and eggs; the function draws a list of two lines. Bob adds bread; the data becomes milk, eggs and bread; the same function runs again and draws three lines. No code anywhere says “insert a row”. There is no update logic to get wrong, only the function and a system that reapplies it.

58.5 What it points towards

The conclusion names two limitations the next design would have to remove, both structural rather than incremental.

The first is topology, the shape of who talks to whom. Today it is hub and spoke: a server in the middle, clients around it. He asks for other topologies, such as devices updating one another directly.

The second is offline operation. Sending the change rather than a notice, as Chapter 45 argued, lets a client work while disconnected and reconcile afterwards. He names Conflict-free Replicated Data Types (CRDTs) for this: a way of recording changes so that copies edited separately can always be merged without a conflict.

He closes by saying the current functionality already gives a lot of value: enough for a chat application, a shared notepad, and two maps that move together.

What happened since

  • The protocol was replaced with a general one. The Solid Notifications Protocol, first drafted in 2022, supports several delivery channels rather than one socket, which is the spectrum of section 58.3 turned into a specification.
  • Sending the change spread. CRDTs became a widely used basis for collaborative editing and local-first software through the 2020s, alongside the older technique of operational transformation.
  • Local-first grew. The term was already in use when he wrote, after Ink & Switch’s 2019 essay “Local-first software”. The idea that an application should work offline and reconcile later has since gathered a wider community of practice.
