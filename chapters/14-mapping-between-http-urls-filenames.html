Chapter 14

Mapping between HTTP URLs and filenames on a server

2015

Source

This chapter is about Mapping between HTTP URLs and filenames on a server, a Design Issues note by Tim Berners-Lee, dated 2015-04-10.

Read the original at https://www.w3.org/DesignIssues/HTTPFilenameMapping.html. The Design Issues notes are Tim Berners-Lee's personal notes and are not endorsed by W3C. This book is commentary; where it quotes, it attributes.

The question

This is the most practical note in Volume II and the only one that reaches a constructive answer rather than a principle. Written in April 2015 after a discussion with Andrei Sambra and elaborated in 2018 with Ruben Verborgh, it asks a question every read-write server must answer: given an HTTP URI, which file on disk does it name?

It belongs here because it is Chapter 12's file-and-HTTP correspondence meeting Chapter 2's opacity axiom, and discovering that the two cannot both be had in full.

14.1 Why anyone would want both views

The motivation is that the two spaces are good at different things, and the note sets them side by side. HTTP space gives access to people who are not on the machine, and access control by Web-wide or server-wide identity. File space gives files one does not want to share, access control by ordinary users and groups, and faster access for serious data munging. On one side, browsers and Web services; on the other, command-line programs, scripts, a version control system, and a build system.

It is actually pretty interesting to live on the edge, or more specifically on the intersection of these worlds where you can address the same files both as local files and as resources on the web. Mapping between HTTP URLs and filenames on a server, 2015

14.2 Three requirements, two of which may be had

The note's contribution is to state the conflict exactly. Three things are wanted, and they cannot all hold.

He works each corner in turn and rejects all three. Dropping direct correspondence defeats the premise of the exercise. Dropping arbitrary PUT turns a general-purpose storage space into one that only applications adapted to that server's constraints can use. Dropping correct extensions is the one he refuses outright, and the refusal is worth quoting because it is the only place in the collection where he calls something non-negotiable:

Control of the local file extensions of things received from elsewhere is a crucial part of web security 101 and not negotiable. Mapping between HTTP URLs and filenames on a server, 2015

The attack he has in mind is stated concretely: someone writes a file whose URI ends in .exe but whose content type is text/html, and in file space the operating system sees a program. The extension is metadata that the local system trusts and that a remote party supplied.

14.3 The sweet spot

The resolution is to weaken the first requirement rather than abandon any of the three:

Some filenames and URIs should directly correspond -- so that links work on both spaces for people who pick those names Mapping between HTTP URLs and filenames on a server, 2015

The rule is then mechanical. A URI maps directly to a filename if and only if that produces a correct extension. Otherwise it maps to a different filename that can be round-tripped back to the URI and does have the right extension, flagged by an otherwise forbidden character such as a dollar sign.

URI on the webContent typeFilename on the system
/space/foo.htmltext/html/space/foo.html
/space/foo.bartext/html/space/foo.bar$.html
/space/foo.exetext/html/space/foo.exe$.html

The bargain is stated plainly. A publisher willing to use URIs with file-like extensions gets the two-space mapping. One who is not does not, and everything else still works.

14.4 The asymmetry nobody expects

A short passage at the end is the most useful thing in the note for anyone implementing this, because it notices that the mapping is not one function but three.

On PUT, the client supplies both the URI and the content type, so the server computes the filename directly: a simple mathematical function. On GET, the server has only the URI, and must search the directory for the file that is either the URI or the URI with a dollar suffix, so the mapping depends on what is on disk. Listing a directory is a simple function again, in the other direction.

Berners-Lee notes the prize for getting it right, which is larger than one server:

many servers end up using exactly the same mapping, with the result that I can simultaneously run more than one HTTP server over the same file space. Mapping between HTTP URLs and filenames on a server, 2015

A shared mapping makes a directory tree portable between servers: it can be archived on one and unpacked on another and remain the same Web space. That is the file-system equivalent of the relative-URI property argued for in Chapter 12.

What happened since

  • The problem became a specification question. The Solid Protocol, whose version 0.9 was published in December 2021, specifies how servers map resource URIs to storage and how auxiliary metadata is kept alongside, which is the interoperability goal section 14.4 names.
  • The attack it defends against stayed real. Content type confusion remains a standard class of vulnerability, and the general defence is the one implied here: do not let a remote party's chosen name determine how a local system treats a file.
  • General-purpose servers did not adopt the convention. Off-the-shelf servers still map URLs to filenames directly, which is Try 3, and therefore rely on not granting untrusted write access rather than on making writes safe.
  • The two-space workflow persisted. Static site generators and file-backed publishing pipelines are the mainstream version of what this note describes, and they avoid the problem entirely by having no arbitrary PUT.

Connections

The correspondence this chapter defends is introduced in Chapter 12. The temptation to read a type from a file extension is exactly the opacity breach warned against in Chapter 2, arriving here from the other side: the server may read it, and the local operating system must not be allowed to. The read-write Web this note assumes is Chapter 50, and the storage model is Chapter 54.

Questions 4

14.1 Restate the three requirements as propositions and show that they are jointly unsatisfiable. Which one does the resolution weaken, and by how much?

14.2 The GET mapping must consult the directory while the PUT mapping need not. Explain why, and say what this costs a server handling many requests.

14.3 The dollar sign is chosen because it is otherwise forbidden. What breaks if a character already in use is chosen instead?

14.4 Berners-Lee calls control of local file extensions non-negotiable. Identify the trust boundary this protects and name the party on each side of it.
