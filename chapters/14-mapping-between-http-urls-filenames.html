Chapter 14

Mapping between HTTP URLs and filenames on a server

2015

Source Mapping between HTTP URLs and filenames on a server, a Design Issues note by Tim Berners-Lee, 2015-04-10. read the original

The short version

A server can show the same files both as web pages and as ordinary files on disk. But if anyone may upload under any name, a stranger can upload a web page called foo.exe, and a user’s computer will treat it as a program. The fix: keep the name when it is honest; otherwise add a $ and the right extension (foo.exe$.html).

The question

This is a practical note that ends in a concrete rule. Written in April 2015 after a discussion with Andrei Sambra and elaborated in 2018 with Ruben Verborgh, it asks a question every read-write server (one that lets clients store files as well as fetch them) must answer: given an HTTP URI, which file on disk does it name?

It belongs here because it is Chapter 12’s file-and-HTTP correspondence meeting Chapter 2’s opacity axiom (do not read meaning into the characters of a URI), and discovering that the two cannot both be had in full.

14.1 Why anyone would want both views

Take a concrete case: a script edits a CSV file on a server, and colleagues read the same file in a browser. The script sees file space, the folders and filenames of the operating system. The colleagues see HTTP space, the same files reached by URI over the Web. The note sets out what each is good at:

HTTP spaceFile space
Reachpeople not on the machineusers on the machine; holds files not meant to be shared
Access controlWeb-wide or server-wide identityUnix users and groups
Speedslowerfaster, for serious data processing
Toolsbrowsers and Web servicescommand-line programs, scripts, version control, build systems

The obvious mapping is to make the URI path the filename. The snag is types. A file’s extension is the part after the last dot; the operating system uses it to decide what a file is. HTTP sends the type separately, in a Content-Type header such as text/html. On a server that accepts uploads, the two can disagree.

14.2 Three requirements, two of which may be had

Two HTTP request types (methods) matter: PUT (upload to a chosen address) and GET (fetch). Three things are wanted, and they cannot all hold.

He tries each design on the same three uploads, all sent as text/html. The table gathers his examples, with the sweet spot of section 14.3 for comparison; the http://localhost/space/ and /users/bob/space/ prefixes are left out.

URITry 1Try 2Try 3Sweet spot
foo.htmlfoo.html.htmlfoo.htmlfoo.htmlfoo.html
foo.barfoo.bar.htmlblockedfoo.barfoo.bar$.html
foo.exefoo.exe.htmlblockedfoo.exe (danger)foo.exe$.html

He rejects all three. Try 1 breaks the correspondence that was the point of the exercise. Try 2 turns a general-purpose storage space into one that only applications adapted to that server’s constraints can use. Try 3, which leaves extensions wrong, he refuses outright:

Control of the local file extensions of things received from elsewhere is a crucial part of web security 101 and not negotiable. Mapping between HTTP URLs and filenames on a server, 2015

The attack he has in mind is concrete. Someone uploads a file whose URI ends in .exe but whose content type is text/html, and in file space the operating system sees a program. The extension is metadata that the local system trusts and that a remote party supplied.

14.3 The sweet spot

The resolution is to weaken the first requirement rather than abandon any of the three:

Some filenames and URIs should directly correspond -- so that links work on both spaces for people who pick those names Mapping between HTTP URLs and filenames on a server, 2015

The rule is then a two-step recipe:

  1. If the URI already ends in the right extension for its type, use it as the filename.
  2. If not, add $ and the right extension. To get the URI back, cut everything from the $.

The note calls $ an “otherwise forbidden character”: one the server does not allow in ordinary URIs, so no real name can collide with a tweaked one. The last column of the table in section 14.2 shows the result.

So a file uploaded as report.html appears on disk as report.html. One uploaded as report appears as report$.html: it still works over HTTP, but a local link to report will not find it.

14.4 One mapping, three directions

The mapping is not one function but three.

On PUT the client supplies both the URI and the content type, so the filename is, in the note’s words, “a simple mathematical function”. On GET the server must search the directory. Listing a directory is a simple function again, in the other direction. Berners-Lee notes the prize for getting it right, which is larger than one server:

many servers end up using exactly the same mapping, with the result that I can simultaneously run more than one HTTP server over the same file space. Mapping between HTTP URLs and filenames on a server, 2015

A shared mapping also makes a directory tree portable: it can be archived (the note says “tar up”) on one server, unpacked on another, and remain the same Web space. That is the file-system counterpart of the relative-URI property of Chapter 12: links inside the tree keep working wherever it is unpacked.

What happened since

  • Solid servers adopted the convention. Solid servers are the personal data stores of Chapter 54. Ruben Verborgh added a URL-to-file mapper to Node Solid Server in March 2018, and version 5.0.0 (March 2019) stores a resource whose name lacks the right extension under a $-suffixed filename, so foo.bar sent as text/html becomes foo.bar$.html. The Community Solid Server’s extension-based mapper, written from 2020, does the same. The Solid Protocol itself leaves storage to each implementation.
  • The attack it defends against stayed real. Unrestricted upload of a file with a dangerous type is catalogued as CWE-434 in MITRE’s Common Weakness Enumeration, which still lists it in 2026, and the general defence is the one implied here: do not let a remote party’s chosen name decide how a local system treats a file.
  • General-purpose servers did not adopt the convention. Servers such as Apache and nginx, when configured to accept WebDAV PUT (WebDAV is an HTTP extension that lets clients write files to a server), still map URLs to filenames directly, which is Try 3, and generally rely on not granting untrusted write access rather than on making writes safe.
  • The two-space workflow persisted. Since the 2010s, static site generators (tools that build a website from local files and upload the result, such as Jekyll, 2008, and Hugo, 2013) have been the mainstream version of what this note describes, and they avoid the problem entirely by having no arbitrary PUT.

Connections

The correspondence this chapter defends is introduced in Chapter 12. The temptation to read a type from a file extension is exactly the opacity breach warned against in Chapter 2, arriving here from the other side: the server may read it, and the local operating system must not be allowed to. The read-write Web this note assumes is Chapter 50, and the storage model is Chapter 54.
